# Jev のカスケード構成(考え方と具体例)

TypeSafe AI の Jev を使うときの基本形は「Jev を前段に置き、コードで済むものはコードで処理し、難しい少数だけを後段(フロンティア LLM や人間)に回す」多段構成。TypeSafe の公式用語ではなく、公式ドキュメントと周辺記事が描く使い方をまとめた呼び方。

## 1. 前提: Jev は「判定」専用で「生成」はしない

- Jev は state(判定対象と文脈)と型付きの質問を受け取り、確率と confidence を返す。テキストは返さない。
- 質問は3種類。Choice(N択、`choice` + `probabilities` + `confidence`)、Score(段階評価、`score` + `probabilities` + `confidence`)、Noul(命題が真である確率、0〜1)。
- 1回の呼び出しに複数の質問を混ぜられ、すべて同じ state に対して並列・独立に評価される。質問を増やしても応答時間はほぼ変わらない。
- 公式ドキュメントの位置づけは「知識のある人が数秒で下せる直感的な判断(System 1)」。長い推論や複数要因の重み付けが要る質問は分解して、それぞれ別の質問にし、組み合わせはコードで書く。

つまり Jev は System 2 の仕事(生成・推論・対話)を最初からやらない。だから後段が必要になり、自然と多段構成になる。

## 2. カスケードの3段

```
入力
 │
 ▼
[1] Jev: 型付き質問を一括で投げ、確率と confidence を得る(数十〜数百ms、ほぼ無料)
 │
 ▼
[2] コード: 確率・confidence を閾値と論理で組み合わせ、決められるものは決める
 │
 ├─ 決められた → 定型処理・ルーティング・フィルタで完結
 │
 └─ 決められない(低 confidence、生成が必要、例外) → [3]
                                                       │
                                                       ▼
                                          [3] 後段: フロンティア LLM または人間
```

各段の役割:

| 段 | 担当 | 得意なこと | コスト |
|---|---|---|---|
| 1 | Jev | 分類、スコアリング、真偽判定を大量・高速に | ごく低い |
| 2 | 自分のコード | AND/NOT/閾値/優先順位、集計、ルーティング | ゼロ |
| 3 | LLM / 人間 | 自由文の生成、長い推論、文脈が足りない例外の解決 | 高い |

設計の要点は「3段目に流す量を最小にする」こと。Jev と閾値の校正がうまくいくほど、高価な段に届く件数が減る。

## 3. 段の間をつなぐルール

- **confidence で分岐する。** TypeSafe の想定は「confidence が高ければソフトウェアがそのまま行動し、低ければエスカレーション」。
- **閾値は質問ごとに校正する。** Noul の分布は質問によって中央値が 0.05〜0.40 と大きく違う。0.5 に普遍的な意味はない。小さなサンプルで分布を見てから決める。
- **実用上は3分割。** 高い帯は自動採用、中間の帯は後段へ、低い帯は捨てる。2値にしない。
- **生の確率を保存する。** ラベルだけ保存すると閾値を変えるたびに再判定が要る。確率を残せば切り直せる。
- **判断ロジックはコードに置く。** ルールを変えるとき、質問文を書き直すのではなく係数や閾値を変える。再判定なしで変えられる。

## 4. 具体例

### 例A: サポートチケットのトリアージ

**state**: チケット本文、件名、顧客のプラン、過去の問い合わせ回数

**Jev への質問(1回の呼び出し)**:
- Choice `category`: 請求 / 障害 / 機能要望 / 使い方 / other
- Score `urgency`: 0(急がない)〜3(今すぐ)
- Noul `is_churn_risk`: 解約を示唆しているか
- Noul `needs_human_reply`: 定型回答では済まないか

**コード側の分岐**:
```python
r = jev.system_one(state, questions)

if r.category.confidence < 0.5:
    route_to("human_queue")            # 3段目
elif r.category.choice == "障害" and r.urgency.probabilities[3] > 0.6:
    page_oncall(); route_to("p1")      # 2段目で完結
elif r.is_churn_risk > 0.7:
    route_to("account_manager")        # 2段目で完結
elif r.needs_human_reply < 0.2:
    send_template(r.category.choice)   # 2段目で完結
else:
    draft = llm.generate(ticket)       # 3段目(生成が必要)
    route_to("agent_review", draft)
```

ポイント: `urgency` の期待値ではなく最上段の確率 `probabilities[3]` に閾値を置く。期待値は両端に割れると真ん中に寄るので、検知用途には端の確率を使う。

### 例B: コメントの分類(300件)

**state**: コメント本文、投稿者属性(視聴者/関係者)、動画のカテゴリ、premise に用語集

**Jev への質問**: 話題(Choice、`other` あり)、離脱理由か(Noul)、皮肉か(Noul)、攻撃性(Score)など8問を1回で

**カスケード**:
- 「離脱理由か」が単独だと宣伝コメントも拾う → 「話題」との AND で除外(2段目)
- 「皮肉か」は無関係な入力でも 0.3〜0.4 が出る → 絶対値でなく順位で上位だけ使う(2段目)
- confidence 0.4 未満、または既存の自己申告ラベルと食い違う行 → 人間の目視キュー(3段目)。300件のうち21件を見るだけで系統的誤りが1つ見つかった

ここでは3段目が LLM ではなく人間。「難しい少数だけを高価な段に回す」構造は同じ。

### 例C: ゲームやシミュレーション内の行動選択

**state**: 現在の局面(位置、体力、周囲の状況)

**Jev への質問**: Choice `next_action`: 前進 / 退避 / 攻撃 / 待機

**カスケード**:
- confidence が高い → そのまま実行(毎フレーム呼べる速度)
- confidence が低い、または状況が想定外 → 事前に定めた安全な既定行動にフォールバック、あるいは上位のプランナー(LLM や探索)に判断を委ねる

リアルタイムループでは3段目に LLM を置けないことが多いので、「既定行動」が後段になる。

### 例D: RAG やエージェントの前処理

**state**: ユーザーの入力

**Jev への質問**: 検索が必要か(Noul)、対象ドメイン(Choice)、有害/対象外か(Noul)、意図(Choice)

**カスケード**:
- 対象外の確率が高い → 定型で断る(LLM を呼ばない)
- 検索不要かつ意図が明確 → キャッシュ済みの回答を返す
- それ以外 → 意図とドメインをヒントとして LLM に渡す(3段目だが、Jev の結果で LLM のプロンプトを絞れる)

## 5. うまくいかないときの疑う順番

1. state に情報が足りているか(その state だけを見せられた人間が判断できるか)
2. 質問が複数の軸を持っていないか(「かつ」「ただし」を含んでいたら分ける)
3. criteria に「紛らわしいが該当しないもの」が書かれているか
4. ドメイン用語を一般語として誤読していないか(premise に用語集)
5. 閾値が質問の分布に合っているか

モデルを疑うのは最後。3段目に流れる量が多いときも、まずこの順で1段目を直す。

## まとめ

- Jev は型付きの判定関数。生成と推論は最初から外に置く。
- 1段目(Jev)で特徴量を一括で取り、2段目(コード)で組み合わせ、3段目(LLM/人間/既定行動)に例外だけを流す。
- 段の境界は confidence と質問ごとに校正した閾値。生の確率を残しておけば境界は後から動かせる。
- 設計の成否は「3段目に届く件数をどれだけ減らせたか」で測る。
