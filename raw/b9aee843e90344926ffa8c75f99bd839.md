# a

リポジトリを clone して、README・`kairon.py`・`agents.md`・`.claude/rules/kairon.md`・memo 群（v1 設計や名前の由来）を読みました。

## kairon の要点

- **コンセプト**: cron（chronos＝時計の時間）に対し、kairon（kairos＝ふさわしい時）は「今がその機会か」を LLM が判断するスケジューラの**概念名**。発火条件 `condition:` を自然言語で書く。
- **参考実装 kairon-sta（v2）**: `python kairon.py` を叩くと、`agents.md` 全体をプロンプトに埋め込んで **単一の `claude -p`** を起動する。その 1 プロセスが JSE フロー（judgement → strategy → execution）を全部こなす。v1 の「dispatcher claude ＋ エージェントごとに claude を fire-and-forget」構成は、パフォーマンスとデバッグのしやすさを理由に捨てられている。
- **判断材料**: `--append-system-prompt` で渡される現在日時と `logs/<name>.log` が主。ツールは Read / Write / Edit / Glob / Grep / WebSearch / WebFetch のみで、Bash は禁止。
- **自分では常駐しない**: 起動タイミング（タスクスケジューラで 3 時間おきなど）は利用者任せ。つまり kairon は **「呼ばれたときに、今やるべきかを判断する」ポーリング型**です。

この構造から、kairon が cron に勝てる場面は次の 3 条件を満たすときだと考えます。

1. 発火条件が**時刻以外の状態**（ログの中身、ファイルの内容、外の世界）に依存する
2. その状態が**意味的・曖昧**で、cron 式やスクリプトでは書きにくい
3. 実行が**数時間単位でずれても問題ない**

## 真価が出そうなユースケース

### 1. 取りこぼしを自動で補う（PC を閉じがちな人向け）

cron やタスクスケジューラは、指定時刻に PC が寝ていると実行されません。kairon なら「最後にやったのはいつか」をログから見て判断するので、呼ばれた時点で自然に追いつきます。個人の Windows PC 運用とは特に相性が良いと思います。

```markdown
# daily-digest
condition: 最後の実行から 20 時間以上経っていて、かつ現在が 7〜23 時のとき
```

### 2. 暦の意味で決まる条件

cron では書けない、あるいは書くと地獄になる暦の条件です。

```markdown
# monthly-report-reminder
condition: 今日が日本の祝日と土日を除いた「月の最終営業日」かその前営業日で、今月まだ実行していないとき

# after-holiday-catchup
condition: 今日が 3 日以上の連休明けの最初の平日で、今日まだ実行していないとき
```

### 3. 結果に応じて間隔が伸び縮みする（間隔反復・適応的頻度）

私が kairon の一番の見せ場だと思うのがこれです。**次にいつ動くかを、前回の結果が決めます。**

```markdown
# vocab-review
condition: ログ最終行の「次回目安」を過ぎていたら実行。目安が無ければ実行

単語帳 notes/vocab.md から 10 語選んで問題を作り、notes/quiz.md に書き出せ。
前回の quiz.md に回答があれば採点し、正答率が 80% 以上なら前回間隔の 2 倍、
未満なら 1 日を「次回目安」としてログに記録せよ。
```

cron では原理的に書けない「自己調整するスケジュール」を、ログ 1 行で実現できます。

### 4. 人間の自然文メモで挙動を操る

`status.md` のような状態ファイルを置き、自分の近況を自然文で書いておきます。各エージェントの condition がそれを参照します。

```markdown
# weekday-news
condition: 平日で今日未実行、かつ status.md に休暇・出張・「ニュース不要」等と書かれていないとき
```

設定を編集しなくても「今週は旅行中」と一行書くだけで全体の挙動が変わります。自然言語条件ならではの使い方です。

### 5. エージェント同士を連鎖させる（疑似イベント駆動）

あるエージェントのログを、別のエージェントの発火条件にします。

```markdown
# article-collector
condition: 前回から 6 時間以上経過
関心テーマの記事を探し、見つけたら URL と一行要約をログに追記

# weekly-synthesis
condition: article-collector のログに前回の synthesis 以降の記事が 10 件以上溜まったとき
溜まった記事から共通するトレンドを 1 本の考察にまとめ notes/ に保存
```

「件数」ではなく「**テーマ的にまとまりが出てきたら**」のような意味的な閾値にできるのも強みです。

### 6. 外部の変化を監視する（コストの安い門番つき）

```markdown
# release-watch
condition: 前回チェックから 12 時間以上経っているとき
（本文で）監視ページを WebFetch し、ログに記録済みの最新版より新しいリリースがあれば要点を追記
```

注意点として、judgement の段階で毎回 WebFetch させると、呼ばれるたびにコストがかかります。condition 側は**ログだけで判定できる安い条件**にしておき、重い確認は本文でやるのがよいと思います。

### 7. 失敗が続いたら間を空ける（自動バックオフ）

```markdown
condition: 今日未成功で、かつ直近のログが連続 ERROR の場合は最後の ERROR から (連続回数 × 3) 時間以上空いているとき
```

## condition を書くときのコツ（実装を読んだうえでの所感）

- **判定材料が観測できる条件にする。** judge が見られるのは現在日時・ログ・読めるファイル・Web だけです。「気分が良いとき」のような観測できない条件は発火が不安定になります。
- **粒度をポーリング間隔より粗くする。** 3 時間おきの起動で「9:00〜9:30」と書くと、ほぼ発火しません。
- **ログの書式を固定する。** `YYYY-MM-DD HH:MM:SS | ...` のように揃えておくと、「○時間経過」の計算ミスが減ります。
- **v2 の判断結果は残らない。** 現在のプロンプトでは最終報告が stdout に出るだけで、見送った判断は記録されません。`logs/_kairon.log` に「起動対象と理由、見送り理由」を毎回追記させると、デバッグしやすくなるうえ、「前回見送ったなら今回は実行」といった条件も書けるようになります。
- **v1 のガイドラインが消えている。** v1 の dispatcher にあった「迷ったら動かさない」という方針が v2 のプロンプトにはありません。過剰実行を避けたいなら戻す価値があります。
- **作業ディレクトリ外のファイル。** `notes/` や Obsidian vault など kairon の作業ディレクトリ外を参照する場合、`dontAsk` モードでは読めない可能性があります（未検証です）。kairon 配下に置くか、`--add-dir` の追加を検討してください。

まとめると、kairon の真価は「**いつ**やるか」ではなく「**どういう状況になったら**やるか」を書けることにあり、特に **3（適応的間隔）と 4（自然文の状態ファイル）** は cron の延長線上では作れない体験です。どれか 1 つ、`agents.md` にそのまま貼れる完成形に仕上げましょうか？
