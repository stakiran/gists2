## つくっているツールの傾向

ざっくり5つの系統に分かれていると理解しました。

**1. テキストベースのタスク管理**：一番太い系統です。Tritask（TaskChute をテキストで）、todaros（日次ルーチン生成）、fudaros（未来にタスクを置く）、commitas、todochute、sortl、lisna など。「1行1タスク」「プレーンテキストを人間が直接編集する」「ソートや生成はツールに任せる」という思想が一貫しています。

**2. カウンター・記録系**：effecounter、counta、counte、awayfromABCD など。「やったことを最小の手間で記録し、後で振り返る」ためのツールで、ほぼ Python CLI＋手元の md/json です。

**3. AI クリップボード系**：cb2ai、aism、askai、screenshot2text（Claude Vision で OCR）、raic など。いずれも自分の API キー前提です。

**4. 発想・思考ツール**：3card、mandaland、concept-field、listinst など。ブラウザで動く単体 HTML が多いです。

**5. Windows 常駐・ランチャー系とコンセプト文書**：AutoHotkey、バッチ、秀丸マクロ類と、CaaT・Four-jects・1on1-kit などのフレームワーク文書群。

最近は「単体 HTML を GitHub Pages に置く」スタイルが増えていて、tritask-webapp1（Firebase）、todaros-puter（Puter）、tasks-appdata.html（Drive appData）と、**データ置き場の方式を比較検討している**のが見て取れます。

## 化けそうな候補

### 1. Tritask Web の Puter 化（本命）

tritask-webapp1 の README に書かれている注意点は、そのまま Puter で解決できる課題です。具体的には「データが生で管理者に見える」「Firebase 無料枠（1日1万回）をすぐ超えるかも」の2点で、Puter ならデータはユーザー自身のアカウントに入り、費用もユーザー持ちなので、開発者側の上限を気にせず公開できます。

しかも Tritask には既に tritask.github.io という公開サイトと既存ユーザーがいて、todaros-puter で fs ベースの実装パターンも確立済みです。データ形式もテキスト1ファイルなので `puter.fs` にそのまま載ります。さらに todaros と統合して「朝開くと今日のルーチンが Tritask の『今日やる』に流し込まれる」ようにすると、2つの道具を1つの体験にまとめられ、単なる移植以上の価値が出ます。

### 2. AI クリップボード系の Web 化（API キー不要化）

前回触れなかった点ですが、Puter.js には `puter.ai.chat()` や `img2txt()` があり、AI 利用料もユーザー持ちです。今の screenshot2text や cb2ai は「自分で API キーを用意できる人」しか使えませんが、Puter 版にすれば「ページを開いて画像を貼るだけ」になり、対象がエンジニア以外にも一気に広がります。

画像を Ctrl+V → OCR → 整形して結果をコピー、という1画面ツールなら実装も軽く、coppai（AI 時代の定型文ツール）のプロンプト集を KV に保存して組み合わせれば、「自分用プロンプトで加工するクリップボード」という独自のポジションになります。障壁を下げる効果が一番大きいのはこの系統だと思います。

### 3. カウンター系の統合 Web 版

effecounter / counta / counte はいずれも Python CLI なので、スマホから記録できません。記録系ツールは「その場ですぐ押せる」ことが命なので、スマホで開けるだけで使い勝手が別物になります。

Puter の KV はこの用途と相性が非常に良く、`puter.kv.incr` でアトミックに回数を増やし、`puter.kv.add` で配列にタイムスタンプとコメントを追記できます。前回話した「複数端末の後勝ち問題」も、追記型の操作なら起きにくいです。3つに分かれている思想（ラベル＋コメント、x/y 印、ワークスペース並び替え）を1本にまとめる良い機会にもなります。

### 番外：3card / mandaland

カードセットやマンダラを保存できるようにする、`puter.ai` でカード候補を生成させる、などの拡張はできます。ただ、これらは「保存できないから使えない」という課題が今あるわけではないので、優先度は下げてよいと思います。

## Puter 化に向かないもの

AutoHotkey・バッチ・秀丸系は OS 操作が本質なので対象外です。playlist1 や dailyrss のように「定期的に外部を取得して全員に同じものを見せる」系は、ユーザーごとのストレージという Puter の設計と噛み合いにくく、やるなら Worker が必要になります。

dailyrss の README で、作りかけで「これ俺がほしいんだっけ？」と立ち止まって中断していましたね。その基準で見ると、1（自分が毎日使っていて、既存版の不満も自分で書いている）が最も筋が良いと思います。2 と 3 は「自分用は既にあって、他人に開くと障壁が消える」タイプです。
