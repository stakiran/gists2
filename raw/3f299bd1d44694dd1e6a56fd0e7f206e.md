# Graph Engineering とは何か — 原典・経緯・DAGワークフローとの違い

*最終更新: 2026-08-03*

## TL;DR

- **Graph Engineering に「原典」と呼べる論文・体系的エッセイは存在しない。** 震源は Peter Steinberger（@steipete）が 2026年7月18日 に投稿した一行のポスト「*Are we still talking loops or did we shift to graphs yet?*」である（[ポスト](https://x.com/steipete/status/2078277297791189132)）。
- 前段の **Loop Engineering** には一応の原典がある。Addy Osmani のエッセイ「Loop Engineering」（2026年6月7日, addyosmani.com）で、Anthropic の Boris Cherny（「I don't prompt Claude anymore」）や Steinberger の同日のポストのアイデアを総合したもの。
- Graph Engineering は投稿から48時間以内に複数の競合する定義が生まれ、2026年7月下旬時点で**標準的な定義・正典的リファレンスアーキテクチャ・Loop Engineering との比較ベンチマークはいずれも存在しない**。Steinberger 自身も「手法の提唱者」というより「議論の触媒」と評されている。
- 従来の DAG 型エージェントワークフローとの違いは「閉路の許容」だけではなく、**(1) 検証NG時に前のノードへ戻るエッジ（＝閉路）、(2) 実行時にトポロジーを組み替えられる動的グラフ、(3) ループを置き換えるのではなくグラフのノードとして包含する階層関係**、の3点セットで語られることが多い。

## 2. Loop Engineering のおさらい

Loop Engineering は「プロンプトを1回ずつ打つのではなく、エージェントに仕事を発見させ・実行させ・検証させ・記録させ・次を決めさせるサイクル（loop）を設計する」という考え方。エンジニアリングの階層としては次の系譜に位置づけられる：

**Prompt → Context → Harness → Loop → (Graph?)**

ループの構成要素は概ね「計画 → 行動 → 観察 → 検証 → 継続/停止判定」。停止条件（checkable statement）と検証役（verifier）の設計が肝で、「ボトルネックはモデルではなく verifier」という指摘が繰り返しなされている。

## 3. Graph Engineering の（暫定的な）定義

正典がないため、現在流通している解釈を3系統に分けて整理する。

### 3.1 実行トポロジーとしてのグラフ（最も多い解釈）

複数のエージェント・ツール・決定的関数・ルーター・人間の承認ステップを**ノード**、実行順序・条件分岐・失敗時の戻り先を**エッジ**として、システム全体を1つの有向グラフとして設計する枠組み。

- ノードが仕事をし、エッジが「次に何を実行するか」を決め、共有状態がその間を流れる
- 誰が誰を検査するか・何が並行して動くかを明示する
- TrueFoundry の作業定義：「Graph Engineering はマルチエージェントシステムのトポロジー（どのノードが存在し、どの遷移が許可され、実行時のワークグラフがどう形成・変化するか）を設計し、Loop Engineering は各エージェントノードの実行方法を設計する」

### 3.2 フィードバックループのネットワーク（ガバナンス寄りの解釈）

メトリクス・評価・監査・ポリシー・ワークフローといった複数のフィードバックループを網状に接続し、**各ループが互いを監視・制約・修正し合う**ようにする実践（Eigent など）。単一ループの自己評価が現実から乖離していく問題（テストは全部緑なのに価値を生んでいない、等）への処方箋として語られる。日次チューニング・週次運用・四半期戦略・年次監査といった**ケイデンス（周期）の階層**も設計対象に含む。

### 3.3 コンテキストグラフ（GraphRAG 系）— 混同注意

エンティティと型付きエッジで知識を構造化しエージェントに走査させる話（GraphRAG / knowledge graph）。同じ「graph」の語で語られることがあるが、**上記2つのオーケストレーションの話とは別物**。混同しないことが誤解回避の第一歩とされる。

## 4. 従来の DAG 型ワークフローとの違い

「閉路つきグラフを扱うということか？」という問いへの答えは「**一面としては正しいが、それだけではない**」。

| 観点 | 従来の DAG 型ワークフロー | Graph Engineering の議論 |
|---|---|---|
| 閉路 | なし（非巡回が前提） | 検証NG→前のノードへ戻る「戻り先」エッジを許容（LangGraph 的なステートマシン） |
| トポロジー | 実行前に固定（事前検証可能） | 実行時に経路を組み替えられる動的な型と、DAG固定で検証可能性を取る型の**両方を含む**。選択基準は「実行中に来る新しい情報でどれだけ仕事が変わるか」 |
| ノードの中身 | タスク/関数 | エージェント（＝内側でループを回す）、決定的関数、ルーター、人間の承認ステップが混在 |
| ループとの関係 | — | **置き換えではなく包含**。ループはグラフ内の1ノードとして残る。「Loop Engineering の卒業ではない」 |
| 検証 | 各タスクの成否 | 相互検証・敵対的検証（あるエージェントの出力を別のエージェントが反証しにいく）、監査ルーティング |

移行判断の目安として「専門性の分割・並列処理・監査ルーティング・成功基準の変化、の4項目のうち2つ以上が揃ったら検討」という整理も提案されている（AI総合研究所）。

## 5. 注意事項

- 命名から数週間のバズワードであり、定義は流動的。実務上は「**LangGraph 等で書く、条件分岐＋サイクルつきのステートマシン／マルチエージェントオーケストレーション**」程度に割り引いて読むのが安全。
- 流行の過程で**捏造された研究（実在しない Stanford の研究助成）が拡散した**実績があるため、二次記事の「研究によれば〜」系の記述は出典を必ず確認すること。
- 本稿の整理も2026年8月時点のスナップショットであり、今後定義が収斂・変化する可能性が高い。
