# Habitat Engineering

> AIエージェントが行動する「生息環境（habitat）」を用意し、タスクに応じて使い分ける技術

---

## 定義

**Habitat Engineering** とは、エージェントの行動が着地する実行環境を **どう用意し（provisioning）、どう割り当てるか（placement）** を設計することである。

エージェントを「どう制御するか」ではなく、「どこで動かすか」を扱う。

## 3つのエンジニアリング

| | 問い | 対象 | 例 |
|---|---|---|---|
| **Context Engineering** | 何を見せるか | モデルの入力 | CLAUDE.md / AGENTS.md、RAG、ツール定義、スキル |
| **Harness Engineering** | どう制御するか | エージェントの振る舞い | 権限判断、フック、テスト強制、フィードバックループ |
| **Habitat Engineering** | どこで動かすか | 行動が着地する世界 | サンドボックス、microVM、使い捨て環境、環境の振り分け |

この3つはレイヤーが異なる。

- Context はモデルの **頭の中** を設計する
- Harness はエージェントの **振る舞い** を設計する
- Habitat はエージェントが触る **世界そのもの** を設計する

### 境界の目安

- 「この操作をしてよいか」を判断する → **Harness**（例：Claude Code の auto mode、許可プロンプト）
- 「この操作が何に届きうるか」を決める → **Habitat**（例：ファイルシステムの範囲、ネットワーク、渡す認証情報）

auto mode は Harness、サンドボックスは Habitat。両者は補完関係にあり、どちらか一方では足りない。

## なぜ今か

1. **エージェントの自律性が上がった**。許可確認なしで長時間動かす使い方が一般的になり、「やらかしたときに何に届くか」が設計課題になった。
2. **環境が安く、使い捨てになった**。microVM やクラウドサンドボックスが秒単位で起動するようになり、環境を「1つ用意して使い続ける」ものから「タスクごとに作って捨てる」ものへ変えられるようになった。
3. **並列化が進んだ**。複数のエージェントを同時に走らせると、環境の分け方と割り当てそのものが設計対象になる。

人間向けの dev / staging / prod の環境設計と発想は同じだが、エージェントの環境は **数が多く、短命で、使い捨て** という点で設計の余地がはるかに大きい。

## 設計の軸

### 1. 種類と隔離の強さ

| 種類 | 隔離 | 特徴 |
|---|---|---|
| ホスト直接 | なし | 最速・最も便利。被害はそのままホストに及ぶ |
| OSレベルサンドボックス | 弱〜中 | Seatbelt（macOS）/ bubblewrap（Linux）など。軽く、普段使いの邪魔をしない |
| コンテナ | 中 | カーネル共有。信頼できないコードには不十分とされる |
| microVM / gVisor | 強 | Firecracker など。カーネル分離。ローカル・クラウド両方に選択肢あり |
| クラウド使い捨て環境 | 強 | ホストと物理的に別。データ転送のコストと遅延がかかる |
| 永続リモート開発環境 | 中〜強 | 状態が残る。長期作業向け |

### 2. ライフサイクル

- **Ephemeral**：タスクごとに作って捨てる
- **Persistent**：使い回し、状態を残す
- **Snapshot / Fork**：途中の状態を保存して分岐させる（例：同じ状態から3通り試し、最良のものを採用する）

### 3. 初期状態（seed）

環境に最初から何を置いておくか。

- 依存パッケージ、ビルドキャッシュ
- データ（本物か、マスク済みか、合成か）
- **認証情報：何を、どの範囲で渡すか**

Context Engineering の「何を見せるか」に対応する、Habitat 側の「何を置くか」。

### 4. 境界（boundary）

- ファイルシステム：どこまで読めて、どこまで書けるか
- ネットワーク：どのドメインに届くか
- 外部権限：渡した認証情報で何ができるか

**サンドボックスに本番の API キーを渡せば、そのサンドボックスは本番につながっている**。隔離はファイルシステムだけの話ではない。

### 5. 配置パターン

- **Agent-in-Habitat**：エージェント自体を環境の中で動かし、セッション中ずっとそこにいる（例：Docker Sandboxes）。安心感が強いが、ホスト側の設定やツールはそのまま使えない。
- **Habitat-on-Demand**：エージェントは外にいて、コマンドやコード実行のときだけ環境を使う（例：Claude Code の組み込みサンドボックス、E2B / Daytona などのクラウドサンドボックス）。軽く、柔軟。

### 6. 並列化と振り分け

複数のエージェントやタスクを、どの環境に割り当てるか。

- git worktree で分けるか、環境ごと分けるか
- どのタスクにどの隔離強度を当てるか
- 環境間でどう成果物を受け渡すか

### 7. コストと速度

起動時間、データ転送量、維持費。隔離を強くするほど安全だが重くなる。**すべてを最強の隔離で動かすのは正解ではない**。

## 使い分けの例

| タスク | 推奨 Habitat | 理由 |
|---|---|---|
| 普段の開発（自分のリポジトリ） | OSレベルサンドボックス | 軽く、作業の邪魔をしない |
| 放置で長時間回す | microVM（ローカル） | 誰も見ていないので被害範囲を絞る |
| 知らないリポジトリ・依存の検証 | 使い捨て microVM | 信頼できないコードを実行する |
| Web 調査・外部文書の処理 | ネットワーク制限付き使い捨て環境 | プロンプトインジェクションの受け皿になる |
| Docker を使う作業 | Docker を内包できる microVM | コンテナの中でコンテナを安全に動かす |
| 複数案の並列試行 | スナップショットから fork | 同じ出発点から比較する |
| 本番に近い検証 | ステージング相当の環境 | 本番の認証情報は渡さない |

**判断の基準は「実行するコードの信頼度」だけでなく「読み込む入力の信頼度」**。自分のコードでも、外部の文書や Web ページを読ませるなら、それは信頼できない入力を扱うタスクになる。

## 原則

1. **サブエージェントは Habitat ではない**。サブエージェントはコンテキストを分ける仕組みであり、親と同じ環境・同じ権限で動く。隔離は別に用意する。
2. **Harness は Habitat の代わりにならない**。権限判断がどれだけ賢くても、判断ミスの被害範囲を決めるのは環境の側。
3. **Habitat はモデルが賢くなっても不要にならない**。Context や Harness はモデルの能力が上がると簡素化される傾向がある。Habitat は「うまくいかなかったとき」のためのものなので、自律性が上がるほどむしろ重要になる。
4. **境界は認証情報で決まる**。どれだけ強い隔離でも、渡した鍵の届く範囲が実際の被害範囲になる。
5. **環境は使い捨てを基本にする**。壊れたら捨てて作り直せる状態が、エージェントに自由を与える前提になる。

## 名前について

- **habitat**：生き物ごとに適した生息環境があるように、タスクごとに適した環境を **用意して住まわせる**。「用意」と「使い分け」の両方を一語で表せる。
- **container** ではない：Docker のコンテナと同一視され、上位概念として伝わらない。
- **sandbox** ではない：隔離だけを指し、用意や振り分けを含まない。
- **runtime** ではない：「実行時の（制御）」と読まれると Harness と混同される。
- RL の訓練用「environment engineering」とも区別する。

## 未解決の問い

- 環境の **状態** はどこまでコンテキストとして扱うべきか（環境の中身をエージェントに説明する必要はあるか）
- 長期作業で、環境の引き継ぎと Context の引き継ぎをどう揃えるか
- タスクから必要な隔離強度を **自動で** 判定し、振り分けられるか
- 個人の開発で、どこまでの Habitat 設計が現実的なコストに見合うか
