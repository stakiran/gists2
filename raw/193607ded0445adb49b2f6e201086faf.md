# q: install と build は何が違うの？install = build ではないのか？
良い質問です。npmでは確かに「install = 全部やる」なので、そう感じるのは自然です。vltはその「全部」を意図的に2つに分けています。

**npm install が実際にやっていること**

npmの `install` は1つのコマンドに見えて、内部では複数の処理をまとめて実行しています。

1. 依存関係の解決(どのバージョンを入れるか決める)
2. パッケージのダウンロードと node_modules への展開
3. **各パッケージのライフサイクルスクリプト(preinstall / install / postinstall)の自動実行**
4. バイナリのリンク(`node_modules/.bin` へのシンボリックリンク作成など)

問題は3番です。これは「インストールしたパッケージが書いた任意のシェルコマンドが、あなたのマシンで自動的に実行される」ことを意味します。近年npmエコシステムで多発しているサプライチェーン攻撃(マルウェア入りパッケージ)の多くは、まさにこのpostinstallスクリプトを悪用しています。`npm install` した瞬間に、依存の依存の依存に紛れ込んだマルウェアが実行されてしまうわけです。

**vltの分離**

vltはこれを次のように分けました。

- `vlt install` → 上記の1と2だけ。ファイルをダウンロードして展開するのみで、**コードは一切実行されない**。ここまでなら悪意あるパッケージが混ざっていても被害は出ません。
- `vlt build` → 上記の3と4。ライフサイクルスクリプトの実行とバイナリリンク。しかもデフォルトで「既知のマルウェアを持つパッケージ」は除外され、DSSセレクタでどのパッケージにスクリプト実行を許可するか細かく制御できます。

つまり:

```
npm install  ≒  vlt install + vlt build
```

**なぜこれが嬉しいのか**

多くのパッケージ(純粋なJSライブラリ、lodashやreactなど)はそもそもインストールスクリプトを必要としません。`vlt install` だけで動きます。スクリプトが本当に必要なのは、ネイティブコードをコンパイルするもの(sharp、node-gyp系、esbuildなど)くらいです。

なので実務的には「基本はinstallだけ、必要なパッケージにだけbuildで実行許可を与える」という運用ができ、攻撃対象面が大幅に減ります。CIでテストだけ回すならinstallのみで済むケースも多く、その分速くて安全です。

逆に言えば、npmと同じ感覚で `vlt install` だけして「ネイティブモジュールが動かない!」となったら、`vlt build` を忘れているサインです。従来と完全に同じ挙動が欲しければ `vlt install && vlt build --allow-scripts="*"` で再現できますが、それだとvltの安全性メリットを捨てることになるので、基本はデフォルト運用がおすすめです。
