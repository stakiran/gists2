# Spark-to-Paper 読解メモ — 「エージェント基盤を作らない」論文自動生成システムの設計論

arXiv: [2608.11924](https://arxiv.org/abs/2608.11924) / GitHub: [Spark-To-Paper-Skills/spark-to-paper-skills](https://github.com/Spark-To-Paper-Skills/spark-to-paper-skills)（Vast Intelligence Lab / UTS、2026-08-12公開）

研究アイデア1行から、文献調査・実験実行・図表生成・原稿執筆までを一気通貫で行う論文自動生成システム。ただし本当の読みどころは論文生成そのものではなく、**長時間エージェントワークフローの信頼性設計パターン集**になっている点。agentic engineering の観点で整理する。

## 1. 何が新しいか（ひとことで）

**独立したエージェント基盤・オーケストレーションサービスを一切持たず、既存のコーディングアシスタント（実装は Claude Code）内の「13個の組み合わせ可能なスキル」だけで実装した**こと。AI Scientist 系の先行研究は専用のオーケストレーションサーバやグラフDB、クラスタスケジューラを持つスタンドアロンアプリだったのに対し、Spark-to-Paper はアシスタントが元々持つファイル操作・コード実行・検索・ツール呼び出し能力を再利用する。

スキル間の通信は**共有プロジェクトディレクトリ内のファイル**が担う。エージェント間メッセージング基盤の代わりに「ファイルシステムが契約」という設計。

| 主要な永続アーティファクト | 生成ステージ | 役割 |
|---|---|---|
| `blueprint.json` | Planning | 論文構造・主張・記法・実験設計 |
| `template.json` | Planning | 投稿先仕様と実行モード |
| `refs.bib` | Citation | 検証済み書誌 |
| `claims_map.json` | Citation | 主張と引用の対応 |
| `sections/*.tex` | Writing | セクション単位の原稿ソース |
| `results.facts.json` | Data | 実測に基づく定量的エビデンス |
| `logs/*.io.md` | 全ステージ | ステージ単位の入出力記録 |

`results.facts.json` を原稿本文と分離しているのがポイントで、下流の整合性チェックが「観測されたエビデンス」と「生成されたテキスト」を機械的に区別できる。

## 2. 13スキルの内訳

注意: 論文本文は13スキルを番号付きで列挙しておらず、「スキル数はパイプラインのステージ数と1対1対応しない」と明記している。以下は本文の記述（§3.1、Fig.2、Appendix D）からの再構成。

**オーケストレーション + ルーティング（2）**

1. **ts-paper（オーケストレーター）** — タスクの高レベルな順序だけを規定。「次に何をやるか」はパイプラインが決め、「どうやるか」は各スキル＋アシスタントの判断に委ねる
2. **入力ルーティング（Stage 0）** — 入力を検査して開始位置を決定。実測データの有無で **Proposal Mode**（結果未取得。数値は空欄のまま）か **Data-Aware Mode**（定量的記述は実データの裏付け必須）を選択し、全下流ステージに伝播

**コア7ステージ（7）**

3. **Planning** — 入力を構造化ブループリントに変換。研究課題・貢献・セクション構造・記法・実験設計を特定し、投稿先仕様も読み込む
4. **Citation** — 文献検索と DOI / arXiv ID 等による書誌検証。モデルの記憶から参照を生成せず、検証済み参照のみを BibTeX に保存
5. **Writing** — ブループリント＋検証済み書誌から LaTeX 原稿を生成。全セクションを同一プロジェクト文脈に対して書き、用語・記法・主張の一貫性を保つ
6. **Refinement** — セクション単位でなく原稿全体を修正（重複除去、用語統一、長さ調整）。修正後に決定的チェックを再実行
7. **Review** — 複数の独立レビューパスが技術的健全性・実験設計・エビデンスの強さを検査。指摘は原稿の特定箇所への紐付けが必須で、検証を通過したものだけが Refinement に差し戻される
8. **Figure Generation** — 実測結果のプロットはデータからプログラム的に生成、説明図は画像生成モデル経由（後述の変換スキルとセット）
9. **Assembly** — 全成果物をテンプレートと結合して LaTeX プロジェクトを組み立て、コンパイルと決定的検証

**実験 + サポートスキル（4）**

10. **Experiment Execution（Stage 8）** — 初稿完成後、計画済み実験の実行可能性を確認し、実行して測定結果を記録、原稿を更新
11. **アイデア展開** — 短い1行アイデアを構造化された研究提案に拡張
12. **測定結果処理** — 実験出力から定量的ファクトを抽出して `results.facts.json` に分離保存
13. **図の編集可能化** — 画像生成モデルのラスター出力を「視覚的ターゲット」として扱い、HTML で再構築 → レンダリングして元画像と比較 → 反復調整 → 編集可能なベクター PDF に変換

## 3. 設計原則その1: 判断と実行の分離

各スキル内部で、**モデルの判断**と**決定的（deterministic）な操作**を分離する。

- モデルが担当: 議論の構成、文献の関連性判断、エビデンスが主張を支持するかの評価、結果の提示方法
- 決定的スクリプトが担当: 原稿構造チェック、引用検証、LaTeX コンパイル、実測データのプロット、生成ファイルの検査

決定的ゲートは fatal（実行停止）と warning（記録のみ）を区別し、Template / Blueprint / Citation / Manuscript / Figure / Compilation の6種のゲートが各ステージの通過条件になる。ゲートは「貢献が重要か」「議論が説得的か」といった意味的判断には踏み込まず、**直接検証可能な要件だけを non-negotiable にする**、と役割を明確に限定している。

## 4. 設計原則その2: 計画と報告の分離（エージェント版・事前登録）

論文自身が「パイプライン内の軽量な事前登録（preregistration）」と呼ぶ、本システムの核。

### 防ぎたい問題

結果を見てから評価方法を選べるエージェントは、何でも「成功」にできてしまう。都合の良い指標だけ選ぶ、弱いベースラインと比べる、最悪の場合は数値を生成（捏造）する。人間の研究における HARKing / p-hacking と同型の問題が LLM エージェントにも起きる。

### 仕組み: 合格条件を先に固定し、答案は後から埋める

1. **計画時にエビデンスの「型」を確定** — 実行前に、主張の評価に必要なデータセット・ベースライン・指標・アブレーション・結果テーブルを Planning が指定する。**テーブル構造は事前に固定され、数値セルは実験完了まで空欄のまま**。答案用紙と採点基準を先に印刷するイメージ
2. **空欄を勝手に埋めることを機械的に禁止** — Proposal Mode では未観測の結果を生成値で埋めることを Manuscript Gate が検出して止める。モデルへの「お願い」ではなくゲートによる強制
3. **実験ステージは委託された設計を実行するだけ** — 主張→必要エビデンスのマッピングから欠落実験を特定し、ギャップを埋める最小セットのみ実行。ガイダンスが推奨はできてもコミット済み設計を上書きすることはできない。さらに「指定された評価をより簡単な代替・異なるデータ構築・合成観測値に置き換えること」を明示的に禁止し、リソースが無い場合は欠損を記録して結果を未指定のまま残す（ダミーデータで数字を出す挙動を塞ぐ）
4. **数値の入場には出所の連鎖が必要** — データセット・モデル設定・シード・指標・出力ソースまで遡れる数値だけが原稿に入れる。集計値は元の実行から再計算可能であること

### 結果が出た後: 評価方法ではなく主張の方を直す

各主張は5ラベルに分類され、ラベルごとに許される行動が決まっている。

| ラベル | 行動 |
|---|---|
| supported | エビデンスに合った表現で維持 |
| partially-supported | 主張を狭めるか追加エビデンスを要求 |
| unsupported | 実行可能な欠落実験を実行、弱める、または削除 |
| contradicted | 削除するか limitations として報告 |
| needs-confirmation | 未解決のまま著者確認に差し戻し |

ネガティブ・ヌル・不確定な結果は省略せず保持。修正は abstract / introduction / results / conclusion の全出現箇所に伝播され、abstract は最後に修正される。

### 検証: ユーザーの誤った期待に迎合しないか

ケーススタディで、提案書に誤った期待を意図的に注入している。臨床スクリーニング例では「Accuracy を主要指標に」という（不均衡データでは不適切な）指定に対し、システムは複数指標でクロス検証して Accuracy と F1 が誤解を招くと結論。PM2.5 予測例では「因果モデルは同等性能のはず」というユーザーの事前期待に対し、実験結果が矛盾することをそのまま報告した。**事前にコミットした評価枠組みが、ユーザープロンプトへの迎合より優先される**ことの実証。

## 5. 設計原則その3: Self-Refutation Loop の有界化

長時間実行で観測された失敗モードに命名し、対策した点も特徴的。

**Self-Refutation Loop（自己反駁ループ）**: 実験→「エビデンス不十分」と判定→手法や実験設計を修正→再実験→また不十分→… と、**「このアイデアはそもそもダメかもしれない」を受け入れずに同じ研究方向を修正し続ける**ループ。生産的な反復（具体的な弱点を解消して結論に近づく）とは異なり、収束しない。

対策はシンプルで、**実験–批評–修正サイクルを7回で打ち切る**。上限に達したら、元のアイデア・試した手法と実験・観測結果・不十分と判断した理由を**失敗レポート**として記録し、見かけ上成功した論文に書き直すのではなく「不成功だった研究方向の成果物」として保存。その後、別のアイデアから新しいトラジェクトリを開始する。

「全ての研究アイデアを成功させることを強制しない」設計。エージェントに無限リトライさせると成功を捏造する方向に圧力がかかる、という洞察の裏返し。

## 6. レビュー機構: 指摘にも検証を課す

Adversarial Review では、複数の独立レビューパスが原稿を攻撃するが、**指摘の側にも通過条件がある**。

- 全ての指摘は、挑戦対象の特定パッセージを引用しなければならない
- 各指摘は3方向から検証される: (1) 問題は実際に存在するか、(2) 原稿の他所で既に対処済みでないか、(3) 研究のスコープ外でないか
- 反駁できた指摘は破棄、生き残った指摘だけが修正に回る
- 新しい生存指摘が出なくなるまでレビューを継続

レビュアーエージェントの「難癖」を無検証で受け入れると修正ループが暴走するため、指摘自体を検証可能な形式に縛る。レビュー精度74%（提起された指摘のうち独立に検証可能な問題だった割合）はこの機構の効果測定。

## 7. 数字で見る効果

8つの統制された研究トピックでの評価（トピック・モデル設定・評価基準は生成前に外部タイムスタンプ付きで固定）。

**品質スタックのアブレーション（捏造検出率）** — 36個の捏造主張を注入した統制実験:

| 構成 | 捏造検出率 |
|---|---|
| 単一パスのドラフト（ゲートなし） | 14% |
| + 決定的ゲート | 69% |
| + Self-Review | 81% |
| + Adversarial Review（フルスタック） | **92%** |

ゲート追加が最大の改善（14%→69%）と最大のコスト増をもたらし、レビュー層は小さな追加コストでさらに積み増す。

**主要結果**: 引用の有効性 99.5%（人間のプレプリント標本は97.8%、単一パスLLMは81%）、図の編集可能性 96.4%。コストは1本あたり平均 11.9M トークン / $8.1 / 3.2時間。単一パス（$0.66 / 16分）との差が、検証スタックの価格ということになる。

## 8. agentic engineering への持ち帰り

1. **フレームワークより先にスキル＋ファイル契約を検討する** — マルチエージェント基盤を建てる前に、既存アシスタントのスキル機構＋共有ディレクトリのアーティファクトで足りないかを問う。オーケストレーターは「順序」だけを持ち、「やり方」はスキルとモデルに委ねる粒度が再利用性を生む
2. **LLM には判断だけをさせ、検証可能な処理はコードに落とす** — そして検証はゲートとして各ステージの通過条件にする。ゲートの守備範囲を「機械的に検証可能なことだけ」に限定するのも重要（意味的判断まで自動化しようとしない）
3. **検証と実行を時間的に分離し、基準の変更権限を実行フェーズから剥奪する** — コーディングエージェントなら「テストを先に書いてコミットし、実装フェーズではテスト改変を禁止（TDD の強制）」、データ分析エージェントなら「分析計画と成功指標を先に JSON で固定し、レポートはその枠しか埋められない」に相当。LLM は結果を見た後だとゴールポストを流暢に動かすので、動かせないタイミングで杭を打つ
4. **リトライには上限を設け、失敗を成果物として保存する** — 無限リトライは成功の捏造への圧力になる。失敗レポートという「正規の出力形式」を用意することで、エージェントが失敗を認められるようにする
5. **批評エージェントの指摘にも検証を課す** — 「特定箇所の引用必須＋3方向の反駁チェック」のように、指摘側にも構造的な通過条件を設けないと修正ループが暴走する
