# オントロジー駆動開発（Ontology-Driven Development）という予感

> テスト駆動開発（TDD）がテストコードを第一級の資産として維持し続けるように、
> 「オントロジーを維持し続ける開発スタイル」が今後整備されていくのではないか。
> ——という仮説を、なぜそう思うか・何が生き残り何が腐るかまで含めて整理したメモ。

---

## 0. 前提：オントロジーとは「意味をリンクの型に載せた網」

オントロジーは、ざっくり言えば「概念（モノ）と、その関係を、機械が解釈できる形で定義した網（グラフ）」。

ここで大事なのは、ただのネットワーク構造（例：Cosense/Scrapbox のページリンク）との違い。リンクでモノをつなぐだけなら自由なメモツールでもできるが、そこでは **意味は「ページ名という文字列」に載っていて、読むのは人間**。オントロジーは **意味を「リンク（関係）の型そのもの」に載せて、読むのは機械**。

| | 自由な網（メモ的） | オントロジー |
|---|---|---|
| リンクの型 | 1種類（「参照している」だけ） | 関係ごとに型がある（`calls` / `is-a` / `owns` …） |
| 一貫性 | 揺れる（`契約中`と`契約している`が別物） | 縛って揺れをなくす（正規化） |
| 推論・検証 | できない | 推移律や制約で機械が推論・検証できる |

**自由さ＝人間向けの強み、そのまま機械向けの弱み。** 同じ性質の裏表であり、機械に「厳密一意（同じ意味は必ず同じ形）」を求めた瞬間、自由さは「揺れ・あいまいさ」に化ける。

---

## 1. オントロジーは2つある：ドメイン と コード

開発の文脈でオントロジーを考えるとき、性質の異なる2つを分けて捉えると見通しが良い。

### ドメインオントロジー（業務・製品の意味）
- **正（source of truth）**：業務・プロダクトの側
- **中身**：注文・顧客・解約・請求といった概念と、その定義やルール（例：「解約 ＝ 90日ログインなし かつ 課金停止」）
- **変わる理由**：ビジネスの意思決定
- **持ち主**：プロダクト／ドメインの専門家
- **答える問い**：「そもそも“解約”とは何を意味するのか」

### コードオントロジー（アプリケーションオントロジー）
- **正**：コードそのもの
- **中身**：関数・クラス・モジュール・型・テーブル・エンドポイントと、`calls` / `imports` / `inherits` / `reads-writes` などの関係
- **変わる理由**：コミット
- **持ち主**：実質コードベース
- **答える問い**：「何が何を呼んでいるか／どこを触ると壊れるか」

> コードは最初から形式言語（厳密で一意）なので、オントロジー化に一番向いた題材。
> AST・型情報から **決定的に自動抽出**でき、grep より正確に「呼び出し元を全部」「影響範囲」に答えられる。
> 既存の実装例：Google Kythe、Meta Glean、Sourcegraph SCIP/LSIF、CodeQL のデータベース——いずれも実質「コード知識グラフ＝コードオントロジー」。

## 2. 本当の価値は「橋（マッピング）」にある

2つのオントロジーを別々に持っているだけでは足りない。効くのは **両者の対応づけ（bridge）** を張ったとき。

```
ドメイン: 「解約」  ＝  90日ログインなし かつ 課金停止
                │  （bridge）
コード:  ChurnService.evaluate()  →  reads subscriptions.status
                                  →  reads User.lastLogin
```

この橋があると、「解約の定義を変えたい」という **ドメインの言葉から、直接“触るべきコード”へ飛べる**。`grep "churn"` で全域を彷徨って当たりをつける工程が要らなくなる。「作っておいた構造を読んで把握してから修正する」という狙いが本当に効くのは、この橋がかかっているとき。

### ただし橋は最も壊れやすい
コードオントロジーは勝手に更新できる。ドメインオントロジーも独立に更新される。しかし **両者を結ぶ線は、どちらかが変わるたびに人（かLLM）が張り直さないとズレていく。** 2つが別々のライフサイクルで動く以上、接合部が一番ドリフトする、という構造的宿命がある。

---

## 3. なぜ「TDDの再来」だと思うのか

TDDでテストが腐らなかった本当の理由は「テストを大事にしようと決めたから」ではない。テストが **実行可能で、CI というフィードバックループの中に置かれた** から。

- ドキュメントが腐る＝**嘘をついても何も起きない**
- テストが腐りにくい＝**嘘をついた瞬間にビルドが赤くなる**

したがって **オントロジー駆動開発（ODD）が成立するかどうかは、オントロジーを実行可能・検証可能にして、ドリフトを“静かな陳腐化”ではなく“うるさい失敗”に変えるループに載せられるか** の一点にかかる。

### この観点で2つを見ると
- **コードオントロジー**：そもそも「導出（derive）」されるもので、維持する対象ですらない。再生成すれば常に真。テストよりコンパイラ出力／インデックスに近い。→ ほぼ自動でループに載る。
- **ドメインオントロジー＋橋**：ここを「実行可能な形」にできるかが勝負。

### 萌芽はすでに別名で存在している
「オントロジーの主張を機械が検証する」仕組みは、実はもう無意識に使っている。

- **スキーマ／型／契約**：OpenAPI・protobuf・GraphQL SDL、DBスキーマとマイグレーション、型システム。コードとズレたらビルドが落ちる＝局所的なODD。
- **アーキテクチャ・フィットネス関数**：「ドメインXのモジュールはインフラYを import してはいけない」を実行可能なテストとして書く（ArchUnit 系）。まさに「オントロジー的制約をCIで守る」＝ODDの赤信号。

→ ODDはゼロから生まれるというより、**バラバラに存在する部品（スキーマ・型・契約・フィットネス関数・トレーサビリティ）が「オントロジーを中心資産として維持する」という旗の下に統合されていく** 形で立ち上がると見る。

## 4. 正直な留保：TDDの魔法がそのまま効かない部分

- テストは「具体例」で真偽が自己完結する（入力→期待出力）から安く書けて検証も容易。
- オントロジーの主張は、**コードから導出できるもの（＝わざわざ人が主張する価値がない）** か、**純粋な人間の判断＝“なぜ”（＝機械的に検証できない）** に割れがち。
- つまり「**独立に主張する価値があって、かつ機械で検証もできる**」という美味しい帯が、テストより狭い。

ここを見誤って「全部にオントロジーを書け」とやると、TDD原理主義と同じで重い儀式になり、「厳密すぎて維持できない」に逆戻りする。

**勝ち筋は、手で並行モデルを保守する重い形ではなく、導出＋制約チェック＋（ズレたらLLMが張り直しを提案し人が承認）という軽い形。**

---

## 5. なぜ「今」なのか：経済性が変わった

リッチなオントロジー／知識グラフの維持は、歴史的には高すぎた（Cyc、セマンティックWebの苦戦）。ところが今、2つが同時に揃った：

1. **作るコストが落ちた**：LLMが抽出も橋の修復も安くやれる。
2. **読む動機が生まれた**：それを読んで得をする貪欲な消費者＝**コーディングエージェント**が現れた。

作るコストが落ち、読む消費者が現れたのは初めて。だから「方法論の流行」ではなく **必要に迫られて** ODDが立ち上がる、という筋書きにリアリティがある。

---

## 6. ODDが根づいた現場の具体像（予想）

- オントロジーは **コミットごとにビルド成果物として再生成**される（手で育てるドキュメントにしない）。
- その上の制約は **フィットネス関数としてCIで守られ**、違反はビルドを赤にする（ODDの赤信号）。
- ドメイン↔コードの **橋はドリフト時にLLMが再リンクを提案し、人が承認**する（半自動）。
- **コーディングエージェントはまずオントロジーを一次コンテキストとして読み**、編集の直前だけ生コードで答え合わせをする（地図で当たりをつけ、現地で確認）。

> 地図を常に最新に保つ仕組みごと開発フローに組み込む——という意味で、
> これは「TDDがテストにやったことを、オントロジーにやる」試みだと言える。

---

## まとめ（TL;DR）

- オントロジーは **ドメイン**（業務の意味）と **コード**（実装の構造）の2つがある。
- 本当の価値は両者を結ぶ **橋** にあり、そこが最も壊れやすい。
- TDDが効いたのは「実行可能＋フィードバックループ」だったから。ODDも **オントロジーを検証可能にしてドリフトをうるさい失敗にできるか** が成否を分ける。
- 検証可能な部品（スキーマ・型・契約・フィットネス関数）は既に存在し、統合されていく。純粋な“なぜ”は機械検証できないので軽く扱う。
- LLM（作るコスト↓）× コーディングエージェント（読む動機↑）が揃った今、ODDは必要に迫られて立ち上がりうる。
