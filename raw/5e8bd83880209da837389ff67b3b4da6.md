# Claude生成コンテンツの不可視透かし：整理ノート

*2026年8月時点の情報。Anthropicの公式サポート記事および関連報道をもとに整理。*

## 1. 何が起きたか

Anthropicは、EU AI Act Article 50(2) の「AI生成コンテンツの透明性に関する実施コード」に署名し、Claudeの生成コンテンツへ機械可読なマークを組み込む方針を発表した。

- **対象モデル**: 2026年8月2日以降にEUで提供開始する新モデルは、リリース時点からマーキングに対応。それ以前の既存モデルは移行期間中で、導入時期は未定
- **適用範囲**: EU限定ではなく**全世界共通**。Claude Platform (API)、Claude、Claude Code、Claude Cowork、Claude Tag のすべてに適用。AWS / Google Cloud / Microsoft Foundry 経由でもテキスト透かしは付く
- **検出手段**: ユーザーや第三者向けの検出機構を提供予定だが、方式・時期は今後の技術文書待ち

## 2. 「プレーンテキストに透かし」は可能なのか

直感に反するが可能。ポイントは、**文字の中に何かを隠すのではなく、単語の選び方そのものに統計的な偏りを仕込む**こと。

### 隠し文字方式との違い

よくある誤解はゼロ幅スペース等の不可視Unicode文字を混ぜる方式。これは正規化やプレーンテキスト貼り付けで簡単に消える。モデルレベルの透かし（Google DeepMind の SynthID-Text が先例）は根本的に異なる。

### 仕組み（SynthID-Text系の場合）

1. LLMは次のトークンを確率分布から選んでいる
2. 直前の文脈から擬似乱数的に決まる「グリーンリスト」のトークンを、ほんの少しだけ選ばれやすくする
3. 1単語単位では気づかない偏りだが、数百トークンを統計検定すると「偶然では説明できない頻度」として検出できる

> 表が51%出るコインは10回投げても見抜けないが、1万回投げれば分かる、というのと同じ理屈。

### この方式の帰結

- **コピペしても消えない**: 透かしは文字コードではなく単語選択パターン自体だから
- **短文では検出不能**: 統計検定に十分なサンプルが必要。EUコードが200トークン未満を例外扱いするのはこの技術的限界の裏返し
- **言い換え・翻訳・大幅編集で信号が弱まる**: SynthID-Text の論文自体が認めている

なおAnthropicが採用する具体方式は未公表。SynthID-Text と同系統かは不明だが、原理的な制約は共通する。

## 3. コンテンツ種別ごとのマーキング方式

公式記事が明示するのは大きく2区分のみ。

| 区分 | 方式 | 強み | 弱み |
|---|---|---|---|
| テキスト（自由文） | 統計的な埋め込み透かし | メタデータを持てない裸の文字列でも機能。コピペ耐性あり | 統計的なので短文・大幅編集に弱い |
| ファイル（.svg / .png / .jpg など） | C2PA標準の署名付き来歴メタデータ | 暗号学的に改ざん検証が可能 | 形式変換・再保存・スクリーンショットで剥がれる |

### 個別形式の補足

- **PNG / JPG**: C2PAが最も成熟。マニフェスト（署名データ）をメタデータ領域に埋め込む標準手法が確立
- **SVG**: 実体はXMLだがC2PA仕様が埋め込みを定義。テキストエディタで該当要素を削除すれば消える程度の耐性
- **PDF / DOCX 等**: 公式には個別言及なし。C2PA仕様自体はPDF対応だが、Anthropicの適用範囲は「ファイル処理をサポートする範囲」という表現に留まる
- **コード（.py / .js 等）**: 明記なし。テキストなので理屈上は透かし対象だが、コードは語彙選択の自由度が散文より低く、統計的透かしの信頼性が下がりやすい領域
- **クラウド経由の差**: AWS / Google Cloud / Microsoft Foundry ではテキスト透かしは適用されるが、C2PAメタデータは各プラットフォームの機能次第

**現時点の正確な答え**: テキスト＝統計的透かし、画像系＝C2PA署名、それ以外は未公表（技術文書待ち）。

## 4. 透かしは除去できるのか

できる。ただしEXIF除去とのアナロジーは半分だけ正しい。

### C2PA側：EXIFと同程度に簡単

メタデータはコンテンツと分離した付加情報なので、再保存・変換・スクショで無劣化除去できる。ただしC2PAの設計思想はそもそも「除去不能」ではなく「存在する場合に改ざんされていないことを証明できる」こと。ネガティブ証明（マークがない＝AI製でない）には最初から使えない。

### テキスト透かし側：可能だが無料ではない

信号がコンテンツ（単語選択パターン）そのものに入っているため、除去には文章自体の変換が必要。

- 別のLLMでの言い換え（パラフレーズ攻撃）
- 翻訳して戻す
- 人手での大幅な書き換え

EXIF除去のような「ワンクリック無劣化」ではなく、毎回コンテンツ変換のコスト（LLM実行、品質変動リスク）を払う。皮肉なことに、言い換えに使ったLLMが別の透かし入りモデルなら今度はそちらの透かしが入り得る。

### 設計目標は「除去不可能」ではない

現実的な狙いは：

1. 大量・自動・無編集のコピペ（スパム、コンテンツファーム等）を検出可能にする
2. 除去に一手間かけさせ、カジュアルな偽装のコストを上げる
3. 除去行為自体が「意図的に痕跡を消した」証拠として意味を持つ（南京錠がピッキング可能でも無意味にならないのと同じ）

EUコード自体が意図的攻撃（除去・コピー・再生成）への堅牢性評価を要求しており、規制側もいたちごっこを織り込み済み。

## 5. 重要な留保

- **マークはClaudeが原著者である証明にならない**: 人が書いた文章の校正・翻訳・要約でも信号は残り得る
- **マークがなくてもAI製でない証明にならない**: 旧モデル、短文、大幅編集、メタデータ剥離などで検出できないケースは多い
- **検出アクセスは当面制限され得る**: 誤解を招く低信頼の間は、規制当局・報道機関・研究者等の確認済み専門家に限定できるとEUコードは定める
- **API利用の開発者は自前の義務評価が必要**: 透かしが入っても、利用側のArticle 50上の表示・記録義務が自動で済むわけではない
