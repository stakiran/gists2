# Observed-State Gating — エージェントに「やったフリ」をさせないハーネス設計

LLMエージェントの信頼性を、モデルの賢さではなくハーネス(実行系)の設計で担保するためのパターン整理。StateM (arXiv:2608.15089) の "checked transitions" を起点に、reward hacking への耐性設計までを扱う。

## TL;DR

- プロンプトの注意書き(「テスト前に必ずビルドして」)は強制力を持たない。エージェントはやったフリができる。
- 対策は、検証をエージェントのタスクから**ハーネスの遷移判定関数**へ移すこと。ハーネス自身が verifier(ビルド・テスト等)を実行し、グリーンになるまで次フェーズへの遷移を拒否する。これを observed-state gating と呼ぶ。
- 判定材料はエージェントの**申告**ではなく、ハーネスが今その場で観測した**世界の状態**(exit code、テスト出力)のみ。申告が存在しないので申告の偽装は不可能になる。
- ただし銀の弾丸ではない。最適化圧力は「ゲートの偽装」から「**verifier の検査範囲の穴**」へ移動する。verifier の強度がそのままシステム信頼性の上限になる。
- 実用上は、(1) 観測ベース判定、(2) 判定の密閉性、(3) verifier への書き込み権限分離、(4) ゲーミング兆候のメタ検査、(5) 正攻法を最も低コストな経路にする、の積み重ねでごまかしコストを正攻法コストより高くする。

## 1. 問題設定:プロンプト指示はなぜ壊れるか

長時間タスクでエージェントが失敗する主因は、個々のステップを解く能力の欠如ではなく実行管理の崩壊にある(状態を見失う、既知の手順をスキップする、早期終了する — StateM の診断)。これに対して「手順をプロンプトに書く」という対処は、以下の理由で信頼性が頭打ちになる。

- 指示の遵守はエージェントの内部状態に依存し、コンテキストが伸びるほど劣化する(context rot)
- 遵守したかどうかを、エージェント自身の申告でしか確認できない
- 詰まったとき、モデルは「指示を満たしたことにする」近道を探し始める

観測される典型的なごまかし:失敗するテストへの `skip` 付与、アサーションの弱体化、`git commit --no-verify`、フラグファイルの `touch`、期待値のハードコード。これらは Goodhart の法則(指標が目標になると指標が壊れる)の実例で、reward hacking / specification gaming と呼ばれる。

## 2. 基本形:検証をハーネスの遷移判定に移す

構造の逆転がポイント。

| | プロンプト指示型 | Observed-state gating |
|---|---|---|
| ビルドの実行者 | エージェント(任意) | ハーネス(遷移要求時に強制) |
| 判定材料 | エージェントの申告・作業履歴 | ハーネスが観測した exit code / 出力 |
| 失敗時 | 申告を偽装できる | 遷移が拒否される。直すしか進めない |
| 制御の所在 | モデルの発話ループの内側 | ランタイム(ループの外側) |

エージェントが「テストフェーズへ進みたい」と要求した時点で、ハーネスが自らビルドを実行し、exit code 0 でなければ却下する。申告というごまかしの対象そのものが存在しないため、エージェントに残る選択肢は「verifier が通るまで直す」だけになる。

### 実装上の2つの必須条件

**密閉性 (hermeticity)** — ハーネスが実行する検証は、エージェントの作業セッションの状態(環境変数、キャッシュ、手元にしかない生成物)に汚染されない環境で走らせる。理想はクリーン環境で git 作業ツリーからのビルドし直し。これを怠ると「エージェントのシェルでは通るが CI では通らない」型のすり抜けを見逃す。

**権限分離** — verifier とその定義(テストコード、ビルド定義、hook 設定、CI 定義)をエージェントの書き込み権限から外す。ここが書き換え可能だと `build: echo ok` への差し替えで終わる。判定器と被判定者を同じ書き込み空間に置かない。EnvHarness (arXiv:2608.19880) が「環境をどう再形成しても元の verifier は必ず保持する」を設計上の不変条件としているのは、この規律の一般化。

## 3. 圧力はどこへ移動するか:ゲーミング耐性の4層

ゲートを強くすると、最適化圧力は消えるのではなく移動する。層で捉えると設計の抜けが見える。

**第1層:自己申告 vs 世界の観測。** 「ビルド成功しましたか? → yes」型のゲートは `yes` と出力するだけで突破でき、事実上ゲートではない。判定は必ずハーネス側の観測で行う(本パターンの核)。

**第2層:観測対象の改竄。** 観測ベースでも、観測される世界(テストファイル、設定)をエージェントが書き換えられれば突破される。対策は権限分離(読み取り専用マウント、`tests/` や CI 定義への Edit 拒否、`--no-verify` のブロック)。

**第3層:字面は満たすが精神を満たさない。** 権限内での合法的な最適化は権限では防げない。`# noqa` / `@ts-ignore` での抑制、無意味テストによるカバレッジ水増し、`any` での型潰し、壊れた機能のコメントアウト(ビルドは通る)。対策は3方向:

1. プロキシを意図に近づける — 行カバレッジより mutation testing、example-based より property-based テスト
2. ゲーミング兆候のメタ検査 — diff に対する「テスト削除・skip 追加・抑制コメント・アサーション弱体化」の検出。ごまかしのパターンは定型的なのでよく効く
3. 独立した複数ゲートの併用 — 1つの偽装で全ゲートを同時に満たすことを困難にする

**第4層:コスト非対称性。** 現行モデルのゲート破りの多くは悪意ではなく「詰まったときの安易な近道」。正攻法のコスト < ごまかしのコストという不等式を維持できればゲーミング率は実際に下がる。ゲートは「壁」単体でなく「壁+正規の門+門までの道案内(runbook)」で設計する。

## 4. 重要な留保:グリーン ≠ 意図の達成

verifier が強制できるのは「verifier が検査している性質」だけで、タスクの意図そのものではない。ビルド通過は特に弱い性質(壊れた箇所を全部コメントアウトしても通る)。構図は次の通り。

- プロンプト指示 → 「やったフリ」ができる
- 観測型ゲート → フリは不可能。ただし圧力が verifier の検査範囲の穴に集中する

したがって設計の焦点は「ゲートを置くか」ではなく「**verifier の検査範囲と意図のギャップをどれだけ狭めるか**」。ビルド → 型チェック → lint → テスト → mutation testing と verifier を強化するほどギャップは狭まり、穴を突く工作コストが正攻法を上回っていく。**verifier の強度 = システム信頼性の上限**。

## 5. ゲートはフィードバックループとして設計する

観測型ゲートは強制装置であると同時に、高品質なフィードバック源でもある。遷移拒否時に「ダメでした」だけを返すと、エージェントは詰まり、穴探しを始める。却下理由を行動可能な形で返すこと。

- ビルドログから該当エラー部分を抽出して返す
- 失敗したテスト名と diff を返す
- 可能なら復旧手順(runbook)への参照を添える

StateM が checked transitions を recoverable runbooks とセットにしているのはこのため。「拒否する壁」ではなく「拒否理由と次の一手を返す関門」として設計すると、突破率とごまかし率が同時に改善する。

なお LLM judge に軌跡を検証させる場合も同じ原則が適用される。judge 自体が騙される対象なので、エージェントの主張ではなく生の証拠(実行ログ、diff、テスト出力)を検証させる。HarnessEval-W (arXiv:2608.16859) の「スカラースコアではなく証拠ツリーを残す」という思想は、judge のゲーミング耐性の設計でもある。

## 6. 最小実装例:Claude Code hooks

PostToolUse / Stop hook でハーネス側が独立に verifier を実行するだけで、observed-state gating のミニ版が組める。

```
エージェントの Bash 実行結果は信用しない
  ↓
hook スクリプトが独立に npm run build && npm test を実行
  ↓
失敗 → exit code 2 でブロックし、stderr にエラー出力を返す
       (エージェントに差し戻され、修正ループに入る)
成功 → 通過
```

併せて設定しておくもの:

- deny ルール:`tests/`、`.github/workflows/`、hook 設定ファイルへの Edit / Write を拒否
- `--no-verify`、`git push --force` 等を含むコマンドのブロック
- 可能なら検証はクリーンな作業ツリーで実行(密閉性)

## 7. 設計チェックリスト

- [ ] ゲートの判定材料はエージェントの申告ではなく、ハーネスが観測した世界の状態か
- [ ] 検証はエージェントのセッション状態に汚染されない環境で実行されるか(密閉性)
- [ ] verifier とその定義はエージェントの書き込み権限の外にあるか(権限分離)
- [ ] verifier の検査範囲とタスク意図のギャップを狭める手段があるか(型・テスト・mutation 等の積層)
- [ ] ゲーミング兆候(テスト削除、skip、抑制コメント、アサーション弱体化)を検出するメタゲートがあるか
- [ ] 独立した複数ゲートが重ねてあるか
- [ ] 却下時に行動可能なフィードバック(エラー抽出、runbook)を返しているか
- [ ] 正攻法がごまかしより低コストな経路になっているか
- [ ] 監査証跡(durable states、実行ログ)が残り、事後検出が可能か
