# Bun の Rust 書き換えから学ぶ Agentic Engineering — Q&A 記録

参照記事: [Rewriting Bun in Rust](https://bun.com/blog/bun-in-rust)(Jarred Sumner, 2026-07-08)

---

## Q1

> https://bun.com/blog/bun-in-rust を読んで、agentic engineering として参考にできる戦略を教えて

### A1

読みました。Bun を Zig から Rust へ 11 日で書き換えた記事ですが、agentic engineering の実践知として参考になる戦略がかなり凝縮されています。重要なものを整理します。

#### 1. コードを書く前の「地図作り」に投資する

コードを書く前に、Zig のパターンを Rust にどうマップするかを約 3 時間 Claude と議論し、その内容を PORTING.md に serialize した。さらに全ファイルの struct フィールドのライフタイムを解析し、2 つの adversarial review エージェントでレビューした上で LIFETIMES.tsv に書き出すワークフローを実行した。ポイントは、判断基準を「他の Claude が参照できる成果物」として先に固定化すること。エージェントが数十並列で動くとき、共有される規範ドキュメントが一貫性の要になる。

#### 2. 小さなトライアルで de-risk してからスケール

1,448 ファイルの翻訳を始める前に、まず 3 ファイルだけで「実装者 1・adversarial reviewer 2・fixer 1」の流れを試した。高コストな一括処理の前に、パイプライン自体の欠陥を小さく検証する。これは人間のエンジニアリングと同じだが、エージェントでは「プロンプト設計の欠陥」が乗数的に増幅されるため、より重要。

#### 3. 実装者とレビュアーのコンテキストを分離する(adversarial review)

これがこの記事の中核。コードを書いた Claude はそのコードをマージしたがる。レビューする Claude はコードの問題を見つけたがる。だから実装者 1 に対して adversarial reviewer を 2 以上つけ、レビュアーの仕事は「バグと動かない理由を見つけること」だけに限定する。しかもレビュアーには diff だけを渡し、実装者の推論は一切見せず、「このコードは間違っていると仮定せよ」と指示する。同一コンテキスト内で「自分でレビューして」と頼むのとは効果が全く違う、という設計思想。

#### 4. コードを直すのではなく、コードを生成するプロセスを直す

何か問題が起きたとき、手でコードを修正するのではなく、コードを生成するプロセス側を修正するのが原則。具体例として、Claude がコンパイルエラーを「関数をスタブ化する」ことで解消し始め、回避策を正当化する長いコメントを書き始めたので、「回避策の正当化に段落レベルのコメントが必要なら、そのコードは間違っている——コードを直せ」というルールをレビュアーに追加した。プロンプトを 1 回編集して数時間後には、この挙動は止まった。個々の出力に介入するのではなく、ルール(プロンプト)にフィードバックを蓄積していく運用。

#### 5. 客観的な検証層を言語・実装から独立させる

Bun のテストスイートは TypeScript で書かれているため、ランタイムの実装言語に依存しない。これが +100 万行の PR をマージできた最大の根拠で、言語非依存の 100 万アサーションのテストスイートと adversarial review が信頼の基盤だったと述べている。エージェントに大規模な変更をさせるなら、「エージェントの自己申告ではない外部の合否判定」が先に存在している必要がある。

#### 6. コンパイラエラーやテスト失敗を「作業キュー」として使う

crate ごとに `cargo check` を走らせてエラーをファイルに保存し、それを 64 の Claude に分配して、修正 → 2 レビュー → 適用のループを回した。同様にテストも、失敗したテストのスタックトレースをファイルに保存し、実装者が修正案を出し、レビュー 2、fixer が適用という同型のループ。「機械的に生成できる失敗リスト」をタスクキューに変換するのは、並列エージェント運用の基本パターンとして汎用性が高い。

#### 7. 並列実行の衝突は「禁止ルール」と「物理的分離」で防ぐ

失敗談が参考になる。開始 2 分で、ある Claude が `git stash` を実行し、別の Claude が `git stash pop`、さらに `git reset --hard` を実行して互いの作業を壊した。対策は「特定ファイルをコミットする以外の git コマンドを禁止、cargo も禁止、遅いコマンド全般を禁止」というルール追加と、4 つの worktree にシャーディングして各 16 Claude を走らせる構成。また、重いテストの隔離は「お願い」では足りず、`systemd-run`(cgroups)でメモリ・CPU 制限と pid 名前空間の分離を行った。エージェントの行儀はプロンプトだけでなくインフラ側でも強制する、という教訓。

#### 8. 人間の役割は「ループの監視とループの編集」

11 日間の大半、ワークフローの出力を手動で読んで問題を確認し、ループ自体を修正するよう Claude にプロンプトしていた。人間はコードを書くのではなく、メタレベル(プロセス設計・品質基準・異常検知)に張り付く。マージ前もテストが実際に実行されていてスキップされていないことを手動で検証したとあり、最終的な信頼判断は人間が握っている。

#### 9. マージ後も検証を自動化し続ける

マージ後に 11 ラウンドのセキュリティレビューを実施し、全パーサーの 24/7 カバレッジガイドファジングを追加。ファジャーが見つけたバグは自動的に Claude に送られ、再現と修正の PR を提出し、人間がレビューする。「バグ検出 → 修正 PR 生成 → 人間レビュー」という常設パイプライン化は、単発プロジェクトを超えた運用戦略として面白い。

#### 補足:注意して読むべき点

この事例が成立した前提条件も見逃せない。(1) 巨大で言語非依存のテストスイートが既にあった、(2) 「機械的移植」というスコープ限定(新機能ゼロ・アーキテクチャ維持)で正解が明確だった、(3) 著者がコードベースの全コンテキストを持つ創業エンジニアで、異常を即座に見抜けた——という点。それでも 19 件の既知リグレッションが発生し(すべて修正済み)、多くは「両言語で構文的には同一だが意味論が異なるコード」に起因したと正直に書かれており、自動レビューをすり抜けるのはこの種の「見た目は正しい」バグだという点も、レビュー設計の参考になる。ちなみにコストは API 価格換算で約 16.5 万ドルだったそうで、「3 人のエンジニアで 1 年」との比較で正当化している。

一言でまとめるなら、この記事の戦略は「エージェントを信頼するのではなく、エージェントが通過しなければならない検証構造を信頼する」に尽きる。

## Q2

> そうだよね?一般的な開発みたいに「コンテキストウィンドウがあふれるサイズのドキュメント全体というコンテキストの中から必要なものだけ読む」問題がないってことだよね?マッピングにより、小さいサイズでの対応ができる世界だよねこれ?

### A2

その理解でほぼ正しい。ただ「もともと問題がなかった」というより、「問題を潰すように設計した」と読むのが正確で、そこが一番の学びどころ。整理すると:

#### タスクの粒度が本質的にローカルだった

「.zig ファイル 1 つ → .rs ファイル 1 つ」という機械的移植は、1 タスクに必要なコンテキストが原理的に小さい。元ファイル+移植ルール+自分の出力だけで完結する。これは彼らが「incremental ではなく一括、ただし忠実な transpile 風の移植」というスコープを選んだ結果。「idiomatic Rust に書き直す」を選んでいたら、周辺コードの設計判断を参照する必要が生じ、ローカリティは崩れていた。スコープ選択そのものがコンテキスト設計だった、ということ。

#### グローバルな知識を「圧縮済み成果物」に前処理した

ここが「マッピング」の核心で、本来グローバルにしか分からないもの——ライフタイムはまさに「この struct フィールドがコードベース全体でどう使われるか」を追わないと決められない——を、事前の解析ワークフローで LIFETIMES.tsv という参照表に serialize した。つまり:

- 巨大コードベース全体(コンテキストに入らない) → 事前解析 → 小さな lookup 表(コンテキストに入る)

各ワーカーは「全体を読んで理解する」代わりに「表を引く」だけでよくなる。PORTING.md も同じで、判断基準の全体像を一度だけ議論して固定化し、以後は数 KB の規範文書として全エージェントに配る。RAG のような「その場で検索して読む」方式ではなく、必要な知識をタスク分割に合わせて事前計算しておく方式。

#### レビュアーはさらに小さいコンテキストで成立させた

adversarial reviewer には diff しか渡していない、という点も同じ思想。「全体を理解していないとレビューできない」を前提にせず、「diff だけ渡して間違い探しに専念させる方が、実装者の推論に汚染されず精度が出る」と割り切った。コンテキストを削ることをむしろ品質向上の手段にしている。

#### グローバルな正しさはテストスイートに外注した

個々のエージェントが全体整合性をコンテキスト内で保証する必要がないのは、100 万アサーションのテストスイートが「全体として正しいか」を実行時に判定してくれるから。コンテキストウィンドウの外にある検証機構が、全体視点の代わりを務めている構図。

#### ただし、ローカリティが崩れた場所がちゃんとある

完全にこの世界観で済んだわけではなくて、循環依存の解消(~100 crate への分割)は本質的にグローバルな問題で、ここでも同じ手を使っている——「どのコードがどこに属すべきかを分類して全部書き出すワークフロー」を先に走らせ、その成果物を見ながら別のワークフローがリファクタする、という二段構え。つまりグローバル問題に出会うたびに「解析して圧縮成果物にする → それを参照してローカルに作業する」を繰り返している。

#### 一般化すると

この事例の戦略は「コンテキストウィンドウに収まるタスクを探した」のではなく、**収まるようにタスク分解と知識の前処理(圧縮・索引化)を設計した**、と言える。一般的な開発でこれを再現するなら、「エージェントに大きなコードベースを読ませる方法」を考えるより、以下を先に設計する、という順番になる。

1. タスクをファイル/モジュール単位に閉じられるか
2. 閉じられない依存知識は事前に表やガイドに落とせるか
3. 正しさの判定をコンテキスト外(テスト・型・CI)に置けるか
