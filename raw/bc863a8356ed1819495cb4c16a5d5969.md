## geovisitor（ジオビジター）設計まとめ

### コンセプト
ストリートビューの写真を手がかりに、実際に歩いて目標地点へ近づく2人対戦ゲーム。GeoGuessr の推理と、オリエンテーリングの身体性を組み合わせたもの。

### ゲームの流れ
1. レンジ（範囲）を指定する
2. レンジ内でランダムに目標地点を選ぶ
3. 目標周辺のストリートビュー写真を数点提示する
4. プレイヤーは GPS と脚で目標に近づく
5. 制限時間終了時点で、目標に何m まで近づけたかで勝敗を決める

### 決まった設計判断
- 勝敗は「先着」ではなく「制限時間内の到達距離」。出発地点の偏りが影響しにくく、目標が到達不能な場所（公園の中、川の上など）でも「最も近づける場所はどこか」という問題として成立する
- 写真は複数枚。方位のばらついた地点から出すことで三角測量的に絞り込める
- 写真の向き（heading）はランダム。目標方向に向ける計算は atan2 一発なので、難易度オプションとして後から足せる
- パノラマの撮影座標はプレイヤーに見せない。内部でのみ保持

### 保留
- 住宅街に目標が落ちる問題はマナーの範疇として今回は扱わない

### 実装方針
- Street View Static API の metadata エンドポイントは「座標＋半径」で最寄りパノラマを1件返す仕様なので、目標を中心に円周上の数点＋中心で叩き、pano_id を重複排除して候補を集める。候補が足りなければ半径を段階的に広げる
- 候補から「目標に近い」と「互いの方位差が大きい」を両立するよう数点を選ぶ
- API キーはクライアントに埋めず、画像 URL の生成はサーバー側で行う
- pano_id は変わりうるので保存せず、座標で保存して都度引き直す

### コスト・制限
- metadata は無料でクォータも消費しないため、探索は何回叩いても問題なし
- 有料なのは提示する画像のみ。1ゲーム3〜4枚で数円程度、API ごとの無料枠もある
- rate limit は 30,000 QPM で、2人プレイの規模では無関係
- metadata の位置精度は 50m 程度。採点には影響しないが、方位計算に多少のズレはありうる

### 残っている検討事項
- チート対策（画像検索、ストリートビュー総当たり）をどこまでやるか
- 安全面のルール（徒歩限定、走行中の位置更新停止など）
- レンジ指定の UI（市町村、駅から徒歩圏、公園内など）
