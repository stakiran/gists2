## 要するに？（一言で）

**「コードを書く作業はほぼタダになった。だから人間の仕事は、何を作るかを決めることと、ちゃんと動くと証明することに移った」** というのがこのガイドの主張です。

## 1. 原則：考え方の転換

- **エージェントの定義はシンプル。** 目的を達成するまで、ツールをループで呼び続けるもの。コードを実際に実行できることが、ただのチャットAIとの決定的な違いです。
- **バイブコーディングとは別物。** バイブコーディングはレビューしていないプロトタイプ品質のコードを指す言葉。本番品質まで持っていく作業とは区別すべき、という立場です。
- **コードは安くなったが、「良いコード」は今も高い。** ちゃんと動く、動くと確認済み、テストがある、ドキュメントが最新、エラー処理がある。こうした条件を満たす責任は人間側に残ります。
- **「割に合わないからやめておこう」と思ったら、とりあえず投げてみる。** 非同期のエージェントに任せれば、失敗してもトークン代が無駄になるだけです。
- **できることを溜め込め。** 動くコード例を手元に蓄積しておき、「AとBの例を組み合わせて新しいものを作って」と頼むのが強力です。一度解いたトリックは二度と解き直さなくていい。
- **AIで品質はむしろ上げられる。** 名前の統一や巨大ファイルの分割のように、単純だけど面倒な技術的負債の返済こそエージェント向きです。小さなコードの臭いも放置しない姿勢が取れるようになります。
- **技術選定はプロトタイプで検証する。** 負荷試験のシミュレーションなども安く作れるので、複数案を並行で試してから選べます。
- **学びを指示書に書き戻す。** LLM自体は失敗から学ばないので、得た教訓を指示やツールに反映して改善を複利で効かせます（Compound Engineering）。
- **最大のアンチパターンは、自分でレビューしていないPRを他人に出すこと。** 小さく分ける、背景を書く、手動テストの記録やスクショを添える。AIが書いたPR説明文も自分で読み直すこと。

## 2. エージェントとの付き合い方

- **仕組みを知っておく。** 中身は「LLM＋システムプロンプト＋ツール」のループにすぎません。LLMは状態を持たないので、会話が長くなるほど毎回の入力が増えてコストも上がります。
- **Gitは全部エージェントに任せていい。** コマンドを覚える必要はなく、何ができるかを知っていれば十分です。「Gitがぐちゃぐちゃになったから直して」「git bisectでバグの混入時点を探して」「直前のコミットを取り消して」などが使えます。
- **セッションの最初に「今日の変更を確認して」と頼む。** 最近の作業内容が文脈に入り、続きの話がしやすくなります。
- **サブエージェントの価値はコンテキストの節約にある。** 調査や大量のテスト出力は子に任せ、親の作業領域をきれいに保ちます。専門役の子を作りすぎる必要はありません。

## 3. テストとQA（ガイドの一番の核）

- **「Use red/green TDD」と一言添える。** テストを先に書き、落ちることを確認してから実装させる、という意味がこれだけで伝わります。動かないコードや不要なコードを防げます。
- **新しいセッションは「First run the tests」から始める。** テストの存在を知らせ、規模感をつかませ、テストを意識する状態にさせる効果があります。
- **テストが通っても動くとは限らない。** エージェントに手動テストもさせます。`python -c` で試す、`curl` でAPIを叩く、Playwright などでブラウザを操作してスクショを確認する、といった方法です。
- **作業の証拠を残させる。** 本人作のツール Showboat を使うと、実行したコマンドと実際の出力がそのまま記録されます。エージェントが「うまくいったことにする」ズルを防げます。

## 4. コードを理解する（認知的負債の返済）

- **AIが書いたコードを理解しないまま放置するのは「認知的負債」。** 技術的負債と同じように、後々の開発を遅くします。
- **リニアなウォークスルーを書かせる。** コード片は手でコピーさせず、コマンドで実際に抜き出させると、幻覚が混ざりにくくなります。
- **アニメーションやインタラクティブな解説ページを作らせる。** アルゴリズムの直感的な理解に効きます。AIを使うと学びが減るどころか、新しい分野を学ぶ機会にできます。

## 5. 実例から学べるプロンプトのコツ

- **短くても伝わる。** ファイル名だけ、既存リポジトリを参照させるだけで、かなりの文脈が伝わります。
- **参照コードは /tmp にクローンさせる。** 誤ってコミットに混ざるのを防げます。
- **自己検証の手段を必ず渡す。** 例えば「この画面と本番サイトのトップページを比べて確認して」のように指示します。エージェントは自分で検証できると格段に良い仕事をします。
- **作業中も見守り、気づいたら追加指示を差し込む。**

## 付録：本人の普段使いプロンプト

- **Artifacts 用：** React を使わず、素のHTML/JSで作らせる指示。
- **校正用：** 誤字・文法・論理の弱さをチェックさせる指示。ただし意見や「私」を含む文章は自分で書く、という線引きをしています。
- **その他：** 画像の代替テキストの下書き、ポッドキャストの名言抽出。

---

**総評：** 新しい魔法の技術ではなく、「テスト・レビュー・検証という昔ながらのエンジニアリング規律を、安くなったコードの世界でどう徹底するか」の手引きです。明日から使えるのは、「First run the tests」「Use red/green TDD」「自分で検証してから出す」の3つだと思います。
