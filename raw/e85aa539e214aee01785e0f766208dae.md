# MV3広告ブロッカーの設計思想 — フィルタリストからの脱却を試みる4段階

Chrome拡張(Manifest V3)で広告ブロッカーを作りながら、「フィルタをどう手に入れるか」という問いを掘り下げた記録。手書きルールから始めて、最終的に「AIがサイトごとにフィルタをその場で書く」設計に到達するまでの発想の変遷を整理する。

## 前提: MV3という制約

MV3ではwebRequestによるブロッキング(リクエストを1件ずつJSで審査して止める方式)が廃止され、`declarativeNetRequest`(DNR)に一本化された。DNRは事前宣言したルールをブラウザ本体が評価する方式で、拡張のコードは通信内容に触れない。プライバシーと性能は上がったが、「実行時に任意ロジックで判定する」自由は失われた。

つまりMV3の広告ブロックは本質的に「**いかにして良いルール集合を用意するか**」の問題になる。ルールの供給源をどこに置くかで、設計は次の4段階に分かれた。

ルール数の上限は意外と広い。静的ルールは各拡張に30,000件が保証され、全拡張共有のグローバルプール300,000件からさらに借りられる(合計最大330,000件)。EasyListのネットワークルールが約35,000件なので、主要リストは丸ごと積める。動的ルール(実行時に追加するルール)もblock/allow等の安全なものなら30,000件まで(Chrome 121以降)。

## v1: 手書きの静的ルール

最初の素朴な実装。doubleclick.net、googlesyndication.com、taboola.com など既知の広告配信ドメイン15件を `rules.json` に手書きし、静的ルールセットとして同梱する。

拡張の骨格(manifest、DNR、ポップアップでのON/OFF、バッジへのブロック数表示)を理解するには十分だが、カバレッジとして話にならない。ここで当然の疑問が生まれる — 「フィルタを充実させるしかないのか?」

## v2: 変換済みフィルタリストの流用 + 動的ルール

手でルールを書き足すのは徒労なので、実務の定石を採る。ポイントは2つ。

**変換済みリストはnpmに落ちている。** `@adguard/dnr-rulesets` パッケージに、AdGuardがEasyList系フィルタをDNR形式に変換済みのルールセットが入っている。ベースフィルタ(約70,000件)と日本語フィルタ(約2,200件)を抽出し、AdGuard独自の `metadata` キーを剥がしてChromeの正式スキーマ(id / priority / action / condition)だけにすれば、そのまま静的ルールセットとして積める。自前で変換器を書く必要すらない。uBlock Origin LiteやAdGuard MV3版もこの「ビルド時変換」方式で、実運用ではCIで npm update → 抽出 → 再ビルドを回してリスト更新に追従する。

**動的ルールで再公開なしの更新。** `updateDynamicRules` APIを使えば、拡張を再公開せずに実行時にルールを追加・削除できる。ユーザーのカスタムブロックや、サーバーからのフィルタ差分配信に使える。

これで実用水準にはなる。しかしこの設計は「誰かがメンテしているリスト」への依存を前提にしている。次の問いは自然に「**フィルタ更新という発想自体から脱せないか?**」になる。

## v3: 構造ヒューリスティクスによる自己学習

リストが不要になりうる根拠は、**広告が構造的な指紋を持っている**ことだ。学術研究もこの方向にあり、AdGraph(ページ構造+ネットワークのグラフをMLで分類)やPercival(レンダリングパイプライン内での知覚的検出)などが知られている。

MV3ではリクエスト単位の実行時判定ができないため、アーキテクチャは「content scriptで検出 → 証拠が溜まったドメインを動的DNRルールに昇格」という**二段構え**になる。検出には3種類の指紋を使った。

1. IAB標準サイズ(300×250、728×90 等)のサードパーティiframe
2. `ad` / `sponsor` 系トークンを持つid・class(単語境界で照合し、かつサードパーティ埋め込みを内包する場合のみ。「shadow」「add」の誤爆防止)
3. 表示義務ラベル(「広告」「Sponsored」「PR」)の完全一致 + 近傍のサードパーティiframe

検出した要素は即座に非表示(DOM層)。同時に供給元ドメインへ証拠スコアを加算し、「スコア閾値超え かつ 2つ以上の別サイトで観測」で動的ルールに昇格させる(ネットワーク層)。つまり**拡張が自分でフィルタリストを書く**。使うほど自分の閲覧傾向に合った自家製フィルタが育つ。

誤検出対策が設計の大半を占める。複数サイト観測を昇格条件にする(1サイトの変なCSS命名で誤学習しない)、main_frameはブロックしない(誤学習してもページ自体は開ける)、ユーザーによる解除は再学習防止リスト入り、CDN(gstatic、cloudflare等)は学習対象から恒久除外。

そして正直な限界もここにある。ヒューリスティクスはprecision(誤検出)とrecall(見逃し)のトレードオフから逃げられない。ML研究でも精度は95%前後で、残る誤検出はサイトを壊す。人間がキュレーションするフィルタリストとは、このトレードオフを人力で解決した成果物なのだ。だから業界はリストを捨てられない。

## v4: AIによるサイト単位のルール生成

最後の発想転換。「サイトのHTMLをAIに読ませて広告を検出させればいいのでは?」— これは筋が良いが、そのまま実装すると破綻する。ページを開くたびにLLMへ問い合わせるとレイテンシとコストが成立しない。

鍵となる設計判断は、**AIを「リアルタイム検出器」ではなく「ルール生成器」として使う**こと。

1. **スケルトン抽出** — HTMLを丸ごと送らず、テキストノードを全て落とした構造表現(`div#sidebar.widget` → `iframe[300x250][@ad.example.net]` の階層)に圧縮する。トークン量が1〜2桁減り、本文やフォーム入力がAPIに渡らないためプライバシーも守られる
2. **AI解析** — スケルトンをClaude Haikuに渡し、広告要素のCSSセレクタと広告配信ドメインをJSONで返させる
3. **出力の検証** — AIの出力は信用しない。`body` や `div` 等の破壊的セレクタは拒否、構文エラー(幻覚)はtry/catchで棄却、1セレクタ25要素超のマッチは「広範すぎ」として不採用、ドメインは形式チェックとCDN除外を通す
4. **キャッシュと二層適用** — 結果はサイト単位で7日キャッシュ。セレクタは以後の訪問で即適用(DOM層)、ドメインは動的DNRルール化(ネットワーク層)

AI呼び出しは**サイトごとに初回の1回だけ**なので、コストはサイト1件あたり1円未満に収まる。人間がフィルタリストを書く作業を、AIがサイトごとにオーダーメイドで代行する構図であり、これはuBlock Originでカスタムフィルタを手書きする文化のAI代替に相当する。

v3との本質的な差は、判定に**文脈理解**が入ること。「このiframeはYouTube埋め込みで、こっちは広告」という区別は、サイズやクラス名では原理的に不可能だが、構造の文脈を読めるLLMなら可能になる。一方で、解析トリガーが手動である点(自動化すると閲覧履歴がAPIに流れるため意図的に手動化)、サイト改修時に再解析が要る点、1回のスナップショットでは遅延読み込み広告を見逃しうる点が弱点として残る。

## 比較と結論

| | ルールの供給源 | カバレッジ | 誤検出 | 更新コスト | 外部依存 |
|---|---|---|---|---|---|
| v1 手書き | 人間(自分) | 極小 | なし | 手作業 | なし |
| v2 リスト流用 | 人間(コミュニティ) | 大 | ほぼなし | CI再ビルド | フィルタリスト |
| v3 自己学習 | ヒューリスティクス | 中(育つ) | あり | 不要 | なし |
| v4 AI生成 | LLM | サイト単位で高精度 | 検証で抑制 | サイト毎に1回 | LLM API |

一周して分かるのは、「フィルタ更新からの脱却」は**部分的には可能だが、単独方式では人力リストに勝てない**ということ。リストとは誤検出問題を人間の目で解決した資産であり、その価値は簡単には代替できない。

現実的な最適解はハイブリッドになる。v2のリストで既知の広告網の9割を即座に潰し、漏れるロングテール(個人サイト、国内マイナー広告、新興配信網)だけをv3の学習やv4のAI解析で個別に埋める。役割分担で言えば、リストは「過去の集合知」、学習とAIは「未知への適応」を受け持つ。

なお、DNRが担うのはネットワーク層のみで、ページ内に残る空の広告枠やアンチアドブロック要素への対処(コスメティックフィルタ)にはcontent scriptでのDOM操作が別途必要になる。v3・v4はその領域も同時にカバーしている点で、単なるDNRラッパーとは層が違う。

## 技術メモ

- DNRの `requestDomains` 条件はサブドメインにも自動でマッチする
- 動的ルールのID空間は静的ルールと独立している(1から採番してよい)
- regexルールは種別ごとに1,000件まで、コンパイル後2KB制限あり
- バッジへのブロック数表示は `setExtensionActionOptions({ displayActionCountAsBadgeText: true })` の1行で済む
- 拡張からのAnthropic API直叩きには `anthropic-dangerous-direct-browser-access: true` ヘッダが要る
- eTLD+1の判定を自前でやる場合、`co.jp` 等の属性型ドメインの近似処理を忘れると学習・判定の粒度が壊れる
