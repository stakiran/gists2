# Agent Plugins Specification 1.0.0 読解メモ — 仕様の要点と Anthropic 不在の考察

> 2026-08-10 時点の情報に基づく。仕様は [agentplugins/agent-plugins-spec](https://github.com/agentplugins/agent-plugins-spec)(公開版 1.0.0、2026-08-06 発表)。後半の「考察」は公開情報からの推測であり、当事者の公式見解ではない。

## 1. Agent Plugins とは

AI エージェントを拡張する再利用可能なコンポーネントを、配布可能な「プラグイン」としてパッケージ化するための、ベンダー中立なオープン標準。設計思想は「最小の移植可能な共通床(interoperability floor)」に徹すること。

- パッケージ単位は zip 等ではなく**普通のディレクトリ**(`ls` / `cat` / `git` で検査可能)
- v1 のコンポーネントは **Agent Skills と MCP サーバーの 2 種類だけ**。コマンド・フック・サブエージェント等は「クライアント固有すぎる」として意図的に対象外
- スキル形式自体は [Agent Skills 仕様](https://agentskills.io/specification)(Anthropic 発の SKILL.md 形式)を参照。本仕様が定めるのは「プラグイン内での発見方法」のみ
- クライアント固有の機能は逆ドメイン名前空間(`extensions` フィールド / トップレベルディレクトリ)に隔離
- 配布・レジストリ・マーケットプレイス・UX は仕様の対象外

発表時の対応クライアントは ChatGPT / Codex / Cursor / GitHub Copilot / Kiro / VS Code。TSC(技術運営委員会)は Amazon・Cursor・Microsoft・OpenAI・Vercel のメンテナで構成され、Google が後からコアメンテナとして参加を表明。**Anthropic は不参加・未表明**。

## 2. 従うべきこと(プラグイン作者の場合)

### 必須構造

```text
my-plugin/
├── plugin.json      # 必須。唯一のポータブルマニフェスト
├── skills/          # スキルはここ固定。直下サブディレクトリの SKILL.md のみ発見(再帰探索なし)
│   └── xxx/SKILL.md
├── mcp.json         # MCP 設定はここ固定。plugin.json へのインライン記述は不可
└── com.example.foo/ # クライアント固有ファイルは逆ドメイン名のトップレベルディレクトリへ
```

### plugin.json

- `$schema`(値は正確に `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`)と `name` が必須
- スキーマは**クローズド**。許可フィールドは `$schema` / `name` / `version` / `description` / `author` / `homepage` / `repository` / `license` / `keywords` / `extensions` のみ。クライアント固有データは `extensions` の逆ドメインキー配下へ
- `name` は小文字英数字・`-`・`.` のみ、1〜64 文字、先頭末尾は英数字、`--` / `..` 不可
- 未知トップレベルフィールドは「報告して無視」(非致命)。それ以外のスキーマ違反は致命的(プラグイン全体が拒否される)

### パス封じ込め

- パッケージ内パスはすべて `./` 始まりのプラグイン相対パスで書き、解決後もプラグインルート内に収まること。`../` での脱出は無効扱い

### mcp.json

- トップレベルは `$schema` と `mcpServers` のみ。`$schema` のバージョンは plugin.json と一致必須
- 各サーバーは `stdio` / `streamable-http` / `sse` のいずれかを `type` で明示するクローズドユニオン。未知フィールドがあるとそのエントリは無効
- `stdio` の `command` はシェル文字列ではなく**単一の実行トークン**(ベア名 or `./` パス)。同梱バイナリは必ず `./` パスで参照
- `args` / `env` / `cwd` で展開されるのは `${PLUGIN_ROOT}` と `${PLUGIN_DATA}` のみ。他の環境変数展開は起こらない
- `env` に `PLUGIN_ROOT` / `PLUGIN_DATA` という名前のエントリを置くとそのサーバー設定は無効
- リモート URL はループバック以外 HTTPS 必須。ユーザー情報・フラグメント不可
- **秘密情報を `headers` や `env` に埋め込まない**(パッケージ内容は可視データ扱い)。認証はクライアント側の責務

### 依存してはいけないこと

- クライアントが stdio と streamable-http の両方をサポートする保証はない(どちらか一方でも適合)
- 継承環境変数や `PATH` の挙動
- 永続化したい状態(node_modules・キャッシュ等)は `PLUGIN_DATA` に置く前提で設計する(パッケージ内容は更新時に置き換わる)

### クライアント実装者の場合

ディレクトリからのロード、クローズドスキーマ検証、パス封じ込めの強制、最低 1 コンポーネント種のサポート、コンポーネント単位の障害隔離(1 つの MCP サーバーが起動失敗しても他のスキルは読み込み続ける)が最低要件。仕様の Appendix A に実装チェックリストがある。

## 3. なぜ Anthropic だけ対応を表明していないのか(考察)

状況証拠:

- 発表は 2026-08-06 でまだ日が浅い
- TSC は Amazon・Cursor・Microsoft・OpenAI・Vercel(+ Google が後から参加)。Anthropic は席なし
- ローンチ対応 6 クライアントに Claude Code は不在。ただしサードパーティの plugins CLI はポータブル形式を Claude Code 独自形式に変換してインストールでき、**実用上はすでに動いている**

考えられる理由(説明力が高いと思う順):

1. **自前の、より広いプラグインシステムを既に持っている。** Claude Code のプラグインはコマンド・フック・サブエージェント・LSP・マーケットプレイスまで含み、エコシステムとして先行。Agent Plugins v1 が標準化した skills + MCP はその部分集合にすぎず、採用しても得られるものが少ない
2. **標準の中身の半分はすでに Anthropic 製。** skills コンポーネントは Anthropic 発の SKILL.md 形式をそのまま参照している。「Anthropic が作った形式を、Anthropic 抜きの競合連合が標準のコアに据えた」構図であり、ポータビリティの本体(スキル形式)は既に握っているので急いで乗る動機が薄い
3. **競争戦略。** TSC の顔ぶれは Claude Code の直接競合。パッケージング標準化は先行者のエコシステム優位をコモディティ化する方向に働く
4. **単なる様子見。** MCP のときは Anthropic が提案側で他社が数ヶ月かけて採用した。立場が逆なだけで、現時点の沈黙は「拒否」ではなく「未表明」の可能性も十分ある

## 4. 仮に Claude Code が対応したら(考察)

### 技術的には障害が少ない

- マニフェストのパスが**衝突しない**(Claude Code は `.claude-plugin/plugin.json`、標準はルートの `plugin.json`)。デュアル形式プラグインは今日でも理論上作れる
- `skills/<名前>/SKILL.md` の探索場所と形式は**両者で完全に同一**(スキル形式が Anthropic 発なので当然)
- MCP 設定は形が違うが機械的に変換可能。`${CLAUDE_PLUGIN_ROOT}` と `${PLUGIN_ROOT}` もほぼ同概念
- 仕様の §8(クライアント拡張)は Claude 固有コンポーネント(コマンド・フック・エージェント定義・出力スタイル)を `com.anthropic.claude-code/` にそのまま収められる設計

対応するなら「ネイティブ形式を維持したままポータブル形式のローダーを追加(移行ではなく併存)」が現実的な形。

### エコシステムへの影響予想

1. **「非公式の相互運用」の公式化。** ユーザー体験としては正規化に近い。むしろ逆方向——最も層の厚い Claude Code 向けプラグイン資産のうち skills + MCP で成立するものが他クライアントへ流出——のインパクトが大きく、Claude Code エコシステムが標準の最大のコンテンツ供給源になりうる
2. **Anthropic の標準内での立場はむしろ強まる。** スキル形式が全ベンダー採用標準の中核を占める構図が固定化。v2 で保留中のコマンド・フック・サブエージェントの標準化議論では、最も成熟した実装を持つ Claude Code の形式が下敷きになる公算が高い
3. **「最小公倍数への引力」リスク。** 全クライアント対応を狙う作者は skills + MCP だけで作るのが合理的になり、フックやサブエージェントを活用した凝ったプラグインが相対的に減る圧力。拡張名前空間で差別化は続けられるが、拡張部分は他クライアントでは無視される
4. **ユーザー・チームには素直にプラス。** 1 つのディレクトリで管理したプレイブックが Claude Code / Cursor / Copilot 等で共通に動き、クライアント乗り換えコストが下がる

**結論(予想):** 技術統合はスムーズに進み、本当の争点は v2 のスコープ交渉に移る。対応表明そのものより、コマンド・フックの標準化議論で Anthropic が自社形式をどこまで通せるかが、数年後のエージェント拡張エコシステムの形を決める。
