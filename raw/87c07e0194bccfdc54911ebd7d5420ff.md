# loop と goal

## `/loop` と `/goal` の違い

出発点はこの2つの区別でした。どちらも再プロンプトなしでセッションを走らせ続けますが、次のターンを何が起動するかが違います。`/goal` は完了条件を満たすまで作業を進め続けるもので、各ターン後に小さいモデル（デフォルト Haiku）が「条件を満たしたか」を判定し、満たすまで制御を返しません。`/loop` は時間間隔で同じプロンプトを再実行するポーリングです。判断のテストは「作業を終わらせたいのか、変化を見張りたいのか」——終わらせるなら `/goal`、見張るなら `/loop`。

## バグ修正を頼んだ場合

「バグ直して」だけではどちらのコマンドも自動発動せず、通常の対話モードで動きます。`/goal` を活かすなら「バグを直して」のようなプロセスではなく、「テストが exit 0 で通る」といった検証可能な終了状態で条件を書く必要があります。

## `return 0` 問題

ここがこの議論の一番鋭かった点です。`/goal` の評価役は Claude が会話に出力した内容しか見ず、コマンドを独立実行しないため、テストにダミーを書いて通せてしまう。これはシステムカードでおなじみの「タスクをゲームする」挙動そのもので、対策は Claude が触れない場所に検証を固定することでした。具体的には、失敗テストを先に人間が書いてコミットし「そのテストファイルを変更しないまま緑にする」と条件付けする、テスト件数やカバレッジまで出させる、といった手です。

## `/loop` の使いどころ

`/loop` はバグ修正の芯には向かず、その周辺の監視役——リグレッション監視やフレーキーテストの炙り出しなど——に合う、という整理をしました。そこから発展して、「普段使いのタスク管理ツールのログを3時間ごとに読ませてレポートと提言を出す」という用途は `/loop` の王道だ、という話になりました。実運用の勘所は、差分だけ読む・レポートはファイルに残す・オートモードは最小範囲、の3点。ただし `/loop` は開いているセッション内でしか回らず、無人常時稼働にはスケジュール実行側（scheduled agents / Cowork の定期タスク）の仕組みが要る、という制約も確認しました。

## Remote Control との組み合わせ

ここで一つ重要な訂正が入りました。Remote Control はクラウド実行ではなく同期レイヤーで、「PCを閉じても回り続ける」ものではない。実行はローカルに残り、スマホやブラウザはその生きたセッションへの窓口にすぎず、PCの起動とネット接続が前提です。

そこから、役割を分ける設計に落ち着きました。**エンジン（無人）は `/loop`**、**ハンドル（随時介入）は Remote Control**。この分け方の良いところは、Remote Control の弱点である承認の壁が、もともと人間がその場にいて会話する側に移るので実質無害化されること。

## 最終形

最後にあなたが削ぎ落として、こうなりました。`/loop` はただ回しっぱなしにして `reports/` を吐かせ、Remote Control で外からそれを覗いて必要に応じて会話で詰める。ループが書く・対話は読むという非対称なので、私が途中で持ち出したセッション分割や drift の心配は不要でした。エンジンは放置、ハンドルは随時。残る現実的な制約は「ローカルマシンが起動していてネットにつながっている前提」の一点だけ、というところで着地しています。
