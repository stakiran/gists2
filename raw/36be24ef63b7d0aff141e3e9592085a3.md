# Graph Engineering は「閉路つきグラフの設計論」である — ループエンジニアリング整理ノートからの接続

前作: [ループエンジニアリング整理ノート](https://gist.github.com/stakiran/f818c64c89f3f74c8ce0b054eb5534d4)

前作では「契約を持ったループ」を第一級の設計単位として定式化した。本稿では、2026年7月に流行語化した **Graph Engineering** を、前作の枠組みの自然な延長——**閉路つき有向グラフの設計論**——として位置づける。バズワードとしての Graph Engineering は定義が割れているが（後述）、この捉え方を採ると議論の大半が整理できる、というのが本稿の主張である。

# 第0部 前提: Graph Engineering の現状

- 震源は Peter Steinberger の2026年7月18日のポスト「[Are we still talking loops or did we shift to graphs yet?](https://x.com/steipete/status/2078277297791189132)」。体系的な原典は存在しない

- 本稿が扱うのは (a) であり、(b) もその特殊ケースとして回収できる。(c) は別物なので扱わない

本稿の立場: **Graph Engineering に新しい機構はない。前作で定式化した「契約を持ったループ」の合成構造を、有向グラフとして明示的に設計対象へ昇格させたものである。**

# 第1部 主張: 「ループ vs グラフ」という対立は定義から消える

## 1.1 ループとは閉路である

グラフ理論の語彙では、ループ（前作の意味での反復実行単位）とは**有向グラフにおける閉路 (cycle)** にほかならない。前作 1.1 の定義——「観測 → 行動 → 評価 → 状態更新を終了条件まで繰り返す」——は、そのまま `観測 → 行動 → 評価 → 状態更新 → 観測` という4ノードの有向閉路として描ける。

すると次が従う:

| 用語 | グラフ語彙での再定義 |
|---|---|
| Loop Engineering | **閉路が1個**の特殊ケースの設計論 |
| Graph Engineering | **一般の有向グラフ**（閉路を複数含みうる）の設計論 |

二次記事が延々と論じている「Graph は Loop の置き換えか、包含か」という問題は、この定義を採った瞬間に消える。**包含は自明**であり、議論する余地がない。「Loop Engineering is dead」という死亡宣告は、「1変数関数は死んだ、これからは多変数関数だ」と言っているのと同じで、命題として成立していない。

## 1.2 前作の合成パターン表は「エッジの型カタログ」だった

前作 3.4 で挙げた合成パターンは、グラフ語彙ではエッジ（と部分グラフ）の型として読み直せる:

| 前作の合成パターン | 記法 | グラフとしての構造 |
|---|---|---|
| 直列合成 | `L₂ ∘ L₁` | DAG エッジ（閉路なし） |
| 監督・入れ子 | `L_supervisor[ L_worker ]` | 制御エッジによる階層閉路 |
| 並列・競争 | `parallel(L_A, L_B)` | fan-out / fan-in（分岐と合流） |
| 相互フィードバック | `L_impl ⇄ L_review` | 2-閉路 |
| フォールバック | `fallback(L_A, L_B)` | 条件付きエッジ（ガード付き遷移） |

前作はノードの意味論（ループの契約）を厳密化した結果、自然に合成構造＝グラフの話に到達していた。Graph Engineering はこの合成構造の側に名前を付けたものと解釈できる。

# 第2部 強連結成分分解による正確な分業

## 2.1 定理の借用

グラフ理論の基本事実を借りる:

> 任意の有向グラフは、各**強連結成分 (SCC)** を1ノードに縮約すると、必ず **DAG**（凝縮グラフ, condensation）になる。

これを設計論として読み替えると、閉路つきグラフの設計は正確に2層へ分解できる:

```
閉路つきグラフの設計
  = SCC の内部設計          … 各ループの契約設計 = Loop Engineering
  + SCC 間の DAG の設計      … パイプライン構造の設計 = 従来の DAG ワークフロー
```

つまり:

- **Loop Engineering** = 強連結成分の内側の設計論（Goal, State, Budget, Evidence, Stop, …）
- **従来の DAG ワークフロー** = 凝縮グラフの設計論（実行順序・並列性）
- **Graph Engineering** = その両方＋**どこに閉路を置くか**の決定

「DAG 型ワークフローと何が違うのか？」への答えもここから出る。違いは「閉路の許容」だが、より正確には**凝縮すれば DAG に戻る形でしか閉路を置かない**、つまり閉路を野放しにするのではなく SCC という管理単位に封じ込める、という規律である。

## 2.2 「内／外の相対性」は階層的縮約の話だった

前作第2部で「内側／外側ループは相対的な呼称であり、実体は階層化された制御ループ群」と結論した。グラフ語彙ではこれは**どの縮約レベルでグラフを見るか**の話に還元される:

```
最も細かい解像度: H₁ の内部（観測→行動→評価→更新の閉路）
1段縮約:          H₁ を1ノードとみなす。H₂ → H₁ → H₂ の制御閉路が見える
2段縮約:          H₂ を1ノードとみなす。H₃ のリリースループが見える
```

`loop(H₂)[ loop(H₁) ]` という前作の入れ子記法は、閉路の中にノードとして別の閉路（縮約済み SCC）が埋め込まれている状態の表記だった、と再解釈できる。

# 第3部 エッジの型付け: パイプラインと外側ループの区別を形式化する

前作 2.3 の核心的な指摘——「結果を使うだけならパイプライン、継続・再実行・終了を制御して初めて外側ループ」——は、グラフ語彙では**エッジの型付け**として形式化できる。

## 3.1 データエッジと制御エッジ

| エッジ型 | 運ぶもの | 例 |
|---|---|---|
| **データエッジ** | 成果物・状態 (artifact, State′) | 実装ループの出力をレビューループへ渡す |
| **制御エッジ** | 制御権限（再実行・指示変更・中断・終了の決定） | 監督ループが worker を再投入する |

すると前作の区別はこう書ける:

> - `loop(H₁) → loop(H₂)` がデータエッジのみ ⇒ パイプライン
> - **制御エッジの部分グラフに閉路がある** ⇒ そこに外側ループ（監督関係）が成立している

「外側ループの成立条件は制御関係である」という前作の命題が、「制御エッジ部分グラフ上の閉路の存在」という判定可能な構造的性質になる。エンタープライズ向けの Graph Engineering 解説で語られる "typed edges"（信頼・権限・ケイデンスをエッジに符号化する）は、実質これを言っている。

## 3.2 フィードバック網解釈 (b) の回収

Graph Engineering の第2の解釈——メトリクス・評価・監査・ポリシーのループ網が互いを監視・制約・修正する——も、この語彙で回収できる。あれは**制御エッジが支配的なグラフ**（実行よりガバナンスが主目的）であり、「速いループは遅いループの決定を上書きできず、シグナルを上位へエスカレーションする」というケイデンス階層は、制御エッジに周期ラベルを付けた半順序として書ける。実行グラフとガバナンスグラフは、同じ形式の上の異なるラベル付けにすぎない。

# 第4部 停止性: budget は閉路上の減少量である

前作 3.6 の筆頭課題「終了が保証されない」も、グラフ側で綺麗に述べられる。

プログラム検証では、ループの停止性を **variant（整礎な順序で減少する量）** の存在で証明する。閉路つきグラフに同じ規律を課すと:

> **停止性の設計規律**: グラフ内のすべての閉路は、**budget を単調減少させるエッジを少なくとも1本**含まなければならない。

- 試行回数・トークン予算・時間予算のいずれかが、閉路を一周するたびに必ず減る
- budget が尽きたとき、閉路は脱出エッジ（`blocked` / `timeout` として上位へ制御を返す）を持たなければならない

前作の `Loop { budget, escalation }` フィールドは、この観点では**閉路に付ける well-foundedness 条件と脱出エッジの宣言**だった。逆に言うと、この規律を満たさない閉路を含むグラフは「暴走しうる設計」として静的に検出できる。閉路を許すことと無限ループを許すことは別である、という点が Graph Engineering の議論ではしばしば混同されているが、区別は variant の有無にある。

# 第5部 この捉え方の限界 (2点)

閉路つきグラフの設計論として捉える立場の、正直な限界を記しておく。

1. **動的トポロジーははみ出す。** Graph Engineering 言説の一部は「実行時にグラフ自体が組み替わる」型（LangGraph 的な動的ルーティング、エージェントによるサブグラフの生成）を含む。静的な閉路つきグラフの設計論がカバーするのは「実行前に位相を固定し検証する」型であり、動的な型を厳密に扱うにはグラフ書き換え系（graph rewriting）やプロセス代数の道具が要る。実務的には「動的に見える部分も、取りうる位相の集合を事前に列挙できるなら静的設計に落ちる」が、真に開いた組み替えは別枠。

2. **設計論の中身の大半は位相ではなくラベルに宿る。** 前作の核心である契約 (Goal, Budget)・証拠 (Evidence)・エスカレーションは、グラフの形（位相）だけでは表現できず、ノードとエッジへの**ラベル付けの意味論**が本体になる。「閉路つきグラフ」は骨格として綺麗だが、骨格だけ真似てラベルの規律（特に Evidence と variant）を欠いた設計は、前作 1.6 で挙げた失敗（誤りの自己増殖、検証可能なものへの偏り）をグラフ規模で再生産する。

# 第6部 先行者たち: これは新発明ではない

「閉路つきグラフ＋階層＋型付きエッジ」の設計論には、数十年の先行者がいる。Graph Engineering を評価するときの参照点として挙げておく。

| 先行技術 | 対応する概念 |
|---|---|
| **Statecharts** (Harel, 1987) | 階層状態（内／外の相対性 = 第2部）、直交並行性（parallel 合成）、ガード付き遷移（fallback） |
| **ペトリネット** | 並行実行・合流・トークンによる資源制約（budget の先祖） |
| **制御工学のブロック線図** | フィードバック閉路の合成、ケイデンス階層（カスケード制御） |
| **プロセス代数 (CSP, π計算)** | 動的トポロジーの厳密な扱い（第5部の限界1への処方箋） |
| **Pregel / BSP モデル** | LangGraph の内部実装。メッセージパッシングによる閉路つきグラフの実行 |

したがって本稿の結論はこうまとめられる:

> **Graph Engineering は新発明ではなく、Statecharts 的な古典的グラフ設計論を、LLM エージェント固有の契約——Goal, Budget, Evidence, 非決定性への規律——で再武装したものである。** 新しいのはグラフでもループでもなく、ノードが非決定的で自己申告する実行主体になったこと、それに対抗するための Evidence と variant の規律である。

# 全体の結論

1. **対立の解消**: ループ＝閉路と定義すれば、Loop Engineering は閉路1個の特殊ケースとなり、「置き換えか包含か」問題は消滅する。
2. **正確な分業**: SCC 分解により、Graph Engineering = SCC 内部の設計（Loop Engineering）＋凝縮 DAG の設計（従来ワークフロー）＋閉路の配置決定、と分解できる。DAG 型との違いは「凝縮すれば DAG に戻る規律の下で閉路を許すこと」。
3. **形式化の利得**: 「パイプライン vs 外側ループ」は制御エッジ部分グラフ上の閉路の有無、「停止性」はすべての閉路における variant（budget 減少エッジ）の存在、として構造的に判定可能になる。
4. **限界の自覚**: 動的トポロジーとラベルの意味論は位相だけでは扱えない。骨格より規律（Evidence, variant）が本体。
5. **歴史的位置づけ**: 新発明ではなく古典の再武装。バズワードの寿命とは独立に、閉路つきグラフ＋契約という設計語彙は残る。
