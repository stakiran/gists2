# a
ここはjjの一番「発想の転換」が必要なところなので、Gitの感覚と対比しながらゆっくり説明しますね。

## Gitの世界:コミットは「凍結された過去」

Gitでは、コミットとは「確定して凍結されたスナップショット」です。そして今編集中のファイル(作業ディレクトリ)は、まだバージョン管理の**外**にいます。`git add` して `git commit` するまで、Gitはあなたの変更を「正式なもの」として扱いません。だから作業中の状態は宙ぶらりんで、stashやaddで自分が面倒を見る必要があります。

## jjの世界:「下書きコミット」が常に1個ある

jjでは、リポジトリに**「現在の下書き」を表す特別なコミットが常に1個存在**します。それを指す記号が `@` です。あなたがファイルを編集するという行為は、jjの解釈では「`@` というコミットの中身を編集している」ことになります。

Gitユーザー向けに乱暴に言い換えると、こうです:

> jjは、**すべてのコマンドの直前に `git add -A && git commit --amend` を勝手に実行してくれるGit**のようなもの。あなたの作業は常に「下書きコミット(@)」に上書き保存され続けている。

## 「自動スナップショット」のタイミング

「自動」といっても、jjが常駐してファイルを監視しているわけではありません。動きはもっと単純です。

順を追って見てみましょう:

1. `jj new -m "ログイン機能"` を実行 → 空っぽの下書きコミットが作られ、`@` がそれを指す
2. エディタで `login.py` を編集して保存 → **この時点ではjjは何もしていない**。ただのディスク上のファイル変更
3. `jj st` と打つ → jjはコマンドの処理をする**前に、まずディスクを見て、`@` の中身を今のファイル状態に書き換える**。それから状態を表示する
4. さらに編集して `jj diff` と打つ → また同じ。まず `@` を最新化してから、diffを表示

つまり「jjコマンドを実行するたびにスナップショット」とは、**どのコマンドも最初の一手として『ディスクの現状を @ コミットに反映する』処理を挟む**、という意味です。`jj st` も `jj log` も `jj diff` も、全部この同期を先にやります。## よくある疑問への先回り

**「じゃあjjコマンドを何日も打たなかったら?」** → 何も起きません。ファイルはディスクにあるだけで、次にjjコマンドを打った瞬間にまとめて `@` に反映されます。監視デーモンがいるわけではないので、コマンドを打つまでの間に何かが失われることはありません。

**「addもcommitもしないなら、いつコミットが『確定』するの?」** → `jj new` を打った時です。`jj new` は「今の `@` はもう完成。これを履歴として置いて、その上に新しい空の下書きを作る」という操作です。Gitの `git commit` に一番近いのは、実はこの `jj new` です(コミットメッセージは `jj describe` でいつでも付けられます)。

**「勝手にコミットされたら、履歴が中途半端な状態で汚れない?」** → `@` は確定前の下書きなので、何度中身が変わっても「1個のコミットが上書きされ続けている」だけです。Gitで言えば、同じコミットに `--amend` し続けているイメージ。履歴に中途半端なコミットが積み上がることはありません。

**「ステージ(index)で『変更の一部だけコミット』してたのはどうするの?」** → jjでは順番が逆になります。まず全部 `@` に入り、あとから `jj split` で「この部分だけ別コミットに分ける」と切り出します。Gitが「入れるものを事前に選ぶ」方式なら、jjは「全部入れてから後で切り分ける」方式です。結果は同じことができて、しかもやり直しが効きます。

一言でまとめると:**Gitでは「作業中の変更」と「コミット」は別世界の住人で、add/commitという儀式で橋渡しする。jjでは作業中の変更が最初からコミット(@)という形で履歴グラフの中に住んでいて、儀式が要らない**——これが「ステージングエリアがない」の意味です。
