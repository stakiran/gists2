# MEA ループ整理 — LongHorizon-Harness の設計思想

長時間(long-horizon)エージェントのためのハーネス設計パターン **Manage-Execute-Audit (MEA) ループ** の整理。

- 論文: [LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks](https://arxiv.org/abs/2608.01964) (Alibaba DreamX Team, 2026-08)
- 実装: https://github.com/AMAP-ML/LongHorizon-Harness

## 1. 解こうとしている問題

既存のエージェントハーネス(Claude Code、Codex CLI 等)は、**タスク実行・タスク状態・完了判定を同じ膨張し続けるコンテキストの中に抱える**。これが長時間タスクで 3 つの失敗モードを生む。

| 失敗モード | 内容 |
|---|---|
| エラーの複利と目標ドリフト | 初期の誤りがトラジェクトリに沿って蓄積し、後続の判断を歪め、元の目標から逸れていく |
| コンテキスト腐敗 (context rot) | 履歴が伸びるほど関連情報の検索・利用が困難になり、使用率が臨界を超えると性能が急落 |
| タスク状態の喪失 | 要件・完了済み行動・成果物・発見事実という「今どこにいるか」を保持・更新し続けられない |

構造的な欠陥は 2 つ:

1. **実行と状態管理が同一コンテキストに同居** — 履歴が伸びるほど状態が追跡困難になる
2. **実行と完了判定が結合** — エージェントの誤った自己評価がそのまま状態に記録され、後続判断の前提として伝播する

エージェントが「完了しました」と言いつつ実際は未完了、という現象はこの構造の帰結であり、モデルを強くするだけでは消えない。

## 2. 発想の転換:長時間実行 = タスク状態管理問題

MEA の核心は再定式化にある。

> 長時間タスクの継続性は「実行の記憶(会話履歴)」ではなく「検証済み状態(台帳)」が担うべき

- タスク状態を**実行の外側**に明示的なレコードとして保持する
- 状態は**環境から独立に検証された事実**によってのみ更新される
- 各サブタスクは現在の状態と元の目標から導出される
- ラウンドをまたいで生き残るのはタスク状態と監査レポートのみ。実行の生履歴は毎回破棄

比喩: 工事現場の継続性を保証するのは前任作業員の記憶ではなく、**図面と検収記録**。作業員は交代してよい。むしろ交代させることに価値がある。

## 3. 三つの役割

3 役とも同一のバックボーンモデル・バックエンド(Claude Code 等)のインスタンス。違いは**権限・ツール・入力・予算**のみ。

### Manager — 台帳と計画を握るが、環境に触れない

- タスク状態を所有し、次のサブタスク契約(目標・受入基準・境界制約・関連する過去の監査レポート)を構築する
- **環境への直接インターフェースを持たない**。画面も見られず、コマンドも打てない。判断材料は監査人が記録した証拠のみ
- 制御判断: `execute` / `done` / `blocked` / `ask`(ユーザーへの確認)

### Executor — 変更できるが、記録を確定できない

- 環境を意図的に変更できる唯一の役割
- **毎ラウンド、フレッシュな予算制限つきコンテキストで起動**。受け取るのは元タスク・現在の状態・契約・契約が参照する監査レポートのみ。前ラウンドの生履歴は受け取らない
- GUI Executor(スクリーンショット・クリック等)と CLI Executor(シェル・ファイル編集等)に能力が分離され、契約に応じて Manager がルーティング
- エピソード終了時、生トラジェクトリと内部推論は**破棄**され、実行レポートのみが監査に回る
- 実行レポートは**未検証の自己申告**であり、それだけではタスク状態を completed にできない

### Auditor — 確認できるが、変更も計画もできない

- **read-only 権限**で環境を独立に検査する「調査員」。LLM-as-a-judge のエージェント版だが、判定だけでなく自ら環境を調べて証拠を集める
- Executor の生履歴・内部推論は受け取らない(実行時の「つもり」に汚染されないため)。実行レポートはファイルの在り処を探すヒント程度に使い、**結論は環境から直接得た証拠でのみ支持する**
- 出力: 完了判定(complete / incomplete / blocked)+ 整合性判定(clean / suspect / violation)+ 検証済み事実と証拠

### 相互牽制(三権分立)

| 役割 | できること | できないこと |
|---|---|---|
| Manager | 記録・計画 | 環境に触れる |
| Executor | 環境の変更 | 記録の確定 |
| Auditor | 環境の確認 | 環境の変更・計画 |

どの一役も単独では「やった事にする」ことができない。台帳の信頼性はこの牽制構造から生まれる。

## 4. 「状態」の二層構造

**環境状態 (e)**: ファイルシステム・プロセス・アプリ画面など、コンピュータそのものの状態。Executor だけが意図的に変更でき、Auditor は読むだけ。

**タスク状態 (S)**: MEA が管理する本体。環境のコピーではなく、構造化レコードの集合。

| レコード種別 | 内容 |
|---|---|
| requirement | 元タスクから導かれた目標・制約 |
| artifact | 実行中に作成・変更された成果物 |
| fact | 後続ラウンドが必要とする環境情報(「このダイアログは応答しない」等の失敗記録も含む) |

- 各レコードは `completed` / `pending` / `blocked` / `untrusted` のステータスと、それを支持する監査証拠への参照を持つ
- **最重要ルール**: Executor の主張は直接状態を変更できない。レコードが completed になるのは**クリーンな監査証拠に支持されたときだけ**

つまり台帳とは「Executor が出した主張を、**Auditor が環境で検証し**、その証拠に基づいて **Manager がまとめた**もの」。

## 5. Auditor の read-only 執行の仕組み

- 禁止スコープは「タスク関連の環境状態」の変更。**観察のための表示変更は許可**(メニューを開く、スクロール、cat 等の「見るために触る」行為は OK)
- 執行はハードなサンドボックス強制ではなく、**証拠の無効化**による。ハーネスがワークスペースと成果物を監査中監視し、変更を検知したら integrity violation として記録 → そのレポートは completed の根拠として使えなくなる → Manager は該当レコードを untrusted 化して再実行を計画
- read-only にこだわる理由:
  1. **循環論法の防止** — Auditor が環境を直せると「Auditor が完成させた状態の検証」になり、証拠としての意味が壊れる(レビュアーが自分でコードを直してはいけないのと同じ)
  2. **証拠保全** — 「修理前の壊れた状態」自体が提出物の一部であるタスクでは、検証行為が状態を汚すと回復不能
- グレーゾーンは残る(テスト実行はビルド成果物を生む、GUI アプリは開くだけで状態が変わる等)。3 段階判定(clean / suspect / violation)はこの曖昧さの吸収装置。実装時はスナップショット上での監査や副作用ホワイトリスト化で補完するのが現実的

## 6. フレッシュコンテキストの意味

「長時間タスクなのに実行者は毎回記憶喪失」という逆説の解消。フレッシュとは「何も知らない」ことではなく、**キュレーションされた最小限を知る**こと。情報のボトルネックを意図的に作り、通過できるのは検証済み事実だけ。

解決するもの:

1. **失敗の記憶という呪い** — ベースラインは応答しないダイアログの失敗観察が履歴に埋まったまま 400 ステップ以上同じ操作をリトライした。MEA では失敗が fact として外部化され、次の Executor は未解決要件だけを受け取る(スコア 0.59 → 0.92)。**忘れることが回復の条件**
2. **自己正当化バイアスの遮断** — フレッシュな Executor には守るべき「過去の自分の判断」がない
3. **コンテキスト予算の使途最適化** — 完了済み作業の経緯を引きずらず、全コンテキストを現在のサブタスクに投じられる

コスト(無料ではない):

- 破棄される生履歴には fact 化されなかった**暗黙知**(環境の手触り)も含まれ、再探索コストが発生する
- Auditor はトークンの 19〜38% を占める主要な追加投資
- 経済性はモデル能力に依存: 弱いモデル(Qwen)は再実行ラウンドが増え消費 3 倍、強いモデル(Opus)はむしろ 16.5M → 11.1M に**減少**(少ないラウンドで契約を満たせるため)
- 短いタスク・個別能力(視覚認識、数学等)がボトルネックのタスクでは効果が薄く、僅かに悪化するカテゴリもある

## 7. 主要な結果

| ベンチマーク | ベースライン → MEA | モデル |
|---|---|---|
| WeaveBench PassRate | 51.8% → 80.7% | Qwen 3.7-Plus |
| Terminal-Bench 2.1 | 69.7% → 77.2% | Qwen 3.7-Plus |
| OSWorld 2.0 (binary) | 2.8% → 8.3% | Qwen 3.7-Plus |
| OSWorld 2.0 サブセット | 20.6% → 35.3% | Claude Opus 4.7 |

特筆点: MEA 付き Qwen(平均 0.733)が素の Claude Code + Opus(0.680)を上回った。**エージェント能力はモデル単体ではなく「モデル × ハーネス」のシステム特性**。

## 8. 実務への写像(Claude Code 等での運用)

- **compaction を待たず、区切りで意図的にセッションを切る**。切る前に外部ファイルへ書き出すのは「作業ログの要約」ではなく「**検証済み事実 + 未解決要件**」
- **サブエージェントへの委譲**は自然な fresh-context executor。渡すのは全履歴ではなく契約(目標・受入基準・境界制約・関連事実)。返ってきた報告は**検証してから**親の状態に反映する
- **TODO リスト / PLAN.md の運用**で問うべきは「そのリストを実行エージェント自身が更新するか、独立検証を経てのみ更新されるか」。自己申告で ✅ を付ける構成は、論文が名指しで批判した構造的欠陥そのもの
- 一つのセッションで「実行しながら進捗管理・完了判定もさせる」構成を避け、実行 / 検証 / 状態管理を分離する

## 9. 一言まとめ

> フレッシュコンテキストは長時間性の否定ではなく実現手段。「長時間」を担うレイヤー(Manager + タスク状態)と「今この瞬間」を担うレイヤー(Executor)を分離し、後者を毎回使い捨てることで、前者が腐敗せずに長く生きられる。**エージェントの寿命をコンテキストウィンドウの寿命から切り離した**設計。
