はい、記事の言葉で言えば「dynamic workflow」の設計・監視・修正がエンジニアリングの本体で、まさにループエンジニアリングです。2つの質問を順に答えます。

## ループの終了条件:一部は明示、一部は推測が必要

明示されているものから。まず記事にはループの原型が擬似コードで示されていて、`while ((task = todoList.pop()))` という形、つまり**タスクキューが空になったら終わる**構造です。そして各ワークフローのキューは外部の検証機構が機械的に生成するので、終了条件は「検証機構がもう失敗を出さない」と同値になります。フェーズごとに整理すると:

| フェーズ | キューの生成元 | 終了条件(ゴール) |
|---|---|---|
| 移植 | 1,448 の .zig ファイル一覧 | 全ファイルに対応する .rs が存在 |
| コンパイル修正 | crate ごとの `cargo check` 出力(約16,000件) | `cargo check` がエラーゼロ |
| スモークテスト | サブコマンドごとの失敗スタックトレース | 各サブコマンドが起動・動作 |
| ローカルテスト | 失敗テストのスタックトレース | 対象テストが緑 |
| CI | 各プラットフォームの CI テスト失敗。「テスト失敗がなくなるまでループした」と明示されています | 全プラットフォームで 100% パス |

つまり終了条件は「Claudeが完了したと判断する」ではなく、**コンテキスト外のオラクル(コンパイラ/テスト/CI)が緑を返すこと**。これが5つ目の戦略(検証層の独立)と直結しています。

そして最後の一段だけは人間がゲートです。CI が全プラットフォームで緑になった後、テストが実際に実行されておりスキップされていないことを著者が手動確認し、ローカルでコマンドを試してからマージボタンを押した。さらに「マージ=リリースではない。前進をコミットする確信はあったが、リリースする確信はまだなかった」と、確信レベルを段階分けしています。

**明示されていない部分(推測)**:収束しない場合の停止条件——同じテストで無限に振動する、flaky テストに騙される、リトライ上限など——への言及はありません。記事の運用から推測すると、これは自動化されておらず、「11日間の大半、ワークフローを監視し、出力を手で読み、問題があればループを編集するよう Claude にプロンプトした」という**人間の監視がwatchdog(タイムアウト兼発散検知)を兼ねていた**と考えるのが自然です。「スタブ化で誤魔化す」問題を人間が発見してルール追加で止めた事例がまさにそれで、ループが「間違ったゴールに収束する」リスクは機械的な終了条件では防げず、人間がゴール条件自体を修正していた。ここが自動化されていない最大の穴であり、人間が張り付いた理由でもあると思います。

## エージェントの構成と数

記事から再構成できるトポロジーは3階層です。

**実行基盤**: Claude Code の dynamic workflows 機能で、64 の Claude を 11 日間走らせ続けた。これがなければ自前のハーネスを書く必要があったとのこと。約50個のワークフローを11日間で順次・並行に実行しています。

**並列の単位**: ピーク時は 4 つのワークフローを同時実行し、それぞれが独立した git worktree を持ち、各ワークフローに 16 の Claude、合計で常時約 64 Claude。worktree による物理分離は、序盤の `git stash` 衝突事故への対策です。

**最小ユニット(1ループ=4体)**: コンパイルエラー修正フェーズの記述が最も具体的で、約16,000のエラーを crate ごとにグループ化してファイルに書き出し、64 の Claude に分配——4 worktree × 16 ループ、各ループは「1 体が修正、2 体がレビュー、1 体が適用」。つまり:

```
1ループ = implementer ×1 + adversarial reviewer ×2 + fixer ×1(計4体)
1 worktree = 4ループ = 16体
全体 = 4 worktree = 64体
```

役割は厳格に分離されていて、実装者はレビューせず、レビュアーは実装しない。レビュアーは別コンテキストウィンドウで、渡されるのは diff のみ(実装者の推論は見せない)、「コードは間違っていると仮定せよ」と指示される。

数字の裏付けとして、ピーク時で毎分約1,300行、1時間で最大695コミット、11日間で6,502コミットという速度が出ています。

まとめると、あなたの言う「ループエンジニアリング」の実態は——**終了条件を外部オラクル(キュー空+チェッカー緑)に固定した4体ユニットのループを16並列×4シャードで回し、機械化できない終了条件(=正しいものに収束しているか)だけを人間が監視する**——という分業だった、と読めます。
