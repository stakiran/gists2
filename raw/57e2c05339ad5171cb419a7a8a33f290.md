# Agent Skillsの自動最適化は「訓練ループ」なのか — 検証信号を中心に考え直す

LayerXの記事「[Agent Skills自動最適化の研究、中身はほぼ深層学習の訓練ループだった](https://zenn.dev/)」(2026/07/08) を出発点にした議論のまとめ。記事の主張を確認するところから始めて、アナロジーの妥当性、検証信号の本質、そして実務での打ち手まで掘り下げた。

## 前提: 記事の主張

2026年上半期に出たスキル自動最適化の研究群 (Trace2Skill, MIND-Skill, CoEvoSkills/EvoSkills, OpenSkill, SkillOpt, SkillGrad) は、いずれも深層学習の訓練ループの部品をテキストに置き換えた形をしている、というのが記事の整理。

| 深層学習 | スキル最適化 |
|---|---|
| 学習パラメータ (重み) | SKILL.md (スキル文書) |
| 訓練データ | エージェントの実行トラジェクトリ |
| 損失関数 | 検証信号 |
| 勾配 | テキスト編集の提案 |
| 学習率 | 1回に許す編集量の上限 |
| 過学習の監視 | 検証タスクでの採否判定 |

これは記事の誇張ではなく、SkillOpt (arXiv:2605.23904) など論文自身が明示的に使っているアナロジー。ただし論文はすべて未査読プレプリントで、数値は自己報告。

## 論点1: このアナロジーは妥当か

**違和感は正しい。アナロジーは深層学習の本質をほぼ全部欠いている。**

勾配降下法が機能するのは、損失が微分可能な数式で、勾配が「損失が最も減る方向」を数学的に厳密に指すから。収束理論があり、大量データによる統計的な平均化の裏付けがある。一方スキル最適化の「勾配」はLLMが書いた編集提案にすぎず、改善方向を指す保証はない。テキスト空間には滑らかさもなく、1行の編集で挙動が激変しうる。数学的実体を借りずに語彙だけ借りている。

実態に近い名前は勾配降下ではなく**山登り法・進化的探索**。変異 (編集) を提案し、良くなったときだけ採用する。勾配という方向情報がないからこそ、試して選別するしかない、深層学習以前からある原始的な最適化。

ただし「測って、変えて、また測る」というループ自体は深層学習の発明ではない。科学の実験、PDCA、A/Bテスト、生物の進化——フィードバックで改善するものはすべてこの形。深層学習はこの一般構造の、数学的に極端に効率化された一例にすぎない。

**重要なのは、形は同じでも力学が逆転していること。** 深層学習ではループの中で最も安く確実な部品が採点 (損失計算) だった。Agentic Engineeringでは、採点こそが最も高く、最もあてにならない部品になっている。「同じ構造」への違和感の正体は、たぶんこの逆転。

## 論点2: そもそも反復ループは必須か

**必須ではない。反復は深層学習の本質ではなく、パラメータが不透明であることの帰結。**

深層学習が盲目的な試行錯誤をせざるを得ないのは、何億個の数値の羅列を誰も解釈できないから。「どこをどう直せばいいか」を理屈で導けないので、試して測るしかない。

ところがスキルはテキストで、読める。パラメータが可読だと、重み空間では原理的に不可能だった改善経路が開く。

1. **演繹による改善** — 橋の設計者は橋を100本壊して学ばない。理論から計算して直す。エージェントも「この手順は並列実行時に競合するはずだ」と実行せずに推論して直せる。
2. **教示と転移** — 他所で書かれたSKILL.mdをコピーすれば改善は一瞬。人間が教科書で一足飛びに学ぶのと同じ、文化を持つ存在に固有の経路。
3. **一回の観察からの模倣** — 上手い実行例を1本見て写す。LLMの強力な事前知識が、統計的平均化なしの1例からの一般化を可能にする。

深層学習が進化 (盲目的変異＋選択) なら、エージェントは工学 (理解に基づく設計) ができる。

**ただし、検証だけは消せない。** 演繹が機能するのは世界モデルが正しいときだけで、LLMの世界モデルは正しいときと自信満々に間違っているときの区別が外からつかない。SWE-Skills-Benchで測定なしに書かれたスキル49本中39本が効果ゼロだったのは、「推論だけによる改善」が現実によく外れる証拠。自己修正 (self-correction) 研究でも、外部検証なしの自己反省は改善しないか悪化するという報告が繰り返されている。

結論: **探索は反復である必要はないが、検証は認識論の問題なので残る。** 検証は学習の方法ではなく、自分の世界モデルが現実とズレていないかを確かめる唯一の手段。

## 論点3: 検証信号は2つの層に分かれる

**第一層: 良し悪しが世界の側で決まるタスク。** コードがテストを通るか、計算結果が参照値と一致するか。検証が必要な理由は「LLMの世界モデルは現実とズレうるから」であり、検証は機械的・自動的にできる。CoEvoSkillsやSkillOptが成果を出せたのは、この層 (正解のあるベンチマーク) で戦っていたから。

**第二層: 良し悪しの基準そのものが人間の中にしかないタスク。** ブログが面白いか、提案がクライアントに刺さるか。検証器を作ろうとすると、必ず人間の判断を代理指標 (proxy) に置き換えることになる。

ここに古典的な罠がある。**Goodhartの法則** — 指標が目標になった瞬間、良い指標であることをやめる。代理指標に向かって最適化ループを回すと、システムは「面白い文章」ではなく「ルールを満たす文章」に向かって進化し、指標と真の目標のズレをループの力で増幅する。OpenSkillで反復を重ねるほど性能が劣化した現象 (3回ピーク82.7% → 10回で78.0%、検証器Precision約57%) は、歪んだ指標への忠実な最適化の結果と読める。ループが強力であるほど、指標の歪みは致命的になる。

第二層での人間の役割は「採点の自動化が間に合っていないから残っている」のではない。**人間が基準の供給源 (ground truth) そのもの**であり、その基準は固定できない。「面白い」の中身は読者や時代で動くので、ルーブリックに書き下して自動化した瞬間から古び始める。代理指標は常にドリフトし、人間が定期的に較正し直すしかない。

## 論点4: 実務での打ち手

2つの打ち手は、同じ一つの原則の両面。**「検証信号のコストを下げ、1回の検証から引き出す情報量を上げろ」。**

### 打ち手1: 第一層をなるべく増やす

限度はあるが、良し悪しが機械的に判定できる領域を広げる。code as agent harness的な発想や、システムを決定的 (deterministic) にせよという従来からの原則はここに接続する。第一層に落とせた部分は、検証が無料になり、自動ループに乗る。

### 打ち手2: 第二層はアジャイルに回す

SDD的なウォーターフォールは、人間の中の基準を**成果物を見る前に全部テキストに直列化できる**という仮定に立っているが、第二層の基準は宣言的に取り出せない。現物を見て初めて「これじゃない」と分かる形でしか現れない。好みは述べられるものではなく、暴かれるもの (revealed preference)。「仕様どおりに作っても納得しない」のは皮肉ではなく構造的必然で、完成品を見た瞬間こそが、基準が初めて現実に問い合わせられた瞬間だから。ならばその問い合わせを最後に一度だけやるのは最悪の設計で、なるべく早く安く何度もやるべき。

アジャイルの教義として昔から言われてきたことだが、「人間 = 較正の必要なground truth」と置くと、信仰ではなく導出になる。

AIはこのループの経済を実際に変えている。

- 従来のスプリントが2週間だったのは、人間が「見せられるもの」を作るのにそれだけかかったから。反復のバッチサイズは製造コストで決まっていた。製造がほぼ無料になれば、バッチサイズは限界まで小さくできる。
- フルスクラッチも安いので、「積み上げた資産に縛られて方向転換できない」という増分開発の弱点も薄れる。捨てる前提で作って見せる、が成立する。
- 人間は絶対評価が下手で比較評価が得意 (LLM-as-a-judge研究でも同じ結論)。1案を磨くより、方向性の違う2〜3案を並べて選ばせる方が、1回の人間の検証から取れる情報量が多い。

### 残る課題: エンタープライズ規模

事例はまだ聞かない。難しさの正体は、規模が上がると壊れるのがコード生成ではなく検証信号の方であること。ステークホルダーが増えると「人間の中の基準」が一人の中ではなく委員会の中にあり、相互に矛盾する。ground truthが政治になる。

現実的な路線はおそらく「システムを第一層の境界で切る」こと。モジュール間の契約やテストを決定的な検証に落とし、人間の判断が要る第二層をUIやドメインロジックの表面に押し出し、そこだけ高速ループを回す。打ち手1と2は、規模が上がると「どこで第一層を張り、どこに第二層を残すか」という**アーキテクチャ設計の問題**に変わる。マイクロサービスやDDDの境界づけは、人間の検証コストの配置問題として再解釈できる。

## まとめ

- スキル自動最適化 ≈ 訓練ループというアナロジーは、語彙は借りているが数学的実体はなく、実態は評価が最大のボトルネックになった進化的探索。
- 反復ループは本質ではない。スキルが可読である以上、演繹・転移・模倣という別経路がある。ただし検証だけは認識論的に消せない。
- 検証信号は「世界が決める第一層」と「人間の中にしかない第二層」に分かれ、第二層をループに入れるとGoodhartの罠が待つ。
- 実務の原則は一つ: 検証のコストを下げ、1回の検証の情報量を上げる。第一層を増やし、第二層は早く小さく見せて比較で選ばせる。
- 規模が上がると、これは開発プロセスの問題からアーキテクチャの問題 (検証コストの配置問題) に変わる。
