## TypeSafe AI / Jev とは

Jev は TypeSafe AI のモデルで、生成テキストではなく「型付きの確率的判定」を返す。プログラムの状態と型付きの質問を送ると、1回の並列パスで 70〜500ms のうちに全部に答える。2026年9月15日に DCVC 主導の 4,000 万ドル調達とともに公開され、開発者は OpenAI で RLHF と InstructGPT を共同発明した Diogo Almeida。

ポイントは以下です。

- **非自己回帰の「System One モデル」**: LLM は人間が読むテキストを作るよう設計されているため、コードが消費する判定をさせようとするとミスマッチが起きる。Jev は state に対する型付き質問を評価し、構造化結果を直接返す。テキスト生成もパースも不要で、コードが分岐・ソート・ルーティングに使える型付き値と確率分布が得られる。
- **3つのプリミティブ**: 1-of-N 選択(最大255択)、2〜10段階のスケール上の位置、yes/no の確率。ドキュメント上はそれぞれ Choice / Score / Noul と呼ばれています。
- **学習法 RLCD**: 新しいアーキテクチャ、並列サンプラー、そして Reinforcement Learning for Calibrated Decisions(RLCD)と呼ぶ学習法からなる新スタックで、System One タスクでは既存 LLM と同程度の知能を保ちつつ2桁速く効率的とされます。各判定には confidence 推定が付き、高ければ自動処理、低ければエスカレーションという使い方を想定しています。
- **速度・コスト**: デモでは Jev が 0.114 秒で応答したのに対し GPT-5.6 Terra は 8.566 秒。料金は入力 $0.042/MTok、出力は無料。名前は「ジェボンズのパラドックス」の Jevons に由来し、トークン効率が上がるほど消費が増えるという業界の賭けを反映しています。
- **位置づけ**: LLM の置き換えではなく、Jev が安価に分類・ルーティングし、コードで処理できるものは処理し、難しい少数をフロンティアモデルに回すカスケード構成が推奨されています。LangChain には TypeSafeClassifier として統合済みです。

## この gist が言っていること

作者(stakiran)が Jev を「コメント判定」(300件のコメントに8つの質問を投げて分類する)に実際に使い、そこから題材によらないエンジニア向けの教訓だけを抜き出したメモです。confidence の定義は公式ドキュメントを見ずにデータから推測している、と断っています。

要旨を一言でまとめると「**Jev は答えを出す機械ではなく、確率つきの特徴量を返す型付き関数として扱え。判断ロジックは自分のコードに書け**」です。12項目の中身はこう整理できます。

**Jev の出力の扱い方**
- 返り値をそのまま最終判断にせず、複数の質問の結果をコードで AND/NOT/閾値で組み合わせる。1つの質問が外れても他で救える。
- 閾値は質問ごとに校正する。Noul の確率分布は質問によって中央値が 0.05〜0.40 と大きく違い、0.5 に普遍的な意味はない。「高い帯は自動採用・中間は人が見る・低い帯は捨てる」の3分割が実用的。
- Score は各段階の期待値なので、確率が両端に割れても真ん中の値になる。値だけでなく confidence と端の確率も保存し、割れていること自体を(両義的な入力や皮肉の検出に)情報として使う。
- confidence は「迷い」の指標であって「正しさ」の指標ではない。低 confidence に誤りが集まるので見直しの優先度には使えるが、情報不足による系統的誤りは confidence 0.97 でも起きる。

**質問の設計**
- 1つの質問に1つの軸だけを持たせる。instructions に「ただし〜は除く」と書いても効きが弱いので、除外条件は別の質問にしてコードで NOT を取る。
- criteria(特に「紛らわしいが該当しないもの」を false 側に)書く方が長文の instructions より効く。
- Choice には `other` のような逃げ道を用意し、次点の選択肢と確率も保存する。ただし `other` が最多になったら選択肢設計の見直しサイン。本質的に複数ラベルなら Choice でなく Noul を並べる。
- examples は極めて強く効く(入れた文言と同じ行は confidence 0.99〜1.0 になる)ので、チューニング用と検証用のデータを分けないと改善幅を過大評価する。

**state の作り方**
- 「この state だけを見せられた人間が正しく判断できるか」が基準。判定対象と文脈は別キーで渡し、手元のメタデータは惜しまず渡し、内輪の用語は premise に用語集として書く。

**運用の型**
- 質問文をコードとして版管理し、版名を出力ファイルに入れる。ラベルでなく生の確率を全部保存して後から切り直せるようにする。複数質問は1回の呼び出しにまとめ、並列で回し、失敗は行単位で記録して止めない。50件→300件→全件と段階的に回す。
- 既存の(不正確でもよい)ラベルと Jev の判定を突き合わせ、食い違いだけを見直しキューにすると、全件読まずに系統的誤りが見つかる。

**判定がおかしいときの疑う順番**
state の情報不足 → 質問が複数軸を持っていないか → criteria に紛らわしいケースがあるか → ドメイン用語の誤読 → 閾値が分布に合っているか。モデルを疑うのは最後で、今回見つかった誤りはほぼ全部この5つで説明がついた、としています。

要するに、この gist は Jev の公式の「速い・安い・構造化」という宣伝を、実運用での落とし穴(閾値・confidence の誤解、質問設計、データリーク、デバッグ手順)に翻訳した「使う側のプレイブック」です。TypeSafe が想定するカスケード構成のうち、「Jev の出力をどうコードで受けるか」の部分を具体化したものと読めます。
