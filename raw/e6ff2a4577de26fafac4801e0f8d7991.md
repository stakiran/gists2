# ARTEX アーキテクチャ解説ノート

LLM マルチエージェントによる自律型ペネトレーションテスト・フレームワーク「ARTEX」の設計を、
エージェント設計の学習教材として整理したもの。攻撃用途そのものではなく、
「どうやって LLM にマルチステップの自律探索を安定して回させるか」という設計パターンに焦点を当てる。

> **出典と確度について**
> 本ノートは公開 README とアーキテクチャ図から読み取れる範囲をまとめたもの。
> 本家リポジトリ（`Autumn-27/ARTEX`）は 2026-10 時点で下架されており、
> 記述はローカライズ版フォーク（例: `jiwoochris/artex-global`）の README に基づく。
> テーブル名など実装詳細レベルは README に明示がなく、構造からの推定を含む。
> その箇所は本文中で「推定」と明記した。確定したい場合はフォークの `db` / `agent` を参照。

## 0. 前提：ARTEX とは何か

- LLM に接続し、自動で脆弱性を発見して侵入テストを実行するマルチエージェント・システム。
- 構成は Go バックエンド + Next.js フロントエンド + PostgreSQL。
  単一の Go バイナリにフロントを `go:embed` で埋め込む。
- エージェント能力は `norma` という SDK が提供。
- ライセンスは AGPL-3.0。

### 経緯（なぜ「公開停止」の話題になっているか）

- 2026 年 9〜10 月、韓国の複数金融機関で相次いだデータ漏えい事件で、
  攻撃者が ARTEX を使用していたことが判明（CrowdStrike が報告。攻撃者サーバーに
  ツール設定ファイルや Claude Code のチャット履歴が残存していたとされる）。
- これを受け、開発者 Autumn-27 は 2026-10-08 にクローズドソース化・更新停止を表明。
  本家 GitHub リポジトリと Docker Hub イメージ（`autumn27/artex`）は下架。
- ただし AGPL-3.0 のため、公開済みコードは他者がバックアップ・再配布可能。
  多言語ローカライズ版フォーク（`artex-global`, `artex-ko` 系）や
  中国語の二次開発版（`artex-ymh`）などが流通している。

## 1. なぜ LLM の安全機構をすり抜けられたのか

LLM の安全機構は年々賢くなっているが、ARTEX が機能してしまうのは
「ガードレールを突破した」のではなく「ガードレールが発火しにくい形に問題を分解している」ため。

1. **タスクが細切れで、個々は悪意に見えない**
   全体像（偵察→侵入→データ持ち出し）はシステム側のグラフ/オーケストレーションが保持し、
   LLM の各呼び出しには「このレスポンスから認証関連フィールドを抽出せよ」のような
   地味でテクニカルな断片だけが渡る。安全機構は「今見えているプロンプト」に対して発火するため、
   正当なセキュリティ作業と区別がつかない。

2. **正当なペンテストと悪用が技術的に見分けられない**
   ペネトレーションテスト自体は合法。対象が自分の資産か・許可があるかを
   モデルは検証できず、悪意は実行文脈にあってプロンプトのテキストには現れない。

3. **モデルを差し替えられる**
   LLM プロバイダは OpenAI 互換エンドポイントなら何でも接続可能。
   フロントフロンティアモデルが拒否しても、ガードレールの緩いモデルに差し替えれば
   同じオーケストレーションが回る。システムの自律性はモデルに依存しない。

> **教訓**：単発プロンプト単位の拒否では防ぎきれない。
> オーケストレーション層が悪意を保持し、LLM には正当に見える断片だけを渡す構造が弱点。
> 対策の方向性は「セッション全体・会話全体の累積的な意図」を見る安全設計へ。

## 2. システム全体構成

```
Frontend (Next.js, go:embed で単一バイナリに埋め込み)
   └─ Dashboard / Tasks / Assets / Coverage graph / Traffic / Workspace / Settings
server (Go net/http)
   └─ REST /api/*, JWT 認証, SSE / engine スケジューリングループ / Manager（ライフサイクル）
agent (norma SDK)
   └─ goals / planner / worker / mainagent
db (PostgreSQL)
   └─ デュアルグラフ（アセットグラフ + 探索グラフ）
支援系
   └─ 記録プロキシ(MITM) / guard・intercept(承認ゲート) / enrich(非同期DNS/HTTP) / MCP・skills・memory・report
```

### エージェント 4 役

| 役割 | 責務 |
|------|------|
| **goals** | 目標分解とスコープ抽出 |
| **planner** | 唯一の intent 生産者。状態を読み、次の方向を判断 |
| **worker** | executor（×N）。単一 intent を実ツールで実行 |
| **mainagent** | human-in-the-loop（人が介入） |

## 3. 設計の肝① デュアルグラフ

「対象が何か」と「どこまで調べたか」を **2 つの独立したグラフに分離**する。

### アセットグラフ（全タスク共有・真実の源）
- ノード: `root_domain / subdomain / ip / service / app / endpoint`
- 対象の構造そのもの。親子関係や重複排除キーは**プログラム側が計算**し、
  エージェントは生の情報だけを投げる（＝グラフ整合性を LLM に任せない）。

### 探索グラフ（タスクごとに独立）
- ノード: `goal / intent / fact / finding / hint`
- エッジ: `spawns / derived_from / yields / proves`
- 「思考と進捗の系譜」を表す。

### 連結：anchor
- `exploration_anchors(node_id, asset_id)` で intent / fact / finding を具体的アセットに紐づける。
- 「この探索方向はどのアセットを攻めていたか」「このアセットをどの intent がテストし何が分かったか」が
  双方向に辿れる。

---

## 4. 探索グラフのノード型（思考の単位）

```
goal  ──spawns──▶  intent  ──yields──▶  fact
                     ▲                    │
                     └──derived_from──────┘

intent ──proves──▶ finding
```

| ノード | 意味 | 状態 |
|--------|------|------|
| **goal** | タスクの最上位目標。`prove_goal` までループが回る | — |
| **intent** | 「次にこれを調べる/やる」という1行動の指示。planner が唯一生産、worker が1つ実行 | これからやる（結果未定） |
| **fact** | intent を実行して**判明した事実・観察**（例: 「ポート8080が開」「未エスケープ」） | 確定（観察済み） |
| **finding** | fact のうち**確認された脆弱性・成果**（例: 「IDOR あり」「認証情報取得」）。レポートに載る | 成果 |
| **hint** | human-in-the-loop で人間が注入する手がかり | — |

### intent と fact の対比（一言で）
- **intent = 問い／行動**（これからやる、結果未定）
- **fact = 答え／観察**（やった結果わかった、確定）

この `intent → fact → intent → fact …` の連鎖がループを駆動する。

### fact と finding を分ける理由
観察された事実が全部成果なわけではない（「ポートが開いてる」は事実だが脆弱性ではない）。
無数の fact の中から、攻撃チェーンを前進させる/報告に値するものだけが finding に昇格する。

### 具体例
```
intent: 「このパラメータに SQLi を試せ」（未定）
  ↓ worker 実行
fact:   「' を入れると DB エラーが返る」（確定）
  ↓ derived_from として planner が次を考える
intent: 「UNION SELECT で列数を特定せよ」（未定）
  ↓ worker 実行
fact:   「列数は 8」（確定）
  ↓ …最終的に
finding:「このエンドポイントに SQL インジェクション脆弱性あり」（成果）
```

## 5. 設計の肝② イベント駆動の閉ループ

engine は「グラフが変化したら planner を起こす」event-driven な閉ループ。

```
1. グラフ変化（debounce 付き）           → planner を wake
2. planner が状態を読み、frontier キューに  → 0〜N 個の intent を割当
   （★ほとんどの wake は 0 個。新しい方向がなければ終わる）
3. worker が claimNext で intent を1つ受領  → asset_ids から初期情報取得
4. worker が実ツール(Kali/Bash/HTTP)を実行  → 記録プロキシ経由
5. 結果を fact/asset/finding としてグラフへ書込
6. その書込が再びグラフ変化を起こす         → planner 再 wake（ループ継続）
```

- `prove_goal`（目標の証明）まで回る。
- **planner = 唯一の意図の生産者**、**worker = 単一 intent の実行者**、という役割分離が核。

---

## 6. 設計の肝③ ワーカー間のプロセスレベル情報交換

深い探索では、価値ある観察（特定のエラー、レスポンス片、隠しパラメータ）が
正式な fact として記録されないまま worker の**実行プロセス中**に出てくる。これを再利用する仕組み。

- `search_all_worker_traces(q)` — 他ワーカーの実行過程をキーワード検索（自分の intent は自動除外）
- `list_worker_traces` / `get_worker_trace(intent_id, step_ids)` — 特定ワーカーの特定ステップの中身を取得

探索グラフにまだ fact がなくても、後続ワーカーが別ワーカーの過程を再利用できる。
各ワーカーの境界（1つの intent だけ実行）は保ったまま、「実行過程」レベルで情報だけが流れる。

## 7. 設計の肝④ planner の永続 todolist ★最重要

実際の攻撃チェーンは「注入点→認証情報→横展開→権限昇格」のような**互いに依存する順序付きステップ**。
一斉に並列ディスパッチすると絡まる（認証情報がないのに横展開を始める等）。

### 「ステートレスなのに永続 todolist」の正体

一見矛盾するが、**ステートレスなのは planner の LLM セッションであって、
todolist は LLM の外（DB）に置いてある**。

- **状態の本体 = DB（グラフ）**：永続。wake をまたいでも残る。
  todolist は探索グラフ側の永続状態の一部として DB にあると読むのが自然（※テーブル名は README 未記載、推定）。
- **LLM セッション = 揮発**：各 wake は新しい LLM セッション。前回の思考はコンテキストに残らない。
  毎回まっさらな状態で起こされ、DB から現在状態を読み直して「今やるべき1手」だけ決める。

### 1 サイクルの動作

```
1. wake        グラフ変化で planner 起動。LLM セッションは新規・空
2. 読み込み     DB から現在状態を読む（graph_overview プリフェッチ + カバレッジ/スコープ）
               ★永続 todolist もここで読み込む（前回までの計画と各ステップの done/in-progress/前提待ち）
3. 判断        前提が済み・依存先 fact が存在するステップを1つ選び、intent を割当
               新しい方向がなければ 0 個割当（何もせず終わる）
4. 更新        todolist を更新（fact 充足ステップを完了にマーク）→ DB に書き戻す
5. 破棄        LLM セッション終了。planner は眠る
6. 次のグラフ変化で 2 から繰り返し
```

計画の連続性を担保するのは **LLM の記憶ではなく、DB に書かれた todolist**。
LLM は毎回「DB の計画書を読み、次の1行だけ実行し、進捗を書き戻す作業員」に過ぎない。
計画書はテーブルに残り続けるので、セッションが毎回死んでも計画は死なない。

### 「一度だけ記録 → 1ステップずつ」

```
DB（永続・wake をまたいで残る）
┌──────────────────────────────────────┐
│ shared todolist                       │
│   1 注入点       [done]               │
│   2 認証情報取得  [in progress] ← 今    │
│   3 横展開       [前提待ち]           │
│   4 権限昇格     [前提待ち]           │
└──────────────────────────────────────┘
      ↑ 読む             ↓ 書き戻す
┌──────────────────────────────────────┐
│ planner LLM セッション（毎 wake 新規・揮発）│
│  round N: DB読む → ②に intent割当 →    │
│           todolist更新 → セッション破棄 │
└──────────────────────────────────────┘
      ↓ intent
   worker が②を実行 → fact 生成 → グラフ変化
      ↓
   planner 再 wake（round N+1）→ ①②done確認 → ③の前提満たされた → ③に割当…
```

- todolist に直列チェーンを**一度だけ丸ごと記録**。
- 実際に intent を割り当てるのは毎ラウンド**依存順で次の1ステップだけ**。
- 前ステップが fact を生んで初めて次ステップの前提が満たされ、次ラウンドで intent が振られる。

これにより「イベント駆動 + ステートレスセッション」という本来マルチステップが苦手な環境で、
重複なく・順序を崩さず直列チェーンを進められる。README が言う
「ARTEX が自律的に多段攻撃を完成させる核心」の中身がこれ。

## 8. 一般化できる設計パターン（学びどころ）

攻撃用途と無関係に応用が効く発想：

1. **状態を LLM に持たせず、外部ストアに持たせる。LLM は読み書きする純粋関数にする。**
   LLM を信頼できる記憶装置として使わず、毎回 DB を真実の源として読み直させる。
   長時間・多段タスクを安定して回す定石。

2. **「真実の状態」と「推論の系譜」を分離する**（デュアルグラフ）。
   整合性計算・重複排除はプログラム側、LLM は判断だけ。

3. **ステートレスなワーカー/プランナー + 永続 todolist で順序性を与える。**
   直列依存のあるタスクを、並列実行環境でも順序を崩さず進める。

> 裏返すと、これらはそのまま「どこがプログラムで、どこが LLM 判断か」の境界であり、
> 防御・検知側にとっては検知ポイント（記録プロキシの痕跡、enrich プローバーや
> norma SDK の User-Agent、探索スキーマが載る PostgreSQL 等）の地図にもなる。
