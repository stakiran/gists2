# a
そういうことです。そして「一手段」と言えたのが重要で、そこまで来ると選定の景色が変わります。憲法の条文は同じでも、**どの層で執行するか**に選択肢があって、執行力に強弱があるんです。

弱い順に並べると:

1. **プロンプト層**:「〜してはいけない」と書く。Bunの「git stash禁止」がこれ。安いが、執行力はモデルの従順さ頼み。実際Jarredはこれで済むものはこれで済ませています。
2. **ハーネス層**:Claude Codeのhooks/permission設定、Agent SDKのpermissionコールバック。ツール呼び出しをコードで許可・拒否できる。エージェントが「忘れる」ことはできない。
3. **オーケストレーション層**:LangGraphはここ。承認ノードを通らない限り次の状態に遷移できない、という構造的執行。状態の永続化・リプレイ・監査証跡もこの層の産物。
4. **インフラ層**:Bunのsystemd-run/cgroupsがこれ。IAMロール、ネットワーク分離、read-onlyのDB接続文字列。エージェントがどれだけ賢く(あるいは狡猾に)なっても物理的に越えられない。

Bunケースが面白いのは、Jarredが自然にこの階層を使い分けていることです——行儀はプロンプトで、リソース隔離はcgroupsで、採点(テストスイート)はそもそもエージェントの書き込み権限の外で。LangGraphだけが憲法の書き場所ではない。

設計原則としては「**条文の重要度と執行層の強度を一致させる**」。破られたら顧客に損害が出る条項(本番への書き込み、データの持ち出し)はプロンプトやグラフではなくインフラ層で执行する。承認フローや監査証跡のように「状態遷移として表現するのが自然で、記録が残ること自体が要件」のものはLangGraphが適地。コーディング規約レベルの行儀はプロンプトで十分。

逆に言うと、LangGraphを選ぶ実質的な理由は「グラフが書けること」ではなく、**checkpointer・interrupt・リプレイという『状態と証跡』のインフラが同梱されていること**です。それが不要な条項までグラフに書き始めたら過剰、それが必要な条項をプロンプトに書いていたら過小。憲法を書き上げてから、条文ごとに執行層を割り当てる——選定はその後、という順番が健全だと思います。
