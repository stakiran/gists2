# AIエージェント設計パターンを2つの境界で整理する

AIエージェントの設計パターンの多くは、OOPやマイクロサービスの古典パターンの言い換えです。古典に足す必要があるのは、次の2つの「境界をどこに引くか」という問いだと考えています。

| 軸 | 向き | 問い |
|---|---|---|
| 決定性 | 縦（エージェントの内と外） | どこまでを決定的な外側にして、どこからを非決定的な内側にするか |
| コンテキスト共有範囲 | 横（エージェント同士） | どこで分割し、境界を越えて何を渡し、何を渡さないか |

## 前提：古典と何が違うのか

従来のパターンは「同じ入力なら同じ出力」を暗黙の前提にしています。LLM呼び出しはこの前提を破るので、それを普通のメソッドとして扱うと、再生や冪等性の議論が崩れます。これが縦の軸が必要な理由です。

また、マイクロサービスで分割したときに失うのはデータの一貫性でした。エージェントで分割したときに失うのはコンテキストです。境界を越えるたびに要約と伝言ゲームが挟まり、判断の前提がこぼれます。これが横の軸が必要な理由です。

## 軸1：決定性（縦の境界）

基本方針は、本体を純粋な関数（stateless reducer）にして、I/O・状態・認証・出力形式をすべて外側の層に追い出すことです。非決定性は内側に閉じ込め、外側からは決定的に扱えるようにします。

| パターン | 古典での出自 | エージェントでの役割 |
|---|---|---|
| Stateless Reducer | Command + Memento | `(state, event) -> state` の形にして、実行を再現可能にする |
| 実行ジャーナル / 再生 | Event Sourcing | LLMの出力を記録し、再実行時は呼び直さずに記録を使う |
| 承認待ちの永続化 | State | 人間の判断待ちを「状態」として保存し、中断・再開できるようにする |
| ツールゲートウェイ | Proxy / API Gateway | ツール呼び出しを外側で検査・制限・記録する |
| アダプタ層 | Adapter / Facade | 実行環境ごとの差分を本体から切り離す |
| イベント列出力 | Observer | 進捗をストリームとして外に流す（SSEなど） |
| 構造化出力 | スキーマ検証 | 自然言語の出力を境界でスキーマに落とす |
| 冪等性キー | Idempotent Receiver | リトライで出力が変わる前提で、キーは外側で振る |
| サーキットブレーカー / バルクヘッド | 同名 | API障害・レート制限・トークン予算を隔離する |

12 Factor Agentsとの対応：Factor 1, 4, 5, 6, 7, 8, 9, 12

## 軸2：コンテキスト共有範囲（横の境界）

マイクロサービスでは「データの所有権」で境界を切りました。エージェントでは「コンテキストの所有権」で境界を切ります。

| パターン | 古典での出自 | エージェントでの役割 |
|---|---|---|
| Small, Focused Agents | 単一責任 / Bounded Context | 1エージェントが持つコンテキストを小さく保つ |
| Single Agent First | Monolith First | 分割コストが高いので、まず分割しない |
| Saga | 同名 | コンテキストを共有しないエージェント間で、補償アクションにより一貫性を保つ |
| Outbox | 同名 | 副作用と状態の永続化を同時にコミットする |
| Consumer-Driven Contract | 同名 | エージェント間メッセージにスキーマを課す |
| Tolerant Reader | 同名 | 受け手が多少揺れた入力を許容する |
| ディスカバリ | Service Discovery | ツール・エージェントを実行時に発見する（MCP、A2AのAgent Card） |
| 分散トレーシング | 同名 | エージェントをまたいだ判断の流れを追う |
| Strangler Fig | 同名 | 既存の業務フローを一部ずつエージェントに置き換える |

12 Factor Agentsとの対応：Factor 2, 3, 10, 11

## 非決定性が横の境界を越えるとき

軸1で非決定性をエージェントの内側に閉じ込めても、エージェント間のメッセージそのものをLLMが生成していると、非決定性は横の境界を越えて別のエージェントに流れ込みます。

例として、調査エージェントAが結果を要約し、執筆エージェントBがそれを受け取って記事を書く構成を考えます。AからBに渡すのがLLMの書いた自然言語の要約そのものだと、Aの外側はそれを素通しするしかありません。Bから見ると、同じ調査でも要約の書き方や、何を含めて何を落とすかが毎回変わり、入力が揺れます。その結果、Bのテストや再生が難しくなり、「AはBに何を渡すのか」という契約（API contract）自体が曖昧になります。

OOPでは非決定性を1つのオブジェクトの内側に閉じ込めればよかったのに対して、ここでは境界そのものが揺れます。対処の選択肢は2つです。

- **送り手側で止める**：境界を越える前にスキーマで固める（構造化出力、Consumer-Driven Contract）
- **受け手側で吸収する**：揺れることを前提に受け取る（Tolerant Reader）

## 保留中の3つ目の軸：権限

従来のサービスは書かれたコードの範囲でしか動きませんが、エージェントは手元のツールのどれをいつ使うかを実行時に決めます。ツールゲートウェイや人間への承認依頼（Factor 7）はこの問題への対処です。

ただし、これは「行動の選択が非決定的」ということなので、軸1に吸収できるとも言えます。独立した軸にするかは、パターンを集めて分類してみて判断します。
