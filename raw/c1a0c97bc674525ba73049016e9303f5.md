# NDDとDD — 非決定的な開発から決定的な開発へ

Agentic engineeringの実践から得た学びの言語化。LLMエージェントを使った開発が、運用を重ねるにつれてどう構造を変えていくかを整理する。

## 概要

- **NDD (Non-Deterministic Development / 非決定的な開発)**: まずLLMに任せて作ってみる。形にはなるが、非決定的なので粗く、ブレる
- **DD (Deterministic Development / 決定的な開発)**: NDDの結果やログを受けて、決定的に作れる部分を特定し、決定的に作る

NDDで始め、ログを観測し、ブレていない工程を順にDDへ引き剥がしていく。これによりNDDの配分を減らし、非決定性のブレと遅さを削減していく。

「最初は全部プロンプトでやらせていたが、気づいたら大半がただのスクリプトになっていた」という、エージェント運用でよく起きる現象を捉えたモデル。

## NDDの本質は「仕様の発見」

NDDの価値は「動くものを作る」こと以上に「仕様を発見する」ことにある。

ある工程が決定的に書けるかどうかは、事前には分からないことが多い。LLMに一度やらせてみると、「ここは実は毎回同じ変換をしているだけ」「ここは本当に判断が必要」という境界線が見えてくる。NDDは実装であると同時に**要件探索**であり、ログを受けてDDに移すのは、探索結果を固定化するプロセスと言える。

また、収束先は「DD 100%」ではないことが多い。自然言語の解釈、曖昧な入力の分類、例外処理などには非決定性が本質的に残る。実務的には「DDのパイプラインの中に、狭く切り出されたNDDの箱がいくつか埋まっている」形に落ち着く。つまり目指すのはNDDの排除ではなく、**NDDの責務範囲を狭く・明確にしていく**こと。範囲が狭いほど、ブレの影響も評価もしやすくなる。

## ログがDD化を駆動する

NDDのログは単なるデバッグ情報ではなく、**DD化の設計資料そのもの**。どの入力パターンが来たか、LLMがどう処理したか、どこで失敗したかの記録が、そのまま決定的コードの仕様とテストケースになる。

ただし、放っておくとログはただのデバッグ用テキストの山になる。DD化に効くログには条件があり、最低限次の3点が**対応づけて**残っている必要がある。

1. どんな入力が来たか
2. LLMが何を判断・生成したか
3. それが成功だったか失敗だったか

特に3点目の成否判定が抜けやすい。これがないと「観測されたパターン」は分かっても「固定化していいパターン」が分からない。頻出だが間違っている振る舞いを決定的コードに焼き固めると、**バグを高速化しただけ**になる。

したがって、NDDを始める時点で「後でDDに移すこと」を前提にログ設計をしておくとよい。構造化された入出力の記録、判断の根拠（LLMに理由を吐かせておく）、成否のラベル。これが揃うと、ログを眺めるだけで「この分岐は毎回同じだからif文でいい」「ここは入力の分散が大きいからNDDに残す」という切り分けが機械的にできる。

言い換えると、**NDDはログを生む活動として設計する**。動くものは粗くブレるので結局作り直すが、ログだけはDDフェーズに引き継がれる資産になる。NDDの成果物はコードよりむしろログが本体、くらいの意識でよい。

## 決め打ちと逃げ道

NDD→DDを一文で言えば、「実際に動かして得られた結果の傾向を取り、その傾向に対処するブツを決め打ちで作る」。

ただし、決め打ちには一つだけ落とせない要素がある。**傾向から外れた入力が来たときの逃げ道**だ。決め打ちコードは観測されたパターンにしか対応できず、想定外の入力に対して黙って間違った処理をするのが最悪のケース。カバー外の入力を検知したら、エラーにするか、NDD（LLM）にフォールバックするかをセットで設計する。

- 傾向内 → DDで高速・安定に処理
- 傾向外 → 検知して逃がす → 再観測 → 次のDD化候補になる

この「検知 → 再観測 → 追加固定化」のループが回る形にしておくと、決め打ちが陳腐化しても対応できる。逆にこの逃げ道が不要なケース（全入力パターンを検証できて完全に決め打ちできるケース）は、最初からDDで書けばよかった部分であることが多い。

## 類似する既存の概念

「柔軟だが高コストな方式でまず走らせ、観測結果をもとに固定的で安価な方式に置き換える」という構造は、既存の多くの概念に見られる。

| 概念 | NDDに相当 | DDに相当 |
|---|---|---|
| JITコンパイラ | インタプリタ実行 | ホットパスのネイティブコード化 |
| プロファイルガイド最適化 (PGO) | 実ワークロードでの計測実行 | プロファイルに基づく再コンパイル |
| 知識蒸留 | 教師モデル（大きく高コスト） | 生徒モデル（小さく特化） |
| メモ化・キャッシュ | 高コストな計算の実行 | 結果の固定・再利用 |
| 踏み分け道 (desire paths) | 芝生を自由に歩かせる | 獣道を舗装する |
| コンシェルジュMVP | 人間による手作業運用 | 定型パターンのソフトウェア化 |
| 判例法の成文法化 | 個別事案ごとの裁判官の判断 | 判例から抽出した成文法 |
| 職人技のマニュアル化 | 熟練者の暗黙知による作業 | 標準手順書 |

特に知識蒸留との対応は深い。教師モデル＝NDDフェーズのLLM、教師の出力ログ＝NDDの実行ログ、生徒＝DDで書く決定的コード。どちらも「高価で非決定的な汎用システムを一度走らせ、その振る舞いの記録をもとに、安価で固定的な特化システムに置き換える」構造をしている。ただし蒸留の生徒は依然として非決定的なモデルであるのに対し、DDの成果物は完全に決定的なコードである点が異なる。NDD→DDは蒸留よりさらに一歩進んだ、**モデルをコードに蒸留する**操作と言える。

説明相手によって効く例は違う。エンジニアにはPGOやキャッシュ、ビジネス側にはコンシェルジュMVPやマニュアル化、一般向けには踏み分け道が通じやすい。

## 具体例: SDD的コード生成エージェントのDD化

要件定義と概要設計を受け取り、その通りに実装するエージェントを考える。初期状態は丸投げのNDD。

```
入力: 要件定義書 + 概要設計書
処理: LLMに「これを読んで実装して」と丸投げ
出力: コード一式
```

### ステップ1: 暗黙の工程を吐かせて記録する

丸投げでも、LLMは内部的に「設計書を解釈 → ファイル構成を決定 → 雛形を作成 → ロジックを実装 → テストを作成」といった工程を踏んでいる。これを明示的に出力させてログに残す。実装前に「作るファイル一覧と各ファイルの責務」をJSONで吐かせる、各ファイル生成時に「設計書のどの記述を根拠にしたか」を吐かせる、生成物のビルド・テスト結果と人間の手直し箇所を対応づけて記録する、など。

### ステップ2: ログを眺めてパターンを探す

数回〜数十回分のログから、たとえばこういうことが見えてくる。

- ファイル構成の決定は毎回ほぼ同じ。「エンティティ名ごとに model / repository / service / handler を作る」というルールで説明できてしまう
- 各ファイルの雛形（import文、クラス骨格、定型のエラーハンドリング）も毎回同じ形。むしろLLMがたまに崩すせいでlintエラーが出ている
- 一方、設計書の曖昧な記述（「適切にバリデーションする」等）の解釈は毎回ブレており、人間の手直しもここに集中している
- テストコードは正常系がCRUDの定型で毎回同じ。異常系だけ解釈が絡んでブレる

### ステップ3: ブレていない部分から順にDDへ

- ファイル構成の決定 → エンティティ一覧の抽出だけを狭いNDDとして残し、構成決定自体はルールベースのコードに
- 雛形生成 → テンプレート／スキャフォールドに置き換え。lintエラーが構造的に消える
- 正常系テスト → エンティティ定義から機械生成
- 曖昧な記述の解釈 → NDDに残す。ただし解釈結果を構造化出力させ、人間が確認してから実装に進む関所を設けてブレの影響範囲を狭める

結果、エージェントの構造はこう変わる。

```
入力: 要件定義書 + 概要設計書
NDD: 設計書 → 構造化された中間表現（エンティティ、API定義、曖昧箇所の解釈）を抽出
DD:  中間表現 → ファイル構成決定 → 雛形生成 → 定型ロジック生成 → 正常系テスト生成
NDD: 曖昧箇所・非定型ロジックの実装（狭い範囲、ファイル単位）
DD:  lint、ビルド、テスト実行、規約チェック
```

最初は全区間がNDDだったのが、NDDの担当は「設計書を中間表現に翻訳する」「本当に判断が要る箇所を書く」の2点に狭まった。重要なのは、**どの工程が引き剥がせるかは事前には分からなかった**こと。「ファイル構成決定は実はルールで書ける」は、丸投げ時代のログを見て初めて確信できる。NDDが要件探索であるとはこういうことである。

## DD化の判断は自動化できるか

部分的にできる。分解すると次のようになる。

**自動化しやすい: ブレの検出。** 同じ・類似入力への複数回実行で出力の分散を測る、工程ごとの出力が同型かをスキーマ比較する、lint・テスト通過率を工程別に集計する。これらは決定的な分析コードで書ける。「この工程は過去30回すべて同一ルールで説明可能、DD化候補」というレポートを自動で上げさせることは今でも十分可能。

**半分自動化できる: DD化の実装。** 候補が特定できれば、パターンをテンプレート／ルールベースに書き起こすのはLLMの得意分野。しかも生成されたDDコードは決定的なので、過去ログをテストケースとして再生し「旧NDDの出力と一致するか」を機械検証できる。

**自動化しにくい: 「固定化してよいか」の判断。** ブレていない＝正しい、ではない。過去30回ブレなく処理していても、30回とも微妙に不適切だった可能性はあるし、31回目の新種の入力で前提が崩れるかもしれない。さらに固定化の判断には「この傾向は今後も続くか」「この組織にとってここは変わりやすい部分か」という、**ログの外にある文脈**が要る。たとえばファイル構成ルールのDD化可否は、組織のアーキテクチャ方針の安定性に依存し、これはログからは読めない。

現実的な形は、**検出と実装案の生成までは自動で回し、「昇格」の承認だけ人間が握る**ループ。エージェントが「この工程、DD化できます。実装案とログ再生による検証結果はこれです」とPRを出し、人間はマージ判断だけする。判断材料の収集が自動化されているため、human in the loopといっても負荷は軽い。

なお、この承認判断自体もログとして溜まる。承認／却下の傾向もまた学習・固定化の対象になり、NDD→DDの構造は開発対象だけでなく開発プロセス自体に再帰的に適用されていく。完全自動には漸近するが、到達はしない。

## 収束の力学 — 比率・時間・非線形な短縮

NDD:DD = 10:0 のとき10時間かかっていたものが、3:7に収束すると3時間で済み、生成物も安定する — という直感は方向として正しいが、比例計算からはいくつかの理由でずれる。

**DD部分の実行時間はほぼゼロに近づく。** LLM呼び出しが数十秒〜数分に対し、テンプレート展開やルール処理はミリ秒〜秒。所要時間は「残ったNDD部分の時間＋α」にほぼ一致する。

**逆方向のずれ: 残るNDDは難しい部分に偏る。** 速くて簡単なNDD（雛形生成など）が先にDD化されて消え、遅くて手戻りの多いNDD（曖昧な設計記述の解釈など）が残る。工程数で3割残っても、時間では4〜5割残ることはある。

**比例以上に得する要因: 手戻りの消滅。** 丸投げ時代の10時間には「lintエラーを直す」「構成がブレて差し戻す」「テストが通らず再生成する」というリトライのループが含まれている。DD化はこのループ自体を消す。雛形がテンプレート化されればlintエラーは構造的に発生しなくなり、その修正時間ごと消滅する。3:7で3時間ではなく2時間になる、という非線形な短縮がよく起きる。生成物の安定は品質の話であると同時に、**再試行コストの消滅という速度の話**でもある。

**収束値はタスクの性質で決まる。** 定型CRUDの量産なら1:9まで行けるし、探索的なプロトタイピングなら7:3から動かないかもしれない。比率は「そのドメインの本質的な非決定性」に漸近していく。

**収束は静的ではない。** 新種の要件が来ればNDD比率は一時的に跳ね上がり、ログが溜まればまた下がる。長期的には「平常時2:8、新領域で6:4に戻り、また収束」というノコギリ波状の推移になる。この「跳ね上がれる」こと自体が価値であり、全部DDの従来型システムでは新種の要件にそもそも動けない。**残りのNDDはコストではなく、変化への対応力の予算**と考えるのがよい。

## 生成物の状態 — 動くことと信頼できることは別

NDD:DD = 2:8 という比率は**生成プロセスの比率**であって、生成物そのものは全部ただのコードである。出力されたリポジトリを見ても、どの行がテンプレート由来でどの行がLLM由来かは外見上区別がつかない。LLMは製造時にだけ関与し、成果物の実行時にはいない。その意味で「そのまま動かせる」。

しかし、動くことと信頼できることは別で、由来による差はここに出る。

- **DD由来の8割は検証済みと同義。** 生成器自体がテストされていれば出力は毎回同じ品質で、個別レビューの意味がほぼない。lint通過や規約遵守が構造的に保証されている
- **NDD由来の2割は、生成のたびに品質が変わりうる。** 人間が書いたコードと同じ扱いが必要で、テストとレビューという個別検証を経て初めて渡せる状態になる

したがって実務上もっとも価値があるのは、**出力に由来情報を添える**こと。「このファイル群は雛形生成（DD）、この関数はLLM生成（NDD）で、根拠にした設計書の記述はここ、通過したテストはこれ」というメタデータがあると、レビュー対象がNDDの2割に絞られる。由来情報がなければ、レビュアーはどこがブレうるか分からず全部を疑って読むしかなく、せっかくのDD化がレビュー工程で活きない。

**生成物は「コード＋由来メタデータ＋検証結果」のセット**、と考えるのがこのやり方の完成形。

（なおこれは、NDDが製造時にいる構成の話。成果物の中にLLM呼び出しが埋め込まれる＝実行時にNDDが残る構成なら、運用中もブレ続けるため、フォールバックや監視込みで引き渡す必要がある。）

## DD比率は説明可能性の指標になる

DDのウェイトが増えるほど、証跡も存在する。しかもそれは偶然ではなく、**構造的に**そうなる。

ある工程をDDに昇格させるには「ログを取り、ブレていないことを確認し、旧NDDの出力との一致を検証し、承認する」という手続きを踏む。つまりDD化された部分には必然的に次が付随する。

- なぜこのルールでよいのか（観測ログ）
- 正しく動くことをどう確認したか（ログ再生による検証）
- 誰がいつ承認したか（昇格記録）

証跡がないとそもそもDD化の判断ができないため、**DD比率が高い＝それだけの検証手続きを通過してきた**、が論理的に成り立つ。対照的に、丸投げ（10:0）時代の成果物は「なぜこうなったか」がLLMの内部にしかなく、再現もできず、証跡ゼロである。

つまりNDD→DDの移行は、機能の固定化であると同時に、**暗黙知を検証可能な記録に変換する作業**でもある。DD比率は、そのシステムがどれだけ説明可能になったかの指標として読める。監査や説明責任のある文脈（規制産業、受託開発の納品、医療・金融系）では、DD比率がそのまま「説明できる範囲」になり、AI生成コードの品質保証という問いへの構造的な回答になる。

注意点として、証跡が「存在しうる」ことと「使える状態にある」ことは別。DD化の過程でログや承認記録が生まれても、生成物と紐づく形で保管する設計をしていなければ後から辿れない。「NDDはログを生む活動として設計する」のと同様に、**昇格の記録自体を成果物の系譜として残す仕組み**まで含めて、このやり方は完成する。

## まとめ

1. まずLLMに任せて作る（NDD）。ただし最初から、後のDD化を前提にログを設計する
2. ログから「ブレていない工程」を特定し、決定的なコードに引き剥がす（DD化）。ブレの検出と実装案の生成は自動化し、昇格の承認は人間が握る
3. 決め打ちには必ず傾向外の検知と逃げ道をセットにし、検知→再観測→追加固定化のループを回す
4. NDDはゼロにはならない。残りは変化への対応力の予算であり、責務を狭く明確に保つ
5. 生成物にはNDD/DDの由来メタデータと検証結果を添えて渡す
6. DD比率の上昇は、速度と安定性の向上であると同時に、説明可能性の向上でもある
