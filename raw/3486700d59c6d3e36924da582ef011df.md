# 同じ「Customer」をスキーマとオントロジーで定義するとどう違うか

ソフトウェアエンジニアが書くスキーマと、オントロジーエンジニアが書くオントロジーは、似ているようで答えている問いが違う。同じ「Customer」を題材に比較し、後半で OWL/Turtle 記法の読み方を解説する。

---

## 1. 二つの定義

### ソフトウェアエンジニア（DBスキーマ）

```sql
CREATE TABLE customers (
  id          SERIAL PRIMARY KEY,
  name        VARCHAR(100) NOT NULL,
  email       VARCHAR(255) UNIQUE NOT NULL,
  created_at  TIMESTAMP,
  status      ENUM('active','suspended','deleted')
);
```

答えている問い：**このシステムで顧客を扱うために、何を保存し、どう制約するか**

- `email` が `UNIQUE` なのは業務上の真理ではなく、ログインの都合
- `status` に `'deleted'` があるのは、物理削除しない設計の都合

### オントロジーエンジニア（OWL / Turtle）

```turtle
:Customer a owl:Class ;
    rdfs:subClassOf :Role ;
    rdfs:comment "取引において購入者側を担う役割。Person または Organization が担う" .

:Person owl:disjointWith :Organization .

:playsRole a owl:ObjectProperty ;
    rdfs:domain [ owl:unionOf (:Person :Organization) ] ;
    rdfs:range :Role .

:Order rdfs:subClassOf
    [ owl:onProperty :placedBy ; owl:someValuesFrom :Customer ] .
```

答えている問い：**顧客とはそもそも何であり、他の概念とどう関係するか**

- Customer は人そのものではなく**役割**。同じ人が Customer でも Supplier でもありうる
- 注文がなければ誰も Customer ではない、という業務上の真理を書いている

---

## 2. 何が違うか

| 観点 | スキーマ | オントロジー |
|---|---|---|
| 目的 | 特定システムを動かす | 複数のシステム・人・組織で意味を共有する |
| Customer の正体 | 行（レコード） | 役割（Person / Organization が担う） |
| 書かれていない事実 | 存在しない（閉世界） | 未知なだけ（開世界） |
| 同一性 | id が違えば別物 | id が違っても同一かもしれない（`owl:sameAs`） |
| 制約の意味 | 保存時に弾く | 矛盾を推論で検出する |
| `email` が UNIQUE | 実装都合として書く | たぶん書かない（世界の真理ではない） |
| 変更の動機 | 機能追加、性能 | 概念の理解が深まった |

### 開世界と閉世界

この差は実務でも効く。

- スキーマ：注文テーブルに顧客IDがない → **エラー**
- オントロジー：「Order は Customer を持つ」という公理があり、顧客の記載がない注文がある → **「誰か知らない Customer がいるはず」と解釈**（エラーではない）

---

## 3. 同じになる部分

概念レベルでは実はかなり重なる。ER図や DDD のドメインモデルで「Customer と Person を分けるか」「Order と OrderLine の関係は」と議論しているとき、やっていることはオントロジー工学とほぼ同じ。違いはその結果を**どこに落とすか**——テーブルとクラスに落とすか、システム非依存の形式知識に落とすか——にある。

現実には：

- 小さなチームでは同じ人が両方をやり、ドメインモデルがオントロジーの代わりになる
- 差が出るのは複数システム・複数組織をまたぐとき。営業DBの「顧客」、経理DBの「取引先」、外部パートナーの "Client" を突き合わせる必要が出て初めて、実装非依存の定義が要る
- 逆にオントロジーからスキーマを導出することもある（オントロジーが概念モデル、スキーマがその一実装）

一言でいうと：

> ソフトウェアエンジニアは「動くために必要十分な定義」を書き、
> オントロジーエンジニアは「誰が読んでも同じ意味になる定義」を書く。

前者は後者の部分集合になるのが理想で、乖離すると「同じ Customer なのに部門ごとに意味が違う」問題が起きる。

---

## 4. Turtle 記法の読み方

Turtle は「**主語 述語 目的語 .**」の三つ組を並べる記法。全部この形なので、それさえ押さえれば読める。

### 基本ルール

| 記号 | 意味 |
|---|---|
| `:Customer` | 先頭のコロンは「このオントロジー内で定義した名前」の印 |
| `owl:` `rdfs:` | 標準語彙の名前空間 |
| `a` | 「〜である（is a）」の略。`rdf:type` と同じ |
| `;` | 主語を繰り返して次の述語へ |
| `.` | 文の終わり |
| `[ ... ]` | 名前のない一時的なもの（無名ノード）。「〜という条件」を書くときに使う |

### ブロック 1：Customer の宣言

```turtle
:Customer a owl:Class ;
    rdfs:subClassOf :Role ;
    rdfs:comment "取引において購入者側を担う役割。..." .
```

- Customer は クラス（概念）である
- Customer は Role の下位概念である（Customer は Role の一種）
- Customer の説明文はこれこれである

→ 「Customer とは役割の一種です」という宣言。

### ブロック 2：Person と Organization は別物

```turtle
:Person owl:disjointWith :Organization .
```

- Person と Organization は互いに素である

→ 「人であり同時に組織であるものは存在しない」。あるものが両方だと推論された場合、矛盾として検出される。

### ブロック 3：関係の型宣言

```turtle
:playsRole a owl:ObjectProperty ;
    rdfs:domain [ owl:unionOf (:Person :Organization) ] ;
    rdfs:range :Role .
```

- playsRole は オブジェクトプロパティ（もの同士をつなぐ関係）である
- その主語側（domain）は「Person または Organization」である
- その目的語側（range）は Role である

`[ owl:unionOf (:Person :Organization) ]` は「Person と Organization の和集合」という名前のないクラスをその場で作っている。

→ 「`X playsRole Y` と書けるのは、X が人か組織で、Y が役割のとき」。

### ブロック 4：注文には必ず顧客がいる（一番読みにくい）

```turtle
:Order rdfs:subClassOf
    [ owl:onProperty :placedBy ; owl:someValuesFrom :Customer ] .
```

- Order は「placedBy の相手に Customer を少なくとも1つ持つもの」の下位概念である

`[ ]` の中身は「placedBy という関係で、Customer である何かにつながっているもの全部」というクラスを無名で定義している。Order はその一種だと言っている。

→ 結果として「注文には必ず注文者（Customer）がいる」という制約になる。

#### なぜ回りくどいか

OWL には「Order は placedBy を持つ」と直接書く文法がない。「そういう性質を持つものの集合」をまず定義し、Order をその部分集合にする、という書き方をする。

集合論的に書くと：

```
Order ⊆ { x | ∃y. placedBy(x, y) ∧ Customer(y) }
```

数学の内包表記をそのまま三つ組にしたものだと思えば、構造は同じ。

### 全体を日本語にすると

1. 顧客とは役割の一種である
2. 人と組織は別物である
3. 「役割を担う」という関係は、人か組織が主語で、役割が目的語になる
4. 注文は必ず誰かの顧客によって出される

データ（誰が誰の顧客か）は一切入っておらず、**概念の定義と制約だけ**が書かれている。
