## 1. stakiran さんの傾向（公開情報から）

千葉在住、公開リポ 260、Works ページで自分の作品を **Software / Concepts / Docs / Catch-upper** に分類している時点で特徴が出ています。

**① 「ソフトウェア」より「概念」を作る人**
Works の約半分が Concepts（`four-jects`, `jects-method`, `staqueue-pattern`, `workware_engineering`, `caat`, `AltPIP`…）。造語で名前を付けて、Markdown で定義し、GitHub Pages で公開する、というパターンが一貫しています。「名前の付いた概念ツール＝workware」という自分の枠組みまで持っている。これは simonw が "tools" を量産するのと対になる、**「概念を量産する人」**です。

**② 情報管理・タスク管理・ナレッジングが主戦場**
`taskmanagement-kamikudaku`, `tms1`, `dwmy_review`, `raiueow`（AI 時代の 5 層ディレクトリ）, `gists2`（gist ベースの LLM Wiki）, `rawden`。Scrapbox 愛（`vscode-scb`, `scbdown`, blog が scrapbox）も強い。翻訳プロンプトの用語集に「ナレッジング／ナレジャー／ナレジニア」とあるので、**知識生産そのものを職能として定義しようとしている**。

**③ AI エージェントとの付き合い方を「運用設計」の視点で考えている**
- `12-factor-fasd`：完全自律開発の 12 原則（要件を検証可能に、品質はプラガブル、ビジュアル排除、コンテキスト超過前にアボート…）
- `kairon`：cron ではなく "kairos"、LLM が「今がその時か」を判断するスケジューラ
- `kizamu1`：`ki` で雑にコミット→AI が squash・清書してから push（Rust 製）
- `my.md`：`.claude/rules/my.md` を gitignore する規約提案
- `github-trend-summarizer`：Claude Code に Trending リポを自律探索させて要約→Pages 公開
- `kairon/CLAUDE.md` の「memo/ を勝手に読むな」など、**AI への指示の切り分けが細かい**

つまり「コードを書かせる」より **ワークフロー・規約・発火条件・人間の介入点をどう設計するか** に関心が向いている。

**④ 道具の作り方：小さく、単機能、CLI/クリップボード起点、Windows 寄り**
`cb2gist`, `cb2ai`, `cc`, `coppai`, `screenshot2text`, `ralarm`, 秀丸・AutoHotkey。日々の摩擦を潰す単機能ツールを Python/Rust で。Web UI ものは少なめ（`todaros-puter`, `playlist1` くらい）。

`prompt.md` + `translator.py` を複数リポに置き、日本語で書いて LLM で英訳する運用。「書く→翻訳→公開」のパイプライン化。

一言でまとめると：**「自律エージェント時代の知的生産を、概念・規約・運用の側から設計する人」**。simonw が「LLM に何が作れるか」を実物で試す側なら、stakiran さんは「LLM とどう働くかの枠組み」を作る側です。

## 2. simon tools で参考になるもの（agentic engineering / Claude 観点）

関心と noticeably 重なるのは、個々のツールよりも**運用の仕組み**です。順に。

### A. リポジトリ運用そのもの（最も参考になる）

**`write_docs.py` ＋ `*.docs.md`**：各ツールの HTML から LLM が 2–3 文の説明を生成し、`<!-- Generated from commit: HASH -->` を埋め込んで**差分があるときだけ再生成**する。プロンプトには "Do not use words like just or simply" のような文体規約まで入っている。
→ `github-trend-summarizer` の docs/ や `aicatchup` に、この「コミットハッシュで鮮度管理する生成ドキュメント」の仕組みはそのまま流用できます。

**`build_colophon.py` ＋ `/colophon`**：全コミットメッセージを集約し、**LLM との対話トランスクリプト（gist/共有リンク）へのリンクを並べたページ**。「このツールはどのプロンプトから生まれたか」が全部追える。
→ 12-factor-fasd の「要件定義の事前情報をプレーンテキストで太らせろ」「オンボーディングの自走」を実践した形がこれ。概念系リポにも「この概念は何の対話から出てきたか」の出生記録を付けると、ナレッジングの事例として強くなるはず。

**`TOOLS_GUIDE.md`**：リポの構造・命名規約・テストの書き方を、**エージェントが新ツールを作るための手引き**として一枚にまとめたもの（タイトルからして LLM に書かせたもの）。CLAUDE.md の「厚い版」と考えると、kairon の `agents.md` 設計の参考になります。

**`build.sh`**：`GENERATE_LLM_DOCS=1` のときだけ LLM を呼ぶフラグ、footer.js の注入、sitemap/redirect 生成。**「人間が触るのは HTML 1 個だけ、残りは全部ビルドが面倒を見る」**という分業。

**`tests/test_chirp_pong.py` など Playwright テスト**：LLM 生成の HTML を pytest+Playwright で検証。12-factor の「要件を検証可能にせよ」「品質はプラガブルに」の具体例。

（訂正：前回「`claude.yml` がある」と書きましたが、実際のワークフローは `test.yml` / `pages.yml` / `deploy-cloudflare-workers.yml` の 3 つで、`claude.yml` は `TOOLS_GUIDE.md` 内の記述のみでした。）

### B. Claude / エージェントの「観測」ツール

- **`claude-code-timeline`**：Claude Code のセッション `.jsonl` をタイムライン表示（メッセージ・ツール呼び出し・ファイルスナップショット）。**kairon の logs/ や trend-summarizer の自律探索ログを人間が後から読む UI** として一番近い。
- **`deep-research-viewer`**：推論ステップ・検索・訪問ページ・コード実行を可視化。エージェントのトレース閲覧の UI パターンとして参照価値あり。
- **`token-usage` / `claude-token-counter`**：`llm logs -su` の YAML からモデル別トークン集計、Token Counting API でモデル比較。12-factor の「コンテキスト超過前にアボート」を実装するなら前提になる計測。
- **`render-claude-citations`**：Claude API の citations 付きレスポンスを blockquote で描画。`gists2`（LLM Wiki）で出典を見せたいときに。

### C. 入出力の「摩擦潰し」系（cb2gist / cb2ai の文脈と同族）

- **`cleanup-claude-code-paste`**：Claude Code のターミナル出力を貼ると ❯ や折り返しを除去。これは完全に `cb2*` シリーズの Web 版発想。
- **`github-issue-to-markdown`**：Issue/PR を本文＋全コメント＋参照コードを展開した Markdown に。**エージェントに食わせる前処理**として優秀。
- **`notes-to-markdown` / `paste-rich-text` / `html-table-extractor`**：クリップボードの rich text を Markdown 化。raiueow 的なプレーンテキスト集約に。
- **`llm-cliche-highlighter` / `writing-style`**：AI 臭い言い回しや weasel word を検出。日英翻訳パイプラインの後段チェックとして。

### D. コンセプトとして面白いもの

- **`prompts-js`**：alert/confirm/prompt を async/await で返すだけの小ライブラリ。「エージェントが人間に質問する」UI の最小形。
- **`chirp-pong`**：技術的には無関係ですが、「サーバーなしで 2 台が協調する」というのは collaboration-modules 的な比喩として使えそう。

### 取り入れ方の提案（1 つだけ選ぶなら）

**`write_docs.py` 方式の「コミットハッシュ連動の LLM 生成ドキュメント」＋ colophon 的な出生記録**を、概念系リポ群に横断適用するのが一番レバレッジが効くと思います。stakiran さんの資産は「概念の数」なので、その一覧・要約・由来を自動生成できれば Works ページが生きた索引になります。
