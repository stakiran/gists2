# エージェントを「借りた実行環境」で動かすための原則

考え方はひとつだけです：**エージェントを動かす箱は自分のものではなく、いつ止められても文句を言えない。** 以下はすべてその帰結です。

---

## A. 書き始める前に決めること（あとから直すと作り直しになる）

**1. 「自分のロジック」と「箱に合わせる部分」を分けて書く**
何を考え、どのツールを呼び、どんな状態を持つか——ここは自分のもので、どこに持っていっても変わらない。一方で、受け口のURL、ポート番号、セッション番号の渡し方、認証情報の受け取り方、デプロイの手順は箱ごとに違う。前者を中心に置き、後者は薄い変換層として外側に付ける。
→ 箱を乗り換えても中心を書き直さずに済む。

**2. 箱の決まりごとには従う。工夫しない**
「このURLで受けろ」「このポートを開けろ」「このCPUで動け」「この言語で書け」は交渉できない。無視すると起動すらしない。決まりごとは最初に全部書き出しておく。
→ よくある事故：手元のPCで動いたイメージを上げたら、CPUの種類が違って無言で落ちる。

**3. 「どのくらい長く生きる箱か」を最初に選ぶ**
短い対話向けの軽い箱と、何時間・何日も走る重い箱があり、あとから切り替えられないことが多い。処理が長いか、GPUがいるか、途中でディスクに残したいかで最初に選ぶ。
→ よくある事故：上限時間に当たってから気づき、作り直し。

**4. 箱の中に何も残さない。状態は全部外に置く**
一回の会話が終わると箱は消え、中身も消える。同じ会話IDでもう一度呼んでも、新品の箱が来る。スリープするタイプの箱でも、メモリ上の変数・タイマー・途中の通信は消える。会話の履歴も途中結果も、必ず外部のストレージに書いて、毎回そこから読み直す。
→ よくある事故：変数に会話履歴を持たせて、2ターン目で記憶喪失。

**5. 会話IDは会話の間ずっと同じものを使う**
呼び出しのたびに新しいIDを作ると、そのたびに新品の箱が立ち上がり、毎回数秒待たされる。
→ よくある事故：この遅さを「モデルが遅い」「サーバーが遠い」と勘違いして無駄な調査をする。

---

## B. 設計の段階で決めること

**6. 作業中なら「作業中」と箱に伝える**
箱は「しばらく通信がなければ暇だ」と判断して勝手に片付ける。裏で長い処理をしているときは、ヘルスチェックや定期的な合図で「まだ忙しい」と伝える仕組みを入れる。
→ よくある事故：処理の途中で片付けられ、結果が消える。

**7. 記憶は二種類に分け、「誰がいつ書くか」を決める**
今回の会話の中身（短期）と、この人について覚えておくこと（長期）は寿命も範囲も料金も違う。長期記憶への書き込みは「毎ターン自動」なのか「区切りで明示的に」なのか、待たされるのか裏で走るのかを決める。外から入ってきた文章が長期記憶に紛れ込まないよう、書く前に検査する。
→ よくある事故：毎ターン長期記憶の抽出を同期で呼んで遅い。悪意ある入力が記憶に残り、以後ずっと影響する。

**8. モデル呼び出しとツール呼び出しは「やり直しても平気」に作る**
途中で落ちたら、どこかの地点から再実行される。その再実行で同じツールが二回走る前提で、毎回「これは○○番の依頼」という印を付け、二回目は無視されるようにする。ループそのものは決められた手順、モデルとツールは不確実な部品、と役割を分けておく。
→ よくある事故：二重予約、二重送信、二重課金。「一時停止の直前」に置いた課金処理が再開時にもう一度走る。

**9. 人間は「返事が遅いツール」。返事待ちは箱の外で待つ**
承認は数分〜数日かかるので、箱の寿命を必ず超える。承認依頼を「ツールを呼ぶ」ことと同じ形で扱い、「返事が来たら続きから再開できる」ように状態を外に保存してから、箱は終わってよい。放置された依頼を一定期間で自動却下するルールも入れる。
→ よくある事故：承認待ちの間に箱が消え、承認したのに続きが動かない。

**10. エージェントは一人のユーザーとして扱い、認証情報は使い回さない**
エージェントには専用のIDを与え、権限はゼロから必要な分だけ足す。人の代理で動くときは「誰の代理か」を示す証明書を、リクエストのたびに受け取り直す。ツールへは直接ではなく、ルールをかける関所を通して呼ぶ。
→ よくある事故：証明書をキャッシュして、別の人の操作が別の人の名前で記録される。

**11. ツール接続は「毎回が初対面」として書く**
リクエストごとに別の箱に振り分けられるので、前回のやりとりを覚えている前提で作ると壊れる。一回の要求に必要な情報をすべて含める。
→ よくある事故：初回に挨拶して状態を作り、2回目で「そんな相手は知らない」と拒否される。

**12. 流れてくるデータは自分で検査する**
画面へ逐次配信する仕組みは箱が用意してくれるが、中身の正しさは見てくれない。受け取った入力の形式チェックは自分の責任。

---

## C. 運用で効いてくること

**13. 料金の数え方と、追跡の粒度に合わせる**
- 「CPUが動いた時間」で課金される箱なら、待ち時間はタダなので恐れなくてよい。「ステップ数」で課金される箱なら、細かく分けすぎると請求が膨らむ。「保存したイベント数」で課金される箱なら、古い会話を自動で消す期限を設ける。
- 追跡は「会話 → 一回の実行 → 個々の呼び出し」の三段で記録し、必ず会話IDを付ける。そうしないと事故のとき、どの会話のどの呼び出しかたどれない。

---

## まとめ：最初の5つは紙に書いてから始める

| 決めること | 一言で |
|---|---|
| どこまでが自分のロジックか | 中心と変換層を分ける |
| 箱の決まりごと | 全部リストにして従う |
| 箱の寿命の種類 | 処理の長さで最初に選ぶ |
| 状態の置き場所 | 箱の中には置かない |
| 会話IDの付け方 | 会話中は同じIDを使い回す |

残りの8つは設計・運用で足していけますが、この5つは後回しにすると作り直しになります。
