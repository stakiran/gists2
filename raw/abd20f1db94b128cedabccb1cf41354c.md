# LLM as judge で出荷判定していいのか問題

AIエージェントに PRD を渡して設計→開発→テストまで全自動で回すパイプラインを考えたとき、各フェーズの品質判定を LLM as judge (evaluator) にやらせることになる。このとき「judge が合格と言った」を出荷エビデンスとして扱っていいのか? という問題を考えたのでメモ。

きっかけは、AI と議論していたら「CPK(工程能力指数)の判定と出口検査をすればいい」と言われたこと。半分正しいが、一番大事な前提が抜けている、というのが結論。

---

## TL;DR

1. LLM judge は「実行するたびに結果が揺れるテスト」。1回の合否では判定できないので、統計的に扱う発想(CPK的なもの)自体は正しい
2. ただしその前に **judge 自体が信用できるかの検証(テストのテスト)** が必要。壊れた物差しで統計を取っても無意味
3. judge の検証は「ゴールデンセット」「欠陥注入」「ブレ計測」「人間とのアグリーメント」の4点セット
4. ground truth は最終的に人間が供給するしかないが、必要な人間は「常駐レビュアー」から「初期の教師+監査役」に圧縮できる
5. 運用が回り始めたら、ground truth を人間の意見から **下流の実測結果(手戻り率など)** に移していける。これが本丸

---

## 1. CPK 的発想の正しい部分と抜けている部分

### 正しい部分

LLM の出力は非決定的なので、品質を点(1回の合否)ではなく分布として捉え、統計的に判定するという発想は正しい。フレイキーテストを1回の緑赤で判断しないのと同じ。

- N 回実行してスコアの平均とばらつきを見る
- ロングラン運用ではスコア分布を継続監視し、ドリフトしたらアラート(製造業の管理図と同じ発想)

### 抜けている部分: 測定器の検証

製造業で CPK を語る前には必ず **MSA(測定システム解析、Gage R&R)** をやる。測定器そのものが信用できなければ、CPK の数字は無意味だから。

LLM as judge の文脈に訳すと:

> **judge というテスト自体がバグっていたら、「バグったテストが安定して緑」なだけ。まずテストのテストをしろ。**

### ついでに: CPK という指標自体も微妙

CPK は連続量・正規分布・明確な規格限界を前提にした指標。judge のスコアは 1〜5 点のような順序尺度に近く(3点と4点の差 = 4点と5点の差である保証がない)、分布も正規とは限らない。

無理に CPK を計算するより、**「スコアが閾値以下だった割合(不良率)+ 信頼区間」** を出すほうが正直で、説明もしやすい。

## 2. judge の検証方法(テストのテストの書き方)

設計フェーズの evaluator を例にする。開発や検証フェーズまで進んでからの手戻りはコストが大きいので、設計時点で欠陥を止めたい、というモチベーション。

### ステップ1: ゴールデンセットを作る

過去の設計ドキュメントを 20〜50 件集めて、シニア 2〜3 人が「合格/不合格 + 理由」をラベル付けする。

- **不合格サンプルを意図的に混ぜる**のがポイント。後工程が炎上した設計、手戻りが発生した設計は最高の教材
- これはユニットテストでいうフィクスチャ。judge のプロンプトやモデルを変更するたびに、このセットで回帰テストする

### ステップ2: 欠陥注入テスト(ミューテーションテストの発想)

良い設計ドキュメントに、わざと欠陥を仕込んだ変異体を作り、judge の**検出率**を測る。

欠陥の例:

- PRD にある要件を1つ黙って落とす(要件カバレッジ漏れ)
- 認証設計を曖昧なまま残す
- 排他制御や冪等性の考慮を消す(後で開発が死ぬやつ)
- 非機能要件(性能・スケール)への言及を削る
- 存在しない API や矛盾するデータフローを入れる

すると「認証漏れは 10/10 検出するが、冪等性漏れは 2/10 しか拾えない」のような**弱点マップ**が得られる。ミューテーションを殺せないテストは信用できない、のと同じ理屈。

**過去に実際に手戻りを起こした欠陥タイプを優先的にミューテーション化する**と、目的(手戻り防止)に直結する。

### ステップ3: ブレの計測

ゴールデンセット全件を、同じ judge で各 10 回評価する。

- 同一入力で合否がひっくり返る率を測る。temperature 0 でも LLM は揺れるので必ず測る
- 揺れが大きい場合、「5回評価して多数決」を judge の実装にする手もある(コスト増と引き換えに分散を下げる)

### ステップ4: 人間とのアグリーメント計測

judge の判定と人間ラベルの一致度を出す。単純一致率だけでなく:

| 指標 | 意味 | 影響 |
|---|---|---|
| 見逃し率 (false negative) | 悪い設計を通してしまう率 | 手戻りコストに直結。最重要 |
| 過検出率 (false positive) | 良い設計を差し戻す率 | パイプラインのスループットを殺す |
| Cohen's kappa | 偶然一致を補正した一致度 | 報告用に便利 |

手戻りが痛いユースケースなら、閾値は見逃し最小化に寄せて、過検出は人間の再判定で救済する設計が合理的。

## 3. judge の作り自体を検証可能にする

検証をやりやすくするために、evaluator の出力設計も変えたほうがいい。**「この設計は80点」という総合スコア1個は、検証もデバッグもできない。**

代わりにチェックリスト分解する:

```
- PRD要件カバレッジ: 各要件IDに対し、設計内の対応箇所を「引用」させる
  (引用できなければ漏れ)
- 整合性: API定義とデータフローの矛盾の有無
- 非機能: 性能/セキュリティ/運用の言及有無と具体性
- 各項目: pass/fail + 根拠の引用
```

利点:

1. 項目ごとに検出率を測れる
2. ブレる項目だけピンポイントで改善できる
3. **引用を強制すると hallucinated pass(見てないのに合格と言う)を機械的に検出できる**

特に要件カバレッジは引用ベースにするとほぼ決定的なチェックになり、judge の中で一番信頼できる部分になる。

## 4. 「結局、設計の良し悪しがわかる人間が必要では?」

なる。これは避けられない。**ground truth はどこかで人間から供給するしかない**。judge を judge で検証すると無限後退するだけ。

「LLM as judge で人間を排除する」は厳密には不可能で、正確には:

> **人間の判断を「全件レビュー」から「少数のラベル付けと監査」に圧縮するのが LLM as judge の正体**

ただし、圧縮の効かせ方が3つある。

### 4-1. 全件レビューではなくラベル付けだけでいい

シニアが常時レビューに張り付く必要はない。最初のゴールデンセット作成(数日)と、運用後のサンプリング監査(月数時間)だけ。1人のシニアの判断力をデータセットに焼き付けて、judge に何千回も適用させるレバレッジ構造。

### 4-2. 判定を「目利き」から「照合」に変換する

「この設計は良いか?」はシニアにしか判定できない。でも「PRD の要件7に対応する設計記述を引用できているか?」なら、引用の有無を確認するだけなので凡庸なスキルで足りる。チェックリスト+引用ベースに分解するほど、必要な人間の希少性が下がる。

### 4-3. 一番強い ground truth は「人間の意見」ではなく「結果」

全自動で開発・テストまで走るパイプラインなら、設計の良し悪しを人間の意見ではなく**下流の実測結果**で定義できる:

- この設計から開発フェーズで何回手戻りが発生したか
- 実装時に設計との矛盾が発覚した回数
- テストフェーズでの欠陥密度
- リリース後の障害

judge の検証を「人間ラベルとの一致」ではなく「**judge が合格させた設計は、実際に手戻りが少なかったか**」で行う。「手戻りを設計時点で止めたい」という目的に対しては、意見ラベルよりこちらのほうが正しい指標ですらある。

現実解はハイブリッド:

> **立ち上げ期は人間ラベル(結果データがまだ無いので仕方ない)→ 運用が回り始めたら結果データに ground truth を移す。手戻りデータが蓄積するほど人間依存が減る構造。**

### それでも残る人間の役割

- 初期ラベルと欠陥注入の設計(どんな欠陥が手戻りを起こすかの知識はシニアの頭にしかない)
- judge と結果が食い違ったケースの裁定
- 「そもそも何を品質と呼ぶか」の定義の更新

## 5. 全体像(パイプラインとして)

```
[立ち上げ期]
  1. ゴールデンセット作成(人間ラベル 20〜50件、不合格例込み)
  2. 欠陥注入テストで judge の検出力を測る(弱点マップ)
  3. 反復実行でブレを測る(必要なら多数決化)
  4. 見逃し率・過検出率を出し、閾値を見逃し最小化に寄せる
  → ここまでやって初めて judge の合格判定がエビデンスになる

[リリース判定]
  - N回実行 → 不良率 + 信頼区間で合否(1回の緑赤で判断しない)

[ロングラン運用]
  - スコア分布を継続監視、ドリフトでアラート(メトリクス監視と同じ)
  - judge 合格分も一定割合(例: 10%)を人間がサンプリング監査
  - ズレたケースはゴールデンセットに追加(回帰テスト資産が育つ)
  - 下流の手戻り実績と突合し、ground truth を結果データに移していく
```

## まとめ

- 「CPK + 出口検査」は方向としては正しいが、**judge 自体の妥当性検証(MSA 相当)を飛ばすと数字が無意味になる**
- judge の検証 = ゴールデンセット + 欠陥注入 + ブレ計測 + アグリーメント計測
- judge はチェックリスト + 引用ベースに作ると検証可能になる
- 人間は不要にならないが、「常駐レビュアー」→「初期の教師 + 監査役」に圧縮できる
- 最終的な ground truth は人間の意見ではなく**下流の手戻り実績**に置くのが本丸
