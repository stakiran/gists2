# エージェンティック・エンジニアリングのための設計パターン：マネージド・エージェント・ランタイムが課すアーキテクチャ制約の比較研究

## TL;DR
- **提案された7パターン分類は妥当だが、8番目に「可観測性・評価」、9番目に「コストモデル・課金単位」を独立パターンとして追加し、さらに「サンドボックス化ツール実行（Code Interpreter/Browser）」を横断的サブパターンとして扱うべき。** AgentCoreの制約（ARM64・8080/8000/9000ポート・15分アイドル/8時間上限・ステートレスMCP・OBOトークン交換）は固有ではなく、Vertex AI Agent Engine、Microsoft Foundry Agent Service、Cloudflare Agents/Durable Objects、Temporal等でも構造的に反復する。
- **ポータブルな層（エージェントループ、ツール、プロンプト、状態スキーマ）とプラットフォーム固有のアダプタ層（HTTP契約、セッションID意味論、認証ヘッダ、デプロイ・パッケージング）を分離するヘキサゴナル/ポート＆アダプタ構成が、全プラットフォームを同時に満たす唯一の現実解。** 12-factor agentsの「ステートレス・リデューサ」（Factor 12）と「実行状態と業務状態の統合」（Factor 5）がこの分離の理論的基盤となる。
- **アーキテクチャ段階（コード記述前）で決定すべき事項：CPUアーキテクチャ、コンピュートタイプ（microVM対Instances）、セッションID採番戦略、状態外部化の方式、承認待ちを持続実行層に押し出す設計、ツールの冪等性。** これらは後から変更困難であり、fresh session IDの毎回発行によるコールドスタート多発、ヘルスチェックのbusy未通知によるスケールダウン、リプレイ下での非冪等ツール二重実行が実務上の頻出ピットフォール。

## Key Findings

1. **ランタイム契約は普遍的パターン**：AgentCoreはHTTP時 `/invocations`(POST)・`/ping`(GET)・ポート8080・ARM64、MCP時ポート8000・`/mcp`、A2A時ポート9000・ルートパス`/`を要求。x86イメージは起動しない。Vertex AIはコンテナ内部の契約を隠蔽するが `container_concurrency`（既定9、Google推奨値は `2 * cpu + 1`）とrequirements.txtパッケージングを課す。Cloudflareはコンテナではなくアクター（Durable Object）契約。いずれも「プラットフォームが規定する固定インターフェイスにコードを適合させる」点で同型。

2. **セッション境界と揮発性状態**：AgentCoreは1セッション=1 microVM（既定15分アイドル・最大8時間、Instancesは最大14日）、終了時にメモリはサニタイズされ、同一 `runtimeSessionId` での再呼び出しは**新しい実行環境を生成**する。状態は必ず外部化（AgentCore Memory等）が必要。これは12-factor Factor 12（ステートレス・リデューサ）の直接的帰結。

3. **メモリの二層化**：ほぼ全プラットフォームが「短期＝セッション内会話」と「長期＝ユーザー横断の抽出済みメモリ」を別サービスとして分離。書き込みトリガーの責任所在が設計上の分岐点：AgentCoreは `CreateEvent` が戦略ACTIVE時に非同期抽出を起動、Vertex Memory Bankは `GenerateMemories`（SDKはブロッキング、ADKの `add_session_to_memory` は非ブロッキング）。

4. **持続実行（Durable Execution）**：決定論的アウターループと非決定論的インナー呼び出し（LLM/ツール）の分離が共通原理。Temporalはワークフロー（決定論・リプレイ可能）とアクティビティ（副作用）を分離し、履歴が肥大化すると Continue-As-New を推奨。LangGraphはチェックポインタ＋thread_idで同等。DBOS/Restate/Inngestも同型だが冪等性の責任はいずれも開発者に残る。

5. **人間参加（HITL）は一時停止可能な状態遷移**：承認は「ツール呼び出し」としてモデル化され、待ち時間がセッション/アイドルタイムアウトを超える場合はセッション外の持続層へ押し出す必要がある。12-factor Factor 6（Launch/Pause/Resume）・Factor 7（Contact humans with tool calls）に対応。

6. **アイデンティティとツールアクセスの外部化**：エージェントを第一級プリンシパルとして扱う潮流。AgentCore IdentityはOBOトークン交換（RFC 8693/RFC 7523）、Vertex AIはSPIFFEベースのAgent Identity（X.509バインド）、Microsoftは1エージェント1つのEntra Agent ID。ゲートウェイ経由のツール呼び出しと事前ポリシー適用が共通。

7. **ストリーミング/イベント契約**：SSEが標準。AgentCoreはAG-UIプロトコル（RunAgentInput形式）をサポートするが、**ペイロード検証はコンテナ側の責任**（プラットフォームは検証せず素通し）。

### プラットフォーム別具体制約

**Amazon Bedrock AgentCore**
- コンテナ契約：HTTP=`/invocations`+`/ping`+8080、MCP=`/mcp`+8000（ステートレスstreamable-http必須）、A2A=`/`+9000。全プロトコルでARM64（Graviton）必須、x86は起動しない。ホストは`0.0.0.0`。
- コンピュート：microVM（既定・最大8時間・CPUのみ）対Instances（最大14日・GPU/Inferentia2可・EBS永続化）。コンピュートタイプは作成後変更不可。Instancesでは同一ホスト上の同居エージェント間はセキュリティ境界がなくファイルシステム共有（AWS明記）。
- セッション：1セッション=1 microVM、既定15分アイドル/8時間上限（設定可能）、呼び出しタイムアウトは同期15分・ストリーミング60分・非同期8時間（調整不可）。終了時メモリサニタイズ、同一sessionIdでの再呼び出しは新環境。`HealthyBusy` pingステータスでバックグラウンド作業中のセッション維持（アイドルHealthyは15分で終了）。
- デプロイ：直接コードデプロイ（Python 3.10-3.13/Node.js 22、zipをS3へ、arm64依存が必須、Node.jsは2026年4月追加）またはコンテナ。
- MCP：ステートレス必須、プラットフォームが`Mcp-Session-Id`ヘッダを自動付与。MCP 2026-07-28仕様でセッション概念自体が廃止（handshakeとMcp-Session-Idを削除、各リクエストが自己完結）。
- Identity：OBOトークン交換（RFC 8693/7523）、`X-Amz-Bedrock-AgentCore-Identity-WAT`ヘッダをリクエストごとに読む必要（キャッシュすると別ユーザーの操作が誤帰属される）。インバウンドはIAM SigV4またはOAuth 2.0。ヘッダは既定でストリップされallowlist必須。2026年に Consent Portal 追加。
- Policy：Cedarポリシーによる事前実行制御（プレビュー）。
- 課金：AWS公式料金（CloudBurnがAC-P-01〜06として引用）——CPU **$0.0895/vCPU時間**（実CPUサイクルのみ課金、I/O待ちは非課金）、メモリ **$0.00945/GB時間**（ピークメモリ・セッション全体・秒課金、128MBフロア・1秒最低課金）。I/O待ちが70%を占めるセッションでAWSは最大3.3倍のCPU節約を提示。12の独立課金コンポーネント。
- Observability：OpenTelemetry互換、CloudWatch、Runtime上ではゼロコード計装。2026年7月20日以降、新規エージェントは`UNIFIED_TRACES_DESTINATION_ENABLED`によりエージェント固有ロググループを既定使用。
- VPC：全サービス（Runtime/Memory/Gateway/Browser/Code Interpreter/Identity/Observability）でVPCコネクティビティ対応。

**Google Vertex AI Agent Engine**（Sessions/Memory BankはGA 2025年12月17日、Code Execution GA 2026年2月18日、課金開始2026年2月11日）
- デプロイ：Pythonのみ、staging bucket（GCS）＋requirements.txt。`adk deploy agent_engine`。
- Sessions（短期）とMemory Bank（長期・LLM抽出）を分離。session TTL設定推奨。
- Code Execution：サンドボックス。VPC-SC/PSC-I有効時の同時実行範囲は[1,100]。
- 同時実行：`container_concurrency`既定9（Google推奨値 `2 * cpu + 1`）。同期コードは1コンテナ1リクエスト、ADK等の非同期エージェントは複数I/Oバウンドリクエストを並行処理可、高すぎるとOOMリスク。
- Identity：SPIFFEベースのAgent Identity、Google Cloud用トークンはX.509証明書にバインドされトークン窃取を防止、IAM allow/denyポリシー、ゼロ権限から開始。未設定時はサービスアカウントにフォールバック。Agent Identity auth managerがOAuth認可を自動化。
- 課金：Runtime vCPU単価は2025年12月16日の値下げ後 **$0.0864/vCPU時間**（AgentCoreの$0.0895に近接）、Sessions/Memory Bankは2026年1月28日以降 **$0.25 per 1,000 events or memories**。
- A2A由来、ADK統合。

**Microsoft Foundry Agent Service**（Agent Service本体はGA、ただしhosted agentsコンピュート層は2026年4月時点でパブリックプレビュー）
- スレッド/ラン/メッセージモデル：スレッド状態は永続・サービス管理（Standard構成はCosmos DB、Basic構成はMicrosoft管理ストレージ）、コンテキスト自動切り詰め。ランには`expired`（時間制限超過）ステータスあり（具体的な数値タイムアウトは非公開）。
- 固定制限（**"can't be increased"** とMicrosoft Learn明記）：スレッドあたり最大**100,000メッセージ**、エージェントあたり最大**128ツール**、エージェント/スレッドあたり最大**10,000ファイル**、プロンプトエージェントのファイルアップロード最大**512MB**、全アップロード合計最大**300GB**、ベクターストア添付は1ファイル最大**2,000,000トークン**、メッセージのtext最大**1,500,000文字**、エージェントあたり最大**1,000バージョン**（超過時HTTP 400）。
- 同時hosted agentセッション：サブスクリプション×リージョン単位で**2,000**（Canada Central、East US 2、Japan East、North Central US、South Africa North、Southeast Asia、Sweden Central）または**1,000**（その他）。アイドル/停止セッションはクォータに計上されない。サポートリクエストで増加可能（リージョン容量に依存）。
- Identity：1エージェント1つのEntra Agent ID（GA）。
- 統合：Microsoft Agent Framework v1.0（Semantic Kernel + AutoGenの統合、GA、`agent-framework-foundry`パッケージ）、`azure-ai-projects` SDK。任意フレームワーク（LangGraph、OpenAI Agents SDK、Claude Agent SDK等）をDockerfileでhosted agentsにデプロイ可（`azd deploy`）。scale-to-zeroとファイルシステム永続化（"files, disk state, and session identity persist across scale-to-zero events"）。

**Cloudflare Agents SDK / Durable Objects**
- アクターモデル：1エージェント=1 Durable Object、それぞれ埋め込みSQLite（2025年4月7日GAで**10GB/オブジェクト**、Freeプランは1GB）、独自WebSocket、独自スケジューラ。単一ライタ。テナント分離はアーキテクチャ的（別エージェント=別オブジェクト=別DB）。
- ハイバネーション：アイドル時にコンピュートゼロへ退避、リクエスト/WebSocketメッセージ/アラームで復帰。退避は通常70-140秒の無活動で発生。`this.state`（`setState()`でSQLiteに永続化）は生存、インメモリ変数・setTimeout/setInterval・進行中fetchは失われる。
- CPU制約：Durable Object呼び出し（HTTPリクエスト/WebSocketメッセージ/アラーム）あたり最大CPU時間は既定30秒（`limits.cpu_ms`で最大5分に設定可能）。**「CPU時間はアクティブ処理時間であり、ネットワーク・ストレージ・I/O待ちは計上しない」**——AgentCoreと同型のI/O非課金構造。
- `keepAlive()`（アラーム・ハートビート）で長時間処理中の退避を防止。cron/queueスケジューリング、MCPサーバホスティング（McpAgent）。

**持続実行エンジン**
- Temporal：ワークフロー（決定論・リプレイ）＋アクティビティ（副作用・自動リトライ）。イベント履歴でリプレイ、履歴肥大時はContinue-As-New推奨。OpenAI Agents SDK公式統合（`temporalio.contrib.openai_agents`）は**2026年3月23日GA**（Temporal公式ブログ："As of March 23rd, 2026, the integration between the OpenAI Agents SDK and Temporal's Python SDK is now Generally Available."、2025年7月プレビュー）、Python 3.10+。
- Restate：仮想オブジェクトモデル、低レイテンシ、ジャーナルで完了ステップをスキップ。
- DBOS：Postgresネイティブ、ステップレベルのメモ化、未完了ステップのみ再実行（副作用は冪等必須）。
- Inngest：ステップ単位課金。20ターン×（モデル呼び出し1＋ツール呼び出し1）で約41実行。通常タスクはat-least-once、冪等性は開発者責任。

### 各パターン比較表

#### P1 ランタイム契約／ホスティング・アダプタ層
| 項目 | 内容 |
|---|---|
| なぜ課すか | プラットフォームがルーティング・スケーリング・ヘルスチェックを管理するため固定インターフェイスが必要 |
| AgentCore | HTTP:8080 `/invocations`+`/ping`、MCP:8000 `/mcp`、A2A:9000 `/`、ARM64必須、host `0.0.0.0` |
| Vertex AI | コンテナ内部隠蔽、Python限定、requirements.txt、`container_concurrency`既定9（`2*cpu+1`推奨） |
| Foundry | スレッド/ラン/メッセージAPI、hosted agentsはDockerfileでBYO（`azd deploy`） |
| Cloudflare | コンテナではなくDurable Objectクラス（`extends Agent`）、`routeAgentRequest` |
| 回避策/推奨 | buildxでarm64ビルド、CodeBuild利用；`/ping`は既存`/health`と別に追加 |
| 設計時決定 | CPUアーキ、ポート、プロトコル選択、パッケージング方式 |
| 後から適応可 | エンドポイント内部ロジック、依存追加 |

#### P2 セッション境界と揮発性状態
| 項目 | 内容 |
|---|---|
| なぜ課すか | セッション分離によるセキュリティ、サーバーレス・スケーリング、揮発性コンピュート |
| AgentCore | 1セッション=1 microVM、15分アイドル/8時間（Instances14日）、終了時サニタイズ、再呼び出しで新環境 |
| Vertex AI | Sessions（短期）、session TTL、`container_concurrency` |
| Foundry | スレッドは永続（Cosmos DB）、ラン`expired`ステータス、hosted agentsはscale-to-zeroでファイルシステム永続 |
| Cloudflare | Durable Object＝永続、ハイバネーション70-140秒、SQLite生存・インメモリ喪失、CPU時間上限30秒（最大5分） |
| Temporal他 | ワークフロー状態は履歴で永続 |
| 回避策/推奨 | 状態外部化（Memory/DB）、安定sessionId採番、`HealthyBusy`通知 |
| 設計時決定 | セッションID戦略、状態外部化方式、アイドル/最大寿命設定 |
| 後から適応可 | 保存頻度、外部ストア選択 |

#### P3 メモリの層化
| 項目 | 内容 |
|---|---|
| なぜ課すか | セッション内コンテキストとユーザー横断の永続知識は寿命・スコープ・課金が異なる |
| AgentCore | 短期=イベント、長期=戦略（semantic/summary/user preference）；`CreateEvent`が戦略ACTIVE時に非同期抽出起動；`event_expiry_days`で短期の自動削除 |
| Vertex AI | Sessions（短期）＋Memory Bank（長期、LLM抽出）；SDKの`generate_memories`はブロッキング、ADKの`add_session_to_memory`は非ブロッキング |
| Foundry | スレッドが会話履歴を自動管理、既定でメモリを用いた文脈連続性 |
| 回避策/推奨 | 書き込みトリガーの責任を明示、namespaceでactor/session分離、memory poisoning対策 |
| 設計時決定 | 短期/長期の分離、抽出戦略、書き込みトリガーの所在 |
| 後から適応可 | 抽出トピック、few-shot、保持期間 |

#### P4 持続実行
| 項目 | 内容 |
|---|---|
| なぜ課すか | 長時間・失敗しやすい・高コストなLLM/ツール呼び出しをクラッシュ越しに回復 |
| AgentCore | Runtime単体は持続層でない；非同期8時間、状態外部化前提 |
| LangGraph | チェックポインタ＋thread_id、interrupt前コードは再実行→冪等必須、本番はPostgres/SQLiteセーバー |
| Temporal | ワークフロー/アクティビティ分離、リプレイ、Continue-As-New |
| DBOS/Restate/Inngest | メモ化/ジャーナル、冪等性は開発者責任、Inngestはステップ単位課金 |
| Cloudflare | Durable Object＋Workflows、CPU時間I/O非課金 |
| 回避策/推奨 | ツール呼び出しをステップ境界に、冪等キー、完了シグナルを明示 |
| 設計時決定 | 持続層採用の有無、ステップ境界、冪等性設計 |
| 後から適応可 | リトライポリシー、タイムアウト値 |

#### P5 一時停止可能な状態遷移としてのHITL
| 項目 | 内容 |
|---|---|
| なぜ課すか | 承認待ちは人間レイテンシ（分〜日）でセッションタイムアウトを超える |
| AgentCore | Gatewayがelicitation対応（streaming+sessions必須）；長時間承認はセッション外へ |
| LangGraph | `interrupt()`＋durable checkpointer、`Command(resume=...)`で再開、paused runにタイムアウトポリシー必須 |
| Temporal | Signal/timerで待機状態をクラッシュ越しに保持 |
| 回避策/推奨 | 承認をツール呼び出しとしてモデル化、待ちを持続層へ、放置runの自動却下ポリシー |
| 設計時決定 | 承認境界の配置、待ちの持続化方式 |
| 後から適応可 | 承認UI、タイムアウト値 |

#### P6 アイデンティティとツールアクセスの外部化

### ポータビリティとヘキサゴナル層化

**プラットフォーム固有（アダプタ層）**：HTTP契約エンドポイント、セッションID意味論、認証ヘッダ処理、デプロイ・パッケージング、課金最適化、VPC構成。

**ポータブル（コア層）**：エージェントループ（制御フロー）、ツール定義、プロンプト、状態スキーマ。

**推奨構成**：
- **ドメインコア**：ステートレス・リデューサとしてのエージェントループ（12-factor Factor 8「制御フロー自己所有」、Factor 12）。イベントログ（Thread）を単一の真実源とし実行状態と業務状態を統合（Factor 5）。
- **ポート**：`SessionStore`、`MemoryService`、`ToolGateway`、`EventStream`、`IdentityProvider`を抽象インターフェイスとして定義。
- **アダプタ**：各プラットフォームのHTTP契約・認証・パッケージングを実装。AgentCoreなら`/invocations`ハンドラ、Cloudflareなら`Agent`クラス、Vertexなら`adk deploy`パッケージ、Foundryならスレッド/ランAPIまたはDockerfile。
- **移植の実証例**：Richard Seroter氏がADK＋Vertex Memory Bankで書いたエージェントをCloud RunとAgent Engineの両方に移植した事例が、コア層とアダプタ層の分離が実際に機能することを示している。

### 実務ピットフォール
- 呼び出しごとにfresh session IDを発行 → 毎回新microVM＝コールドスタート（実務ブログでは約6秒）を「クライアントやモデルや距離のせい」と誤帰属。
- ヘルスチェックがbusyを通知しない → バックグラウンド作業中にスケールダウン（`HealthyBusy`未使用、アイドルHealthyは15分で終了）。
- リプレイ下で非冪等ツール → 二重予約・二重送信（LLMツール呼び出しは本質的に非冪等）。
- 承認待ちがアイドルタイムアウト超過 → セッション消失。持続層へ押し出すべき。放置runの自動却下ポリシーも必要。
- MCPがステートフル前提 → AgentCoreはステートレス必須、各リクエストが別コンテナにルーティングされ400 Bad Request。
- LangGraph interrupt前のAPI課金コード → 再開時にノードが先頭から再実行され二重課金。
- x86イメージをデプロイ → AgentCoreで無言のimportエラーまたは起動失敗。
- WATトークンやユーザートークンのキャッシュ → 別ユーザーの操作が誤帰属。
- 単一Durable Objectへの高スループット集中 → 単一ライタでボトルネック（シャーディング必要）。

## Recommendations

**段階1（アーキテクチャ確定前・最優先）**：以下をコード記述前に決定せよ。
1. CPUアーキテクチャをARM64に固定（AgentCore対象時）。CIをarm64ビルド（buildx/CodeBuild）に。
2. コンピュートタイプ選択：短時間対話ならmicroVM、数時間〜数日／GPU必要ならInstances。作成後変更不可のため慎重に。
3. セッションID採番戦略：安定した会話単位IDを再利用（毎回発行しない）。コールドスタート多発を防ぐ。
4. 状態外部化方式：全状態を外部ストア（AgentCore Memory/DB/チェックポインタ）へ。インメモリ依存を排除（12-factor F12）。
5. ツールを冪等に設計し、冪等キーを付与。リプレイ・リトライ下の二重副作用を防ぐ。

**段階2（設計）**：
6. ヘキサゴナル層化を採用し、ポート＆アダプタでコアをプラットフォーム非依存に。マルチクラウド移植性を確保。
7. 承認・長時間待ちは持続実行層（Temporal/LangGraphチェックポインタ/Durable Object）へ押し出す。セッションタイムアウトを超える待ちをセッション内に置かない（F6/F7）。
8. メモリ書き込みトリガーの責任を明示（誰がいつ長期メモリへ書くか）。memory poisoning対策も設計に含める。
9. アイデンティティを第一級プリンシパルとして設計、ゲートウェイ経由・事前ポリシー、OBO/委譲を明示。

**段階3（運用）**：
10. OpenTelemetry計装をセッション/トレース/スパン三層で。`trace_attributes`にsession.idを付与。
11. 課金単位を理解し設計（I/O待ち非課金を活かす、Inngestならステップ数を課金に照らす、session TTLでストレージ費抑制）。

**判断を変える閾値**：
- 同時500クエリ超や50ms未満のリコール要求ならマネージド・ベクター基盤へ移行を検討。
- Temporalで履歴肥大によりリプレイが遅ければContinue-As-New。
- 単一Durable Objectがホットスポット化すればコーディネータ＋シャーディングへ。
- Foundryで同時セッションが1,000/2,000上限に近づけばサポートリクエストで増枠、またはリージョン分散。
- AgentCoreで8時間microVM壁に当たる長時間ジョブはInstances（最大14日）へ。

## Caveats
- **プレビュー機能に注意**：AgentCore Policy（Cedar）、managed harness、最適化機能（recommendations/A/Bテスト・batch評価）はプレビュー。Foundry hosted agentsコンピュート層は2026年4月時点でパブリックプレビュー（Foundry Agent Service本体はGA）。Vertex Agent Identityの詳細は進化中。
- **日付明記**：AgentCore Node.js直接デプロイは2026年4月、Temporal OpenAI統合GAは2026年3月23日、MCPステートレス仕様は2026-07-28、Vertex Sessions/Memory Bank GAは2025年12月17日・課金開始2026年2月11日、Cloudflare SQLite in Durable Objects GAは2025年4月7日、Foundry Entra Agent ID GAは一次ソースで確認（具体的なGA日付「約2026年5月1日」は第三者ブログ由来で一次未確認）。
- **数値タイムアウトの非公開**：Foundryのラン`expired`の具体的秒数、およびAgentCoreコールドスタート秒数（実務ブログの約6秒）は公式には非公開／環境依存の目安。
- **一部制約は設定可能vs固定が混在**：AgentCoreのアイドル/最大寿命は設定可能だが同期15分・ストリーミング60分・非同期8時間の呼び出しタイムアウトは調整不可。Foundryのファイル/メッセージ/ツール制限は固定で増加不可（Microsoft Learn明記）、セッション同時実行数はサポート経由で増加可。
- **料金の変動性**：Vertexは2025年12月に値下げ、AgentCoreは12コンポーネント構成で複雑。単価は本レポート作成時点（2026年9月）のものであり、必ず各社公式料金ページで最新値を確認すること。
- 一部の具体的数値（Cloudflareの退避70-140秒、AgentCoreコールドスタート約6秒）は公式ドキュメントではなく実務ブログ由来であり、環境依存の目安として扱うべき。
