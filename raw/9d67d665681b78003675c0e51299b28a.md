# 第1部：概要・技術・採用判断

TypeSafe AI の「Jev（ジェヴ）」は2026年9月15日に発表されたばかりの新しいモデルで、一次資料（公式ブログ・ドキュメント）と第三者の報道を突き合わせて整理しました。採用可否の判断材料になるよう、仕様・根拠・既知の弱点・リスクを分けて書きます。

## 1. 何者か（概要と会社）

TypeSafe AI は2026年9月15日にステルスを脱し、DCVC がリードするシード資金4,000万ドルを調達した。創業者は元 OpenAI 研究者で RLHF/ChatGPT の共同発明者とされる Diogo Almeida と、Erik Gafni、Sasha Sheng。2024年創業、本社サンフランシスコです。

Jev の位置づけは「テキストを生成しない AI モデル」です。文字列を1トークンずつ生成する代わりに、非構造化のプログラム状態を入力として受け取り、型付きの確率的な判断を1回の並列パスで返す設計で、同社はこれを「System One モデル」という新カテゴリと呼んでいます。名前はカーネマンの『ファスト＆スロー』のシステム1（速く直感的な思考）に由来し、Jev はジェヴォンズのパラドックスにちなむとのことです。

要するに「LLM の代替」ではなく、**コードの中の if 文を意味的な判断で置き換える部品**として設計されています。同社自身も、用途を「AI を組み込んだワークフロー／賢い if 文（分類・ルーティング・スコアリング・抽出・分岐）」「ビッグデータの map-reduce」「100ms 級のリアルタイム用途」「LLM の出力検証・ガードレール・ジェイルブレイク検知」に限定して説明しています。

## 2. 技術的な仕組み（公開されている範囲）

同社は自動化に特化した新スタックとして、新しいモデルアーキテクチャ、効率最大化のための並列サンプラー、および RLCD（Reinforcement Learning for Calibrated Decisions）と呼ぶ学習手法を構築したと述べています。RLHF/RLVR が人間の選好や検証可能な報酬を最適化するのに対し、RLCD は「認識論的に正直な確率を伴う較正された判断」を最適化する、というのが同社の整理です。

速度の源泉は逐次生成をしないことです。LLM は次トークンを逐次予測するが、System One アーキテクチャはクエリへの全出力を一度に返すため、質問数が増えてもレイテンシがほぼ増えないとされます。

「ハルシネーションしない」の意味は限定的なので注意が必要です。TypeSafe が「ハルシネーションしない」と言うのは許可された答えからしか選ばないという意味で、この保証は答えの形式に関するもの。許可された選択肢を選んでも判断自体は誤りうる、と The Rundown も指摘しています。同社もこれは否定しておらず、型エラー0%という数値は実測ではなく、スキーマ一致が保証されているため定義上0%だと明記しています。

なお、モデルの詳細（パラメータ数、ベースモデル、学習データ）は公開されていません。公式ブログの FAQ に「Jev はただの小さい LLM か」「学習データはどこから」という項目がありますが、取得したページでは回答本文が展開されていませんでした。

## 3. API の形（実装者向け）

エンドポイントは1つです。`POST https://api.typesafe.ai/v1/systemone` に Bearer トークンで認証し、`state`（string / object / array）、`model`、`questions`（自分でキーを付けた質問のマップ）を送る形です。質問のキーは推論には使われず、同じキーで答えが返るため、コード側での取り回しは容易です。

質問は3種類（プリミティブ）だけです。

- **Noul**（yes/no）: yes である確率を返す。`criteria` で yes/no の意味を任意に定義できる。
- **Choice**（選択）: 定義した選択肢から1つ選び、選ばれた `choice`、全選択肢の確率分布（合計1）、`confidence` を返す。
- **Score**（順序付き段階評価）: 順序付きのレベル配列（最低2つ）に対し、確率加重した `score`（レベルの間の値もとりうる）、`legend`、各レベルの確率、`confidence` を返す。

3種類は1回の API 呼び出しに混在でき、すべての質問が同じ state に対して並列かつ独立に評価される。質問を追加しても応答時間はほとんど変わらず、各質問が独立なので context rot が起きないとされています。設計哲学として 各質問は「知識のある人が数秒で下せる直感的判断」程度に絞り、複数要因を含む判断は分解してコードで合成することが強く推奨されています。

SDK は Python（`typesafe_sdk`）と JavaScript（`@typesafe-ai/sdk`）が公式にあります。エラーは 401/422/429/529 で、429 と 529 は指数バックオフで再試行する。公式 SDK はデフォルトで自動処理します。Claude Code や Codex などのエージェント環境向けの「Agent skill」も用意されています。

## 4. スペック・価格・制限（jev-1.13.0 時点）

現行モデルは Jev 1.13（`jev-1.13.0`）。価格は入力 $0.042/Mtok（$42/Btok）で出力トークンは無料。レート制限は 250,000 tokens/秒・1,200 requests/分。コンテキストは1リクエスト64kトークン（state と全質問の合計）、かつ state と最長の質問の合計で32kトークン。入力はテキストのみで、画像・音声・動画は不可。

留意点がいくつかあります。

- レート制限は動的に調整中で、予告なく変わりうる。より高い上限はカスタム／エンタープライズプランで対応。
- `jev-latest` と `jev-preview` というエイリアスがあり、エイリアスは新リリースで移動するため、confidence の閾値を特定バージョンに合わせて調整した場合はバージョン ID を固定すべき。これは本番運用では重要です。
- Jev は顧客データでファインチューニングや LoRA 適用はされず、全アカウントが同じ重みを使う。ドメイン適応は `state` に自社データを入れ、`instructions` と `criteria` にルールや境界事例を書き込む形で行う。
- **日本語**: 英語が主要学習言語で精度も最良。CJK を含む他言語は「扱えるが同等ではない」とされ、非英語ワークロードでは自社コンテンツで検証し confidence に注意して振り分けることを推奨しています。日本企業の採用判断ではここが最大の検証ポイントになります。
- サービスは現在米国西海岸ベースとのことなので、日本からのレイテンシは同社公表の 70〜500ms に太平洋往復分（概ね 100ms 以上）が乗ると見込むべきです。国内リージョンの有無は資料にありません。

## 5. 性能の根拠と、その読み方

同社は自前の「ワークフロー評価」を主な根拠にしています。正解ラベルではなく、コードで表現された「正しい計算グラフ（ワークフロー）」を固定し、最大級の外部モデル（GPT-6 Astra と Fable 5.1）の予測確率の平均を参照値として、各モデルがどれだけ一致するかを測る方式です。この4ワークフローのベンチマークで Jev は約68%の精度で、中位 LLM（GPT-5.6 Terra）に近く、40〜400倍安く20〜200倍速いとまとめられています。

同社が自ら挙げている留保は評価に値します。ホームページの「193.6倍速い・444.6倍安い」は実世界の上限寄りであること、ワークフローは自社チームが作ったので偏りの可能性があること、参照値が OpenAI/Anthropic のモデル平均なのでその2社に有利に働くこと、LLM 側は同社の System One アダプタで構造化出力を強制しており通常の使い方より遅く高価になることを明記しています。

第三者の見立ても慎重です。参照答えは GPT-6 Astra と Claude Fable 5.1 の判断の平均であり、それらとの一致は Jev の判断の正しさの一部しか示さない。総コストはワークロードと周辺インフラに依存する（The Rundown）。「質問数を増やしてもレイテンシがほとんど増えない」という主張は第三者による計測を見たい（Anthony Maio）。また較正の意味についても、「80%の確率を付けた予測群のうち約80%が正しい」という母集団の性質であって、個々の答えが正しいかは分からないという指摘があります。

つまり **「フロンティア級」というより「中位 LLM 相当の判断を2桁安く速く」** と読むのが妥当で、独立した検証はまだ存在しません（発表から3日）。

## 6. 公式に認められている弱点（Jaggedness ページ）

同社は Jev 1.13 の失敗モードを公開しており、採用検討ではこれが最も実用的な資料です。Jev は速く較正され常識的判断は得意だが完璧ではなく、追加の間接参照を要するタスクに弱く、かなり字義通りに解釈し、数値精度を要するタスクが苦手。

具体的には：

- **字義通り解釈**: 書かれた質問に答え、意図した質問には答えない。スコープ語、否定、暗黙条件は額面通り読まれる。
- **計算・カウント**: 文字数、出現回数、長いリストの要素数を信頼性高く数えられない。数え上げはコードで行い、要素ごとに Noul を投げて合計することが推奨。hex や RGB のような数値表現より英語の色名のような意味表現の方が良く、Score の期待値から正確な数値を補間で復元してはいけない。
- **日付比較**: 日付をテキストとして読むため、前後関係・期間・ウィンドウ内判定は信頼できない。年月日を Choice で抽出し、比較はコードで行う。
- **大きな state**: 判断に無関係な内容が増えると精度が落ちる。コードで事前にフィルタし、必要なフィールドだけ送る。
- **敵対的コンテンツ**: state はデータとして扱われ、デフォルトで敵対的とは見なさない。注入された命令や誘導的な文章は答えを動かしうる。ガードレール用途に売り込んでいる一方でこの制限があるので、プロンプトインジェクション検知に使うなら自社でレッドチームが必須です。
- **生成不可**: Choice を連鎖させて無理やり生成することもできるが、うまく動かず非常に遅い。抽出は regex や生成モデルで候補を出し、Jev に選ばせる。

## 7. データ取り扱い・法務

Jev は顧客のリクエスト／レスポンスで学習しないとされ、DPA、Master Customer Agreement、プライバシーポリシーが公開されており、エンタープライズ向けにゼロデータリテンション（ZDR）を提供しています。データ所在地（米国以外のリージョン）、SOC 2 / ISO 27001 等の認証、SLA については取得した資料に記載がなく、営業（sales@typesafe.ai）に確認が必要です。

## 8. 提供状況

早期アクセスを開放し、ウェイトリストから順次開発者を招待している段階で、一般提供（GA）ではありません。設立2年・発表3日・シード段階の単一ベンダーであり、価格が補助金的でないことは証明できず、長期的な持続性を示す必要があると同社自身が認めています。ベンダーロックインという観点では、API は極めて単純（state + 3種類の質問）なので、同じインターフェースを LLM の構造化出力で再現するアダプタを自前で持てば切り替えコストは低く抑えられます（同社も LLM 向けの System One アダプタを GitHub で公開しています）。

## 9. 採用判断のための整理

**向いている**: 分類・ルーティング・優先度付け・重複判定・リランキング・RAG パッセージの関連性判定・LLM 出力の事後検証など、答えの集合が事前に定義でき、大量・高頻度・低レイテンシで、確率と confidence を使って自動処理と人手レビューを振り分けたい処理。公式クックブックにはリランキング、階層分類、エンティティ照合、引用の検証、LLM ガードレール、日付抽出、関数呼び出しのマッピングなどが揃っています。

**向いていない**: 生成、要約、説明文、複数ホップの推論、算術、日付演算、コンテキストが巨大な処理、そして（現時点では）日本語が主体で精度要求が厳しい処理。

**PoC で検証すべき項目**:
1. 自社の日本語データでの精度（英語で同じタスクを試して差分を見る）と、confidence と正答率の較正の実測。
2. 東京からの実効レイテンシ（p50/p99）と、動的レート制限の実運用での挙動。
3. 既存の LLM 構造化出力パイプラインとの総コスト比較（Jev は入力課金のみだが、state のフィルタリングや抽出候補生成に別モデルが要ると相殺される）。
4. 自社ドメインでのプロンプトインジェクション耐性。
5. 契約面：データ所在地、SLA、ZDR、価格の据え置き保証、エイリアスではなくバージョン固定での提供継続期間。

総じて、コンセプトは筋が良く（判断とポリシーの分離、較正された確率、型安全な出力）、価格・速度が主張通りなら「賢い if 文」用途で LLM を置き換える価値は大きい一方、**独立検証ゼロ・早期アクセス・英語中心・スタートアップ単一依存**という状態なので、現時点の妥当な判断は「本番採用ではなく、限定的な非クリティカル用途で PoC を回しつつ、LLM 構造化出力へのフォールバックを設計しておく」だと思います。

# 第2部：スキーマとインターフェース


スキーマとインターフェースを、公式ドキュメント・SDK・第三者実装（Vercel AI SDK プロバイダ）から確認できたものと、確認できず推測で補ったものを明確に分けて整理します。凡例は **【確認済】** = 一次資料に記載あり、**【推測】** = 資料に記載がなく設計や周辺情報からの推定です。

## 1. HTTP API の契約【確認済】

エンドポイントは1つで、`POST https://api.typesafe.ai/v1/systemone`、`Authorization: Bearer <API_KEY>`、`Content-Type: application/json` です。リクエストは `state`（string | object | array、必須）、`model`（string、必須）、`questions`（自分でキーを付けた Question のマップ、必須）の3フィールド。キーは推論には使われず、同じキーで回答が返ります。

確認済の内容を TypeScript 風の型定義に起こすと次のようになります（型名は説明用に私が付けたもので、公式の名称ではありません）。

```ts
// ---- Request ----
type JsonValue = string | number | boolean | null | JsonValue[] | { [k: string]: JsonValue };

interface SystemOneRequest {
  state: string | object | any[];        // 評価対象。文字列 or 構造化データ
  model: "jev-latest" | "jev-preview" | "jev-1.13.0" | string;
  questions: Record<string, Question>;   // キーは任意。推論には非使用
}

type Question = NoulQuestion | ChoiceQuestion | ScoreQuestion;

interface NoulQuestion {
  type: "noul";
  instructions: string | object | any[];   // yes/no の質問文
  criteria?: { true?: string; false?: string }; // 任意。yes/no の意味を補足
}

interface ChoiceQuestion {
  type: "choice";
  instructions: string | object | any[];
  criteria: Record<string, string | null>; // 選択肢 → 説明（null 可）。必須
}

interface ScoreQuestion {
  type: "score";
  instructions: string | object | any[];
  criteria: string[];                       // 順序付きレベル。最低2つ。必須
}

// ---- Response ----
interface SystemOneResponse {
  model: string;                            // 実際に応答したバージョン ID
  answers: Record<string, Answer>;          // 質問と同じキー
  usage: { input_tokens: number; output_tokens: number };
}

type Answer = NoulAnswer | ChoiceAnswer | ScoreAnswer;

interface NoulAnswer   { type: "noul";   noul: number; }             // 0..1、yes の確率
interface ChoiceAnswer { type: "choice"; choice: string;             // 最大確率の選択肢
                         probabilities: Record<string, number>;      // 合計≈1
                         confidence: number; }                       // 0..1
interface ScoreAnswer  { type: "score";  score: number;              // 確率加重、レベル間の値も可
                         legend: Record<string, string>;             // "0": "Calm", ...
                         probabilities: Record<string, number>;      // レベル番号(文字列)→確率
                         confidence: number; }
```

回答側の補足：Noul 回答は `noul` のみ、Choice と Score には確率分布から導出した 0〜1 の `confidence` が付きます。Score の `score` はレベル間の値をとり、`legend` は各レベル番号を説明にマップし直したものです。

エラーは 401（認証）、422（バリデーション失敗、本文に問題フィールドの詳細）、429（レート制限）、529（過負荷）で、429/529 は指数バックオフで再試行します。応答に `retry-after` ヘッダが乗る場合があり、公式 SDK はこれを尊重します。

### 数値上の制約

- Choice の選択肢は最大 255 個（Wikiracing デモの説明で明記）。Vercel の AI SDK プロバイダ側では Choice が1〜255 選択肢、Score が2〜10 段階と記載されています。Score の上限10は AI SDK 側の記述のみで、TypeSafe 公式 API リファレンスには「最低2つ」しか書かれていません（上限が API 由来かプロバイダ由来かは未確認）。
- スコアと確率は小数第2位に丸めて返されるため、確率の合計が厳密に1にならないことがあります。しきい値判定のコードでは `sum == 1.0` を前提にしないでください。
- コンテキストは state と全質問の合計で 64k、state と最長質問の合計で 32k トークン。

### `instructions` / `criteria` の構造化【確認済（詳細は一部推測）】

ドキュメント索引に「Advanced: structure — Instructions, Choice options, Score levels, Noul criteria all accept JSON structure」というページがあり、AI SDK の例でも `billing: { includes: ['Charges', 'Invoices', 'Refunds'] }` や `technical: ['Bugs', 'Outages']` のように選択肢の説明にオブジェクトや配列を渡しています。つまり `criteria` の値は `string | null` に限らず JSON 構造が許容されます。ただし **`includes` のようなキーに特別な意味があるのか、それとも単に JSON として文字列化されてモデルに渡るだけなのかは未確認**（推測では後者、つまり自由形式）。この Advanced ページは今回取得できなかったので、実装前に必読です。

structured な state を使う場合、質問文の中でバッククォート付きのドット／インデックスのパス（例：`` `ticket.messages[0].text` ``）で該当フィールドを指す書き方が公式に推奨されています。

## 2. Python SDK（`typesafe_sdk`）

**【確認済】** インストールは `uv add typesafe-sdk`（pip でも同名と推測）。`TYPESAFE_API_KEY` を環境変数に設定し、`TypeSafeClient` をコンテキストマネージャとして使い、`client.system_one(state=..., questions={...})` を呼びます。`questions` には `Choice`, `Noul`, `Score` のオブジェクトを渡します。

```python
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

with TypeSafeClient() as client:          # または TypeSafeClient(model="jev-1.13")
    response = client.system_one(
        state={"ticket": "...", "account_tier": "business"},
        questions={
            "intent": Choice(instructions="...", criteria={"refund": "...", "other": None}),
            "is_urgent": Noul(instructions="..."),
            "frustration": Score(instructions="...", criteria=["Calm", "Concerned", "Very angry"]),
        },
    )

# 回答へのアクセス（いずれも実例で確認）
response.answers["intent"].choice          # 汎用: answers[key]
response.answers["intent"].probabilities
response.answers["is_urgent"].noul
response.answers["frustration"].score
response.choices["intent"].choice          # 型別ビュー: choices / nouls
response.nouls["is_urgent"].noul
```

確認できた要素：
- `TypeSafeClient(model="jev-1.13")` のようにコンストラクタでモデル指定可（Jaggedness ページのコード例）。
- `questions` は SDK オブジェクトでも dict（生 JSON）でも渡せる（索引に「objects or dictionaries」と記載）。
- 非同期版 `AsyncTypeSafeClient` があり、`client.models.list().models` で各モデルの `name`, `release_date`, `description` を列挙できます。
- `RetryPolicy` で試行回数・リトライ対象ステータス・バックオフ・retry ヘッダの扱いを設定でき、例外クラスとしてレート制限・接続失敗・タイムアウトが定義されています。レスポンス型からトークン使用量も読めます。
- ライセンスは MIT、リポジトリは発表時点で 3 コミット・7 スター。

**【推測】**
- `response.scores["frustration"]` という Score 用ビューも `choices` / `nouls` と対称に存在する可能性が高い（未確認）。
- `Noul(criteria={"true": "...", "false": "..."})` は HTTP API 上で任意なので SDK でもキーワード引数として受けるはず。
- `state` / `instructions` に `str | dict | list` を渡せる型ヒントになっていると思われる。
- 環境変数名は `TYPESAFE_API_KEY` が確認済ですが、ベース URL 上書き用の環境変数（例 `TYPESAFE_BASE_URL`）は索引の「Constants」ページに載っている可能性があるものの未確認。

なお GitHub の Issue #3 で、pydantic ベースの高レベル API（`bool` → noul、`Literal[...]` → choice、`float` → score にマップするスキーマ層）が提案されていますが、これは**外部コントリビューターの提案で未マージ**であり、公式インターフェースではありません。

## 3. JavaScript SDK（`@typesafe-ai/sdk`）

**【確認済】** `import { TypeSafeClient } from "@typesafe-ai/sdk"` で、`client.models.list()` が配列を返します（Python と違い `.models` プロパティを挟まない）。ドキュメント索引には `choice()`, `noul()`, `score()` のヘルパー関数、`ChoiceQuestion<T>`, `ScoreQuestion<T>`, `NoulQuestion`, `ChoiceResponse<T>`, `ScoreResponse<T>`, `NoulResponse`, `SystemOneRequest<Q>`, `SystemOneResult<Q>`, `ResultFor<T>`, `ScoreLegend<T>`, `RetryPolicy`, `TypeSafeClientConfig`, `Usage` のインターフェースと、`APIError`, `RateLimitError`, `AuthenticationError`, `UnprocessableEntityError`, `InternalServerError`, `APITimeoutError`, `APIUserAbortError` などの例外クラスが列挙されています。

**【推測】** 型名から判断すると、`ChoiceQuestion<T>` の `T` は選択肢キーのリテラル型ユニオン、`ResultFor<T>` は質問型から回答型を導く条件型で、`SystemOneResult<Q>` は `answers` を質問マップ `Q` のキーごとに正しい回答型で推論する設計だと思われます。つまり次のような使い勝手が期待できます（未検証の再構成）：

```ts
const res = await client.systemOne({
  state: {...},
  questions: {
    intent: choice("What is the main request?", { refund: "...", other: null }),
    urgent: noul("Does the ticket convey time pressure?"),
    frustration: score("How frustrated?", ["Calm", "Concerned", "Very angry"]),
  },
});
res.answers.intent.choice        // "refund" | "other" と推論される（推測）
res.answers.urgent.noul          // number
res.answers.frustration.score    // number
```

メソッド名（`systemOne` か `system_one` か）、ヘルパーの引数順、環境変数名は未確認です。

## 4. Vercel AI SDK プロバイダ（`@ai-sdk/typesafe-ai`）【確認済】

TypeScript 界隈では公式 SDK より馴染みやすい選択肢です。`experimental_evaluate({ model: typeSafeAi.evaluationModel('jev-latest'), state, questions })` の形で呼び、質問型は `choice` / `score` / `boolean` で、`boolean` が TypeSafe の `noul` にマップされます。回答は `result.answers.department.choice`, `result.answers.severity.score`, `result.answers.requestsRefund.probability`（Noul は `probability` という名前）。confidence は `result.providerMetadata.typesafe.confidence[questionId]` に置かれ、`result.rounding` で丸め精度を報告します。環境変数は `TYPESAFE_AI_API_KEY`（公式 SDK の `TYPESAFE_API_KEY` と異なる点に注意）、`baseURL` 既定は `https://api.typesafe.ai/v1`、リトライは AI SDK コア側で `maxRetries`（既定2）。プロバイダ固有オプションは現時点で未定義、言語・埋め込み・画像モデルとしては使えません。

## 5. 補助エンドポイント・周辺【確認済】

- `GET /v1/models` がアカウントで使えるモデル名（現状はエイリアス）を返し、バージョン ID はリストになくても `model` フィールドで受理されます。
- Claude Code / Codex 向けの Agent skill（ドロップイン）が提供されており、エージェントが「1 呼び出し 1 質問」の癖に陥るのを防ぐ指示が含まれています。
- LLM で同じ `system_one(state, questions)` インターフェースを再現する `system-one-adapter-python`（`SystemOneAdapterClient`、provider に openai/anthropic を指定、`llm_answer_mode="probabilities"|"discrete"`）が公式リポジトリとして公開されています。フォールバック設計に直接使えます。

## 6. 資料に無く、推測または要確認の事項

- **confidence の計算式**: 「確率分布の形状から導出した統計量」としか説明されておらず、別クックブックで扱う予定と書かれています。推測ではエントロピー正規化か上位2候補のマージン系ですが、公式定義は未公開なので、しきい値は自社データでの実測較正が前提です。
- **バッチ API・ストリーミング・非同期ジョブ**: 記載なし。並列サンプラーで単発応答が 100ms 級なので、ストリーミングは設計上存在しない可能性が高い（推測）。大量処理はクライアント側の並行呼び出し＋ 250k tok/s・1,200 rpm のレート制限で回す形になります。
- **リクエスト ID・冪等性キー・タイムアウト上限**: 記載なし。SDK に `APITimeoutError` があるのでクライアント側タイムアウトは設定可能と推測。
- **`usage.output_tokens`**: 返却されるが課金は 0。何をカウントしているか（回答の分布サイズ？）は不明。
- **API バージョニング**: パスの `/v1/` のみで、ヘッダによる日付バージョン指定などは確認できず。互換性はモデルエイリアスを固定することで担保する設計。
- **Score の上限 10 段階、`criteria` オブジェクト内の予約キー、Noul の `criteria` に JSON 構造を渡した際の挙動**: 前述のとおり Advanced ページ未取得のため要確認。
- **エンタープライズ向け専用エンドポイント／リージョン**: 記載なし。

実装レベルで最初に検証すべきは、(1) `probabilities` の丸め誤差を吸収したしきい値ロジック、(2) `model` フィールドの応答値をログに残してバージョンを追跡すること、(3) 32k/64k のトークン予算に対する state のフィルタリング、の3点です。
