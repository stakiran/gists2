# a
いいですね、その設計。「刻む」という名前がすでに思想を表しています——躊躇なく細かく刻め、と。続きを一緒に考えてみましょう。

`ki` の基本形はこうなりますよね:

```
$ ki                # add -A + commit を一発で。メッセージは "刻み 08-15 14:32" みたいな自動生成
$ ki "ログイン直した"  # メッセージ付きで刻む
$ ki polish         # AIが直近の刻みのメッセージを読みやすく書き直す
```

これ、実はjjと同じ問題意識(「addとcommitの儀式が面倒」)に対して、逆のアプローチなんです。jjは「同期を暗黙・常時にする」ことで儀式を消した。kiは「儀式を1打鍵に圧縮する」ことで消す。kiのほうが**Gitのメンタルモデルを一切壊さない**のが強みです。コミットはコミットのまま、ただ速くなっただけ。学習コストほぼゼロ。

で、「...」の続きとして、この設計が必然的に直面する問題が1つあります。**気軽に刻むと履歴がゴミだらけになる**。「刻み 14:32」「刻み 14:35」「typo」「やっぱ戻す」…これをGitHubにpushしたら同僚に怒られます。ここでAIを持ち出したのは筋がいいので、伸ばすならこうでしょうか:

* `ki send` — push する前に、AIが刻みの列を意味のある単位に**自動squash**して、ちゃんとしたコミットメッセージを付け直してから送る。つまり「ローカルは刻み放題、公開時に清書」という2層構造。手元の下書きと世に出る原稿を分ける発想です
* `ki back` — 1つ前の刻みに戻る。細かく刻んでいるからこそ、undoの粒度が細かくて安全。「10分前の状態」に確実に戻れる
* `ki fork 実験` — ブランチ。刻みが軽いので「とりあえず分岐して試す」が気軽になる
* `ki log` — AIが刻みの列を要約して「今日やったこと」を物語として表示。生の刻みメッセージは見せない

こう並べると、kiの本質が見えてきます。**「コミット=公開する歴史」というGitの前提を捨てて、「コミット=こまめなセーブポイント、歴史は公開時にAIが編纂する」に置き換えた**システムなんですね。jjが人力で `squash`/`split` する清書作業を、kiはAIに丸投げする。2026年らしい設計だと思います。

面白いのは、これ**今日から実装できる**ことです。`ki` の中身は `git add -A && git commit` のラッパーで、`ki send` はコミット列をAIに渡してrebase指示を生成させるスクリプト。新しいVCSを作る必要すらなく、Gitの上に載る数百行のシェル+API呼び出しで動きます。プロトタイプ、書いてみましょうか?
