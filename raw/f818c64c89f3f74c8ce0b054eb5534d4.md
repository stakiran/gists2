# ループエンジニアリング整理ノート
## 「コードを書くこと」から「ループを書くこと」へ

元資料: @IT記事「ソフトウェアエンジニアの仕事は『ループを書くこと』になる」(Armin Ronacher氏 "The Coming Loop" の解説) と、それに対する議論の整理。

---

# 第1部 基本概念の定義

## 1.1 ループ (loop)

ここでの「ループ」は `for` / `while` のような反復構文ではない。

> **定義**: 目標に対して、状態を観測し、行動し、結果を評価し、終了条件を満たすまで状態を更新し続ける実行単位。

## 1.2 ハーネス (harness)

> **定義**: AIエージェントを動かす実行レイヤー。エージェントの成果を独立に評価し、継続・再実行・終了を制御する基盤。

役割を一言でいえば、AIエージェントを1人の作業者として使うための **CI + タスク管理 + 監督 + 記録 + 引き継ぎ** をまとめたもの。

## 1.3 内側ループ (エージェントループ)

> **定義**: AIエージェント自身が1セッション内で回す反復。ツールを呼び、結果を見て次の行動を決め、「完了した」と自己申告するまでのループ。

```
状況を考える → ファイルを読む → コードを変更 → テスト実行
→ 結果を見て次を決める → …… → 「完成した」と判断
```

- 例: Claude Code や Codex の通常動作、`/goal` コマンド
- 特徴: **「次に何をするか」「いつ終えるか」をAI自身が判断する**

## 1.4 外側ループ (ハーネスループ)

> **定義**: AIが「完了」と言っても、ハーネスが独立した基準で判定し、未達なら継続・再指示・セッション再作成・別エージェントへの引き継ぎを行うループ。

```
タスクを渡す → エージェントが完成を報告
→ ハーネスがテスト・レビュー・要件適合を検証
→ 不合格なら修正タスク化して再投入 → 合格まで繰り返す
```

**本質**: 「AIが終わったと言ったこと」と「本当に終わったこと」を**分離**する点。

外側ループが担う処理の例:

| 分類 | 内容 |
|---|---|
| 検証 | テスト、Lint、型検査、ビルド、受け入れ条件との照合 |
| セッション管理 | コンテキスト肥大時の再作成、要約と引き継ぎ |
| タスク管理 | 分割、優先順位付け、再投入 |
| 多重化 | 別モデル・レビュー用エージェントによる検証 |
| 安全装置 | ロールバック、人間へのエスカレーション条件 |
| 資源制限 | コスト、時間、試行回数の上限 |

## 1.5 記憶の二層構造

長時間の作業ではチャット履歴を記憶として使うのは不安定(コンテキスト上限、埋没、要約時の欠落)。記憶は**会話の外**に置く。

| 種類 | 内容 | 例 |
|---|---|---|
| 一時的な作業記憶 | セッション内の短期状態 | 調査中のファイル、直前のテスト結果、仮説、次の操作 |
| 永続的なプロジェクト記憶 | セッションを越えて残す状態 | 仕様・受け入れ条件、設計判断と理由、未完了タスク、既知の問題、変更履歴、テスト結果、Git、引き継ぎ文書 |

原則: **Git・Issue・タスクキュー・テスト結果・構造化された状態ファイルを「正」とし、AIの会話履歴に依存しない。**

タスクキュー自体も外側ループの記憶として機能する:

```
未着手 → 作業中 → 検証待ち → 修正必要 → 完了
```

## 1.6 外側ループの課題 (6点)

1. **誤りの自己増殖** — 初期理解の誤りを前提にタスクが量産される。ループが速いほど誤った方向へ進むのも速い
2. **検証可能なものへの偏り** — テストで測れる品質だけが最適化され、設計の分かりやすさ・保守性・UX・セキュリティの微妙なリスクなどが漏れる。「テストに合格するコード ≠ 良いソフトウェア」
3. **引き継ぎでの意図喪失** — セッション移行のたびに設計理由などの暗黙情報が削られ、要約を重ねると不確実性が確定事項化する
4. **人間の理解の空洞化** — レビュー可能量を超え、「テストは通るが誰も全体を説明できない」状態になり得る
5. **終了条件設計の難しさ** — 緩いと未完成、厳しいと無限修正。コスト・時間・品質の妥協点も設計対象
6. **手応えの変化** — 「自分で作る仕事」から「並列に進むAIを管理する仕事」への心理的・職業的違和感 (Ronacher氏の「まだなじめていない」の正体)

# 第2部 議論①: 「内側／外側」は相対的である

## 2.1 問題提起

`/goal` は「内側」とされるが、`/goal` 自体もループを検証する始点を持つ。ならば「内／外」という2分法より、複数のハーネスのループを組み合わせる見方の方が適切ではないか?

## 2.2 結論: 内外は相対的な呼び方

**「内側／外側」はループ固有の種類ではなく、どの実行主体を基準に見るかで決まる相対的な呼称**。

ハーネス H に対して、そのループを次のように書く:

```
loop(H)
```

`/goal` が「目標解釈 → 操作 → 観測 → 達成度検証 → 未達なら再試行」と動くなら、それ自体がハーネス H₁ を持ち、`loop(H₁)` と表現できる。「内側ループ」と呼ばれるのは、単に1つのセッション内部に収まっているからにすぎない。

別のハーネス H₂ が「`/goal` を実行 → 成果物を独自検査 → 不合格なら再実行」を行うなら、入れ子になる:

```
loop(H₂)[ loop(H₁) ]
```

- 記事の「内側」 = H₁ のループ
- 記事の「外側」 = H₁ を管理する H₂ のループ
- ただし H₂ も、さらに上位の H₃ から見れば「内側」になる

つまり `/goal` は見る階層によって内側にも外側にもなる:

| 視点 | `/goal` の位置づけ |
|---|---|
| セッション内でモデルが自分の作業を反復 | そのセッションに対する**内側**ループ |
| `/goal` ランタイムがモデル呼び出しを反復・検証 | モデル呼び出しに対する**外側**ループ |
| CIやジョブ管理が `/goal` を再起動 | `/goal` に対するさらに**外側**のループ |

## 2.3 「外側ループ」の成立条件は制御関係

`loop(H₂)` が `loop(H₁)` の**結果を使う**だけでは外側ループとは限らない。それは単なる直列パイプラインかもしれない:

```
loop(H₁) → 成果物 → loop(H₂)    ← これはパイプライン
```

外側ループと呼ぶには、H₂ が H₁ に対して次の**制御権限**を持つこと:

- H₁ の成果を独立に評価する
- 未達と判定する
- H₁ を再実行する
- 指示やコンテキストを変更する
- 別モデル・別エージェントに切り替える
- 中断・ロールバック・完了を決定する

> **本質**: 結果の利用ではなく、**上位ループが下位ループの継続・再実行・終了を制御すること**。

## 2.4 より適切な整理: 3つの軸

「内／外」の2分法の代わりに、各ループを次の3軸で記述する:

| 軸 | 取り得る値の例 |
|---|---|
| **① 所有者** (誰がループを回すか) | モデル / エージェントランタイム / CLI / CI / タスクオーケストレーター / 人間 |
| **② 対象** (何を反復するか) | 1回のモデル呼び出し / ツール操作 / エージェントセッション / タスク / PR / リリース全体 |
| **③ 終了判定者** (誰が終わりを決めるか) | モデル自身 / テスト / レビュー用エージェント / ハーネス / 人間 |

記述例:

```
H₁: 対象 = ツール操作          判定 = エージェント自身      状態 = セッション内コンテキスト
H₂: 対象 = H₁のセッション      判定 = テストと受け入れ条件   状態 = タスクDB、Git、テスト結果
H₃: 対象 = 複数のH₂タスク      判定 = リリース基準と人間の承認 状態 = Issue、PR、CI
```

これは2分法ではなく、**階層化・合成された制御ループ群**。実務では入れ子だけでなく、並列競争ループ・実装⇄レビューの循環ループ・人間が途中選択するループもある。

# 第3部 議論②: ループは「関数」に並ぶ抽象化単位になる

## 3.1 主張

プログラミングで関数が基本単位であるように、AIエージェント時代には**契約を持ったループ**が主要な設計・合成・検証単位になる。

## 3.2 関数とループの型の対比

**関数**:

```
f : Input → Output
```

契約の中心 = 引数、戻り値、事前条件、事後条件。

**エージェント的ループ**:

```
L : (Goal, State, Budget) → (Result, State′, Evidence)
```

内部では状態更新を繰り返す:

```
State(t+1) = step(Goal, State(t), Observation(t))
```

終了条件は「達成した / 失敗が確定した / 予算を使い切った / 人間の判断が必要 / 上位ループに制御を返す」のいずれか。

> **対比の核心**: 関数は「結果を**計算する**もの」、ループは「不確実な環境の中で結果へ**収束させる**もの」。

## 3.3 第一級のループに必要なインタフェース

関数が合成可能なのは入出力と契約が明確だから。ループも同様に、少なくとも以下を明示する:

```
Loop {
    goal           // 何を達成するか
    initialState   // 何を引き継ぐか
    observe        // 状況をどう観測するか
    propose        // 次の行動をどう決めるか
    act            // 何を実行できるか
    evaluate       // 結果をどう評価するか
    stop           // いつ終了するか
    budget         // 時間・費用・試行回数
    checkpoint     // 何を永続化するか
    escalation     // 解決不能時に誰へ渡すか
}
```

戻り値も成果物だけでは足りない:

```
LoopResult {
    status         // success / failure / blocked / timeout
    artifact       // コード、文書、PR など
    evidence       // テスト結果、ログ、レビュー結果
    finalState     // 引き継ぎ可能な状態
    remainingWork  // 未解決事項
}
```

特に重要なのは **evidence (証拠)**。上位ループは下位ループの「できました」という自己申告ではなく、成果物と証拠で次を判断する。

## 3.4 ループの合成パターン

| パターン | 記法 | 構造 |
|---|---|---|
| 直列合成 | `L₂ ∘ L₁` | 仕様化 → 実装 → 検証 → リリース。前の成果物と状態を次へ渡す |
| 監督・入れ子 | `L_supervisor[ L_worker ]` | 上位が下位を実行し、結果と証拠を評価、不十分なら条件を変えて再実行 (≒ 記事の外側/内側) |
| 並列・競争 | `parallel(L_A, L_B)` | 複数の実装ループを並列実行 → 評価ループが比較 → 最良案を採用/統合 |
| 相互フィードバック | `L_impl ⇄ L_review` | レビュー結果を実装側へ戻し、条件を満たすまで往復 |
| フォールバック | `fallback(L_A, L_B)` | 小型モデル → 失敗時のみ大型モデル → それでも失敗なら人間 |

## 3.5 高階ループ演算

関数型プログラミングが「関数を受け取り関数を返す」ように、**ループを受け取り別のループへ変換する高階ループ**が鍵になる:

```
retry(loop, policy)          // 再試行方針を付与
timeout(loop, budget)        // 予算制限を付与
verify(loop, evaluator)      // 独立検証を付与
supervise(loop, supervisor)  // 監督を付与
parallel(loopA, loopB)       // 並列競争させる
fallback(loopA, loopB)       // 失敗時の代替を付与
checkpoint(loop, store)      // 永続化を付与
compose(loopA, loopB)        // 直列合成
```

> 記事でいう「ハーネス」は、この**高階ループを実装するもの**と解釈できる。

## 3.6 関数より合成が難しい理由 (5点)

1. **終了が保証されない** — 非収束が通常の設計課題になる
2. **非決定的** — 同じ入力でも結果が変わる。契約は「常にこの値を返す」ではなく「このテストを満たす / この信頼度を超える / この予算内で試みる / 失敗時はこの状態を返す」という形になる
3. **副作用が大きい** — ファイル変更・デプロイ・外部API操作を伴い、再試行が安全とは限らない。冪等性・トランザクション・チェックポイント・ロールバックが必要
4. **状態と履歴を持つ** — ループの意味が過去の試行や外部状態に依存する。状態の所有権と引き継ぎ形式が必要
5. **評価器自体が誤る** — テスト・AIレビュー・人間も不完全。「評価ループをどう検証するか」という一段上の問題が生じる

## 3.7 抽象化の境界の移動

| | 従来 (関数・モジュール) | これから (ループ) |
|---|---|---|
| 隠蔽されるもの | 内部実装 (計算方法) | 内部の試行錯誤 (何回モデルを呼んだか、どのツールを使ったか) |
| 呼び出しに必要な知識 | 入力・出力・契約 | 目標・権限・予算・終了条件・証拠の契約 |

## 3.8 中心概念の対比 (まとめ)

```
関数の中心概念:   Input, Output, Contract
ループの中心概念: Goal, State, Action, Evaluator, Stop, Budget, Evidence
```

# 全体の結論

1. **仕事の移行**: エンジニアの中心的な仕事は、コードを直接書くことから「AIが実装・検証・修正を反復できる環境と終了条件を設計すること」へ移る。ただし人間には、曖昧な要求の明確化、検証可能な受け入れ条件の作成、記憶とタスクの構造化、ループの暴走防止、自動評価できない品質の判断、最終責任、が残る。

2. **内／外は便宜的**: 「内側／外側」は初心者向けの便宜的な2分法。正確には「H₂ が H₁ の成果を観測し、H₁ の再実行・終了を制御する」という入れ子関係の説明であり、実体は**異なるスコープ・状態・評価基準・制御権限を持つ複数のループの階層的・並列的な合成**。長期的には「所有者・対象・状態・評価器・制御関係」で記述する方が有用。

3. **ループが第一級単位**: 核心は「AIを何度も実行すること」ではなく、**ループを名前付きで切り出し、明確な契約を与え、検証し、別のループと合成できるようにすること**。今後の主要な抽象化単位はエージェントそのものではなく「契約を持ったループ」であり、エージェントやモデルはその内部で交換可能な実行戦略の一つになる。
