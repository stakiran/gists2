# 提言：Knowledge Engineer（Context Engineer）という役割を定義する
## テクニカルライターと ML エンジニアの間に生まれるべき職種について

> 本稿は、株式会社Helpfeel の公開情報（経営メンバーページ、求人票、Tech Conf 2026 のセッション情報など）を題材にした外部からの考察をもとに、ナレッジを AI に供給する事業に共通して必要になる役割を提言するものです。同社を批判する意図はなく、同社を「この問題に最も早く直面している会社の一つ」として扱っています。社内の実態は知らず、推測を含みます。

---

## 1. 要旨

- 生成AIの精度は「モデル」ではなく「参照するナレッジの質と構造」で決まる局面に入った。ナレッジを設計・執筆・構造化・評価する人が事業の中核になる
- しかしその担い手であるテクニカルライターは、多くの組織で「制作職」として定義されており、求人要件にも待遇にも構造設計・評価・データの素養が含まれていない
- Data Engineer と Analyst の間に Analytics Engineer が生まれたのと同じ構図で、Technical Writer と ML Engineer の間に **Knowledge Engineer（Context Engineer）** を定義すべきである
- この役割は「AIへの指示を書く」プロンプトエンジニアより寿命が長い。「AIが参照する知識そのものを設計する」仕事だからである
- 最大の障害は技術ではなく、待遇と地位。ここを変えないと定着しない

---

## 2. 背景：なぜ今この役割が必要か

### 2.1 ナレッジ供給型の事業では、書き手が製品品質を決める

FAQ検索、社内ナレッジ検索、AIエージェント、ボイスエージェント。いずれも「文書を入れれば答えが返る」RAG的な機能自体はコモディティ化し、差がつくのは参照されるナレッジの側になった。

Helpfeel を例にとると：

- 意図予測検索は「1つの記事から約50倍の質問表現を **AIと人が共同で** 生成」する仕組み。顧客のユーザーがどんな言葉で聞くかを知らないと作れない
- 料金はコンテンツ数ベースの月額固定で、FAQ構築・検索チューニング・運用サポートまでパッケージに含まれる。つまり顧客は「FAQを設計し書き改善し続けるチーム」を買っている
- 導入900サイト以上。金融の規程1万ページ、建材メーカーの製品群、自治体の手続き——顧客ごとにドメイン語彙も業務フローも異なり、そのコンテキストは書き手の頭の中に蓄積される

書き手が辞めれば「この銀行の用語のクセ」「この顧客が嫌う言い回し」は一緒に消える。離職率がそのまま製品品質に跳ね返る構造になっている。

### 2.2 一方で、役割の定義は「制作職」のまま

同社の公開求人票におけるテクニカルライターの定義：

- 業務：顧客からもらったFAQ文書を編集し、「探しやすく読みやすく」する。「探しやすく」＝FAQと検索キーワードを紐付ける質問文を作る。「読みやすく」＝スタイルやページ間リンクを整える
- 必須要件：ペルソナを意識した執筆経験、FAQ／マニュアル制作の経験（目安3年）
- エンジニアリング、データ、評価に関する要件はなし。時短転職媒体にも掲載

会社の看板は「AI-Readyなナレッジ基盤」に掛け替わっているのに、それを実現する人の定義が制作職のままである。このギャップが本稿の出発点。

### 2.3 評価データは、エンジニアには作れない

同社の Tech Conf 2026 では、Helpfeel Analytics について「実際の問い合わせから『期待する振る舞い』と『もっともらしい誤り』を評価データとして蓄積し、143件を変更のたびに検証している」と語られた。Voice Agent についても「実コールログからテストシナリオを作り、応答の正しさや業務完了率を評価」している。

この評価データを作る——何が正解で、何が「それっぽい間違い」かを判定する——には、ドメインの言葉を理解している必要がある。それはエンジニアではなく書き手の能力である。しかし現状、書き手はソリューションデザイン部、評価基盤は開発部の新規ソリューショングループと、部署が分かれている。

## 3. 提言：Knowledge Engineer の定義

### 3.1 一文で言うと

**AIが参照するナレッジを、設計し、書き、構造化し、評価し、改善し続ける人。**

プロンプトエンジニアが「AIへの指示」を扱うのに対し、Knowledge Engineer は「AIが根拠とする知識」を扱う。モデルが変わっても、指示の書き方が変わっても、知識の設計は残る。

### 3.2 責務

| 領域 | 責務 | 従来のライターとの差分 |
|---|---|---|
| **設計** | 記事の粒度、記事間のリンク構造、メタデータのスキーマを決める | 「整える」から「設計する」へ。文章力ではなくスキーマ設計 |
| **執筆** | ドメイン語彙を踏まえ、検索・生成に最適化された形で書く | 従来と同じ。ただし「どう書けばヒットするか／根拠として拾われるか／ハルシネーションの温床にならないか」を意識する |
| **評価** | 実ログから評価データ（期待する振る舞い／もっともらしい誤り）を作成・保守する | 新規。品質の定義そのものを担う |
| **観測** | 検索ログ・VoC・エージェントの応対ログを読み、「足りないナレッジ」「間違って参照されているナレッジ」を発見する | 「言われたものを書く」から「何を書くべきか決める」へ |
| **改善** | 評価結果とログをもとにナレッジを継続的に改善する。AIによる自動生成の出力をレビュー・修正する | 新規。AIとの共同作業の「人」側を担う |
| **伝達** | 顧客固有のコンテキストを属人化させず、型やドキュメントとして残す | 新規。自分の頭の中を組織の資産にする |

### 3.3 必要な素養

**必須（コードは書けなくてよい）**

- ドメインの言葉を読み書きする力。従来のライター能力はそのまま土台
- 構造化の感覚：粒度、階層、リンク、タグ、メタデータを「読者のため」だけでなく「機械が参照するため」に設計できる
- 検索・生成の挙動の直感：チャンク分割、エンベディング、リランキング、引用の仕組みを、実装は知らなくても「こう書くとこう振る舞う」として体で分かっている
- 評価の設計：正解セットを作り、変更前後で何が良くなり何が悪くなったかを言語化できる
- ログを読む力：定量（ヒット率、到達率、解決率）と定性（実際のクエリ）の両方から仮説を立てられる

**あると強い**

- SQL や簡単なスクリプトでログを自分で引ける
- 評価パイプラインに自分でケースを追加できる（YAML/JSON程度）
- バージョン管理の概念（ナレッジの変更履歴と評価結果を紐付ける）

**求めないもの**

- モデルの実装、インフラ、アプリケーション開発。これは ML／プロダクトエンジニアの領域で、Knowledge Engineer は「隣」に立つ

### 3.4 成果物と KPI

成果物：

- ナレッジのスキーマ定義（粒度・リンク・メタデータの規約）
- 評価データセット（顧客ごと、変更ごとに保守される）
- ナレッジ改善のバックログと、その根拠となるログ分析
- 顧客コンテキストのドキュメント（用語集、禁止表現、業務フローの要点）

KPI の候補（従来の「記事数」「納期」からの転換）：

- 評価セット上の正解率・誤り率の推移
- 自己解決率、ノーヒット率、エージェントの業務完了率
- 「足りないナレッジ」を発見してから埋めるまでのリードタイム
- 属人化度：担当者が変わったときに品質が維持されるか（引き継ぎ後の評価スコアの落差）

## 4. 隣接職種との違い

| 職種 | 扱う対象 | Knowledge Engineer との関係 |
|---|---|---|
| Technical Writer | 人間の読者向けの文書 | 土台。Knowledge Engineer はここに「機械の読者」と「評価」を足したもの |
| Prompt Engineer | AIへの指示 | 指示はモデル更新で陳腐化する。知識は残る。寿命が違う |
| ML / AI Engineer | モデル、パイプライン、評価基盤の実装 | 評価基盤を作るのは ML Engineer、評価データを作るのは Knowledge Engineer |
| Data Engineer | ログの収集・整備 | ログを整えるのは Data Engineer、ログから「何を書くか」を決めるのは Knowledge Engineer |
| Customer Success | 顧客の利用促進・継続 | CS は顧客との接点を持ち、Knowledge Engineer はそこで得た文脈をナレッジに落とす |
| Analytics Engineer（類推） | Data Engineer と Analyst の間 | 生まれ方が同じ。「両側の言葉を話せる人」がいないと境界で価値が落ちる |

---

## 5. 組織への置き方

### 5.1 境界に置く

Helpfeel の現状に当てはめると、ライターはソリューションデザイン部、評価基盤は開発部の新規ソリューショングループ、両者の受け渡しは「顧客要望実現チーム」経由。Knowledge Engineer は **この境界そのもの** に置くべき役割である。

具体的には二方向から作る：

- ライター側から：評価データを自分で作り、評価パイプラインにケースを追加できるようになる人
- エンジニア側から：コンテンツの構造や書き方に口を出し、ライターと同じ言葉で話せる人

どちらか一方だけでは境界は埋まらない。

### 5.2 The Model 型の分業との折り合い

インサイドセールス → AE → ソリューションデザイン → CS と担当が変わるたびに顧客コンテキストは削れる。Knowledge Engineer は「顧客ごとのナレッジ」に責任を持つことで、この分断を横断する存在になりうる。ただし全顧客を一人が見るのは不可能なので、業界別（金融、自治体、製造…）にドメインを持たせるのが現実的。

### 5.3 AI との分担

「AIと人が共同で質問表現を生成」「AIが不足ナレッジを自動生成」という方向は正しいが、その「人」の部分を定義しないまま自動化を進めると、レビューできる人がいなくなり、品質が静かに劣化する。AI が下書きを量産する時代には、**下書きを判定できる人の価値が上がる**。Knowledge Engineer はその判定者。

## 6. 一番の障害：待遇と地位

技術的な問題より、ここが本丸だと思う。

- ライターは日本では「安い職種」として扱われがちで、時短求人に出されるのもその表れ
- しかし Knowledge Engineer は「顧客ごとのドメイン知識 × 構造設計 × 評価」を担う人材で、希少性はエンジニアと同等かそれ以上
- エンジニアと同等の給与テーブル、シニア／スタッフ相当のキャリアパス、技術カンファレンスでの登壇機会、といった「地位の装置」がないと、定義しても定着しない
- 逆に、ライターがエンジニアと同じ会場で評価設計について登壇している状態が作れれば、その会社は「AI-Ready」というカテゴリを言葉だけでなく人材で押さえたことになる

---

## 7. 導入のステップ（案）

1. **役割を名付ける**：ジョブディスクリプションを書き直す。求人票の必須要件に「構造設計」「評価」「ログ分析」を入れる
2. **評価データの所有権を移す**：現在エンジニア側にある評価セットの追加・保守を、ドメインを持つ書き手に渡す
3. **境界に人を置く**：ライター出身で評価に手を出せる人、エンジニア出身で構造に口を出せる人を、それぞれ1人ずつ「兼務」から始める
4. **KPI を変える**：記事数・納期から、評価スコア・解決率・属人化度へ
5. **給与テーブルを作る**：エンジニア職種と並ぶ形で
6. **外に発信する**：「Knowledge Engineer とはこういう仕事だ」を最初に定義した会社がカテゴリを取る

## 8. 想定される反論と応答

**「AI が全部書くようになるからライターは不要になる」**
→ 書く量は減る。判定する必要は増える。何が正しく何が「それっぽく間違っている」かは、ドメインを知る人にしか分からない。人が減っても役割は残り、むしろ一人あたりの重要度は上がる。

**「エンジニアが評価データも作ればいい」**
→ 実際にそうしている会社は多いが、金融の規程や自治体の手続きの「正解」をエンジニアが判定するのは無理がある。評価基盤とデータの分業は Data Engineer と Analyst の分業と同じで、両方を一人が持つとどちらかが薄くなる。

**「新しい職種を作るより、ライターに研修すればいい」**
→ 研修は必要だが、役割・KPI・待遇が変わらないまま素養だけ求めると、できる人から辞めていく。名前と地位はセットで変える必要がある。

**「顧客ごとのカスタマイズはそもそも減らすべき」**
→ 同意。ただし減らすためにも「何が共通で何が顧客固有か」を判定する人が要る。それも Knowledge Engineer の仕事。

---

## 9. まとめ

- ナレッジを AI に供給する事業では、書き手が製品品質を決める
- その書き手の定義が「制作職」のままなのは、看板と中身のズレ
- Technical Writer と ML Engineer の間に **Knowledge Engineer（Context Engineer）** を定義する。責務は設計・執筆・評価・観測・改善・伝達
- 置き場所は部署の境界。KPI は記事数から評価スコアと属人化度へ
- 最大の障害は待遇と地位。ここを変えた会社が「AI-Ready」を人材で押さえる
