# 非人間アイデンティティ時代のID管理入門 ── トレンド整理と「アダプティブアイデンティティ」の立ち位置

> 2026年7月時点の整理メモ。ID管理を「社員アカウントの管理」だと思っている人向けに、なぜそれが数百万規模の問題になっているのか、どういう対策があるのか、SailPointが提唱する「アダプティブアイデンティティ」がその中でどこに位置するのかをまとめたもの。
> 数字の多くはセキュリティベンダーの調査に基づくため、バイアスを含む点に留意（本文中で都度注記）。

---

## 1. 前提：ここでの「ID」は社員証ではない

ID管理というと従業員アカウントの発行・削除を思い浮かべがちだが、この文脈での**アイデンティティとは「何かにアクセスできる資格情報」すべて**を指す。人間のアカウントはむしろ少数派になる。

含まれるもの：

- サービスアカウント、DB接続用アカウント
- APIキー、アクセストークン、リフレッシュトークン
- クラウドIAMロール（AWS Lambda関数ごと、Kubernetes Podごとに発行される）
- TLS/クライアント証明書、SSH鍵
- SaaS間連携のOAuthトークン（「連携を許可」ボタンを押すたびに1個生まれる）
- CI/CDのデプロイキー
- AIエージェント

これらをまとめて **NHI（Non-Human Identity、非人間アイデンティティ）** と呼ぶ。

### なぜ数が爆発するのか

Webサービスを1本動かすだけで、裏側にこれだけの「鍵」がぶら下がる：

```
サービス1本
├─ DB接続用アカウント
├─ 決済APIのキー
├─ メール配信APIのキー
├─ オブジェクトストレージ用IAMロール
├─ ログ収集ツールへの送信トークン
├─ 監視ツールの読み取り権限
├─ CI/CDのデプロイキー
└─ TLS証明書（90日で失効 → 自動更新の仕組みにも鍵が要る）
```

軽く10〜20個。マイクロサービスが200個あればそれぞれに同様のセットがあり、Lambdaなら関数単位、Kubernetesならワークロード単位でIDが発行される。さらに全社員が思い思いに押すSaaS連携の許可ボタンが積み上がる。

### 数字

| 出典 | 非人間ID : 人間ID |
|---|---|
| Veza | 17 : 1 |
| Rubrik Zero Labs | 45 : 1 |
| KPMG Cybersecurity Considerations 2026 | 80 : 1 |
| Palo Alto Networks 2026 Identity Security Landscape | 109 : 1（前年82:1） |
| Entro Labs（クラウドネイティブ環境） | 144 : 1（2024年上期は92:1） |

事例として、ある大手金融機関の監査では人間のアカウント約5万に対し非人間IDが420万見つかったと報告されている。

**注意**：比率が出典によって8倍以上ばらつくのは、「何を1つと数えるか」（失効済み証明書は？未使用キーは？）の定義が各社バラバラなため。正確な数値というより「桁が違う」という理解が適切。かつ、これらは全てセキュリティ製品を販売する側が出している数字である。

Palo Altoの調査では、109個の機械IDのうち79個がAIエージェントとされており、比率上昇の主因はエージェントの増加になっている。

## 2. なぜ管理が難しいのか

数の問題以上に、**人間のアカウントとは性質が違う**ことが本質。

| 性質 | 人間のアカウント | 非人間ID |
|---|---|---|
| 削除 | 退職処理がトリガーになる | 誰も消さない。作った人が退職すると持ち主不明の孤児になる |
| 有効期限 | パスワード変更・棚卸しがある | 8年前のAPIキーが今日も有効 |
| 多要素認証 | かけられる | 構造上かけられない。鍵1本で入れる |
| 漏洩経路 | フィッシング等 | GitHubへの誤コミット、設定ファイル、Slackへの貼り付け |
| 稼働 | 業務時間に偏る | 24時間動くので「異常な時間帯」という概念がない |

結果、攻撃者はゼロデイ脆弱性を探すより、漏れた鍵で正面から入る方が安上がりになった。OAuthリフレッシュトークンやサービスアカウントを悪用してSaaS間の信頼関係を横断する攻撃（Salesloft-Drift経由の侵害では700社以上に影響）は、「A社を攻撃したらA社と連携していたB社にも入れた」という形をとる。

なお**人間側も簡単ではない**。10年勤めて営業→企画→情シスと異動した社員は各部署の権限が足し算で残っている（権限クリープ）。退職者アカウントの残存も高確率。金融・上場企業では監査で「誰が何にアクセスできるか」の証明義務があり、これを年4回人手でやっていたのが従来のIGA（Identity Governance and Administration）である。

## 3. 対策アプローチの5層

### 層1：鍵を発行しない（secretless / 構造的解決）

静的なAPIキーの配布をやめ、その場で発行される短命なトークンに置き換える。**盗まれる鍵が存在しなければ、監視も回収も不要になる**ため理屈の上では最強。

- CNCFの2026年推奨構成：「アイデンティティは SPIFFE、アクセス移譲は OAuth 2.0、ポリシーは OPA」
- Workload Identity Federation（AWS IAM Roles Anywhere / GCP Workload Identity Federation / Azure Managed Identity）：ワークロードがプラットフォーム発行のIDトークンをクラウドIAM資格情報に交換し、長期の秘密情報を持たずに済む
- 実例：Anthropicも2026年6月にWIFをGA化し、長期の静的APIキーをスコープ限定・短命の資格情報へ移行

### 層2：鍵を金庫に集める（Secrets Management）

層1が理想でも既存システムを全部書き換えられないので、残る鍵は一箇所に集約して定期ローテーションする。HashiCorp Vault、CyberArk Conjur など。現実解。

### 層3：鍵を見つける（Discovery / ISPM）

そもそも何本あるか誰も知らない、が出発点。コードベース・クラウド・SaaSを総なめして棚卸しする。GitGuardian（コミットされたシークレット検出）、Entro など。ISPM（Identity Security Posture Management）はITDRの予防側カウンターパートで、設定の堅牢化・権限の適正化・休眠アカウント削除を攻撃される前にやる領域。

### 層4：統治する（Governance / IGA）

見つけた鍵に「持ち主」と有効期限を割り当て、棚卸し・承認・JIT化する。SailPointの本丸。地味だが、層3で420万個見つけた後に誰が責任を持つのかを決めないと何も進まない。

### 層5：監視して止める（ITDR）

IdP・クラウド・SaaS・Active Directoryのシグナルを常時監視し、行動分析とリスクスコアで異常を検知して、セッショントークン失効やアカウント無効化を自動実行する。Okta Identity Threat Protectionが分かりやすい例で、Shared Signals / CAEP という標準経由でEDR等からリスクシグナルを受け取り、ログイン時ではなくセッション途中で強制ログアウトやアプリ権限剥奪を発動する。

## 4. 「リアルタイム監視」は本命か

**商業的には完全にトレンド。**

- ITDR市場は2025年 27.8億ドル → 2026年 34.2億ドル → 2031年 105億ドル（年率25%）の予測
- Palo Altoが250億ドルでCyberArkの買収を2026年2月に完了

ただし、**なぜ監視がトレンドなのかは冷静に見た方がいい**。監視は「買える製品」だが、層1の「鍵をなくす」は顧客側がアーキテクチャを書き換える話でベンダーの商材になりにくい。業界の音量と実効性は一致しない。

実際、2026年の実務者調査（900人超）では、**AIエージェントのプロジェクトの93%がスコープ制限のないAPIキーを使用中**とされる。監視の高度化を議論する以前の段階で止まっている組織が大半、というのが実態。

### AIエージェントに監視させる、については

現状は**「トリアージの自動化」であって判断の自動化ではない**。優先順位付け、権限の異常検知、レビュー作業の要約は人間より速い。ただし「この権限を剥奪していいか」は業務影響が読めないと決められず、最終承認は人間に残る構成がほとんど。

## 5. AIエージェント固有の未解決問題

むしろ難しいのは**エージェントを監視する側**で、既存の道具で解けていない。

**SPIFFEの構造的限界**：認証するのは「コンテナ」であって「中身」ではない。信頼できるプロセスが通信していることは証明できるが、そのプロセスが次に何をするかは何も保証しない。決まった動作しかしない従来のマイクロサービスでは問題にならなかったが、自律的に判断するエージェントでは致命的になる。

**モード追跡の欠如**：OpenID Foundationが2025年10月に公開した文書は、既存のOAuth 2.0 / OIDCは境界が明確な用途なら十分だが、エージェントは「自律的に動くモード」と「人の代理で動くモード」を行き来するのに、現行の仕組みではどちらのモードで動作しているのか追跡できない、と指摘している。

**標準化の状況（2026年半ば時点）**：

- IETF：2026年3月にAIMS（Agent Identity Management System）ドラフト公開。WIMSE・SPIFFE/SPIRE・OAuth 2.0を組み合わせ、システム横断のエージェント認証と移譲チェーン検証を扱う
- MCP：独自の認可仕様を持ち、MCPサーバーが認可要件を公告する標準エンドポイントを定義
- OAuth 2.1拡張、SPIFFE、商用プラットフォーム、IETFドラフト群が同時並行で走っており、市場が分裂する前に決着をつけようという競争の最中

→ **標準が固まっていないため、現時点で特定ベンダーに深くロックインするのはリスク。**

## 6. SailPoint「アダプティブアイデンティティ」の立ち位置

### 何か

単一の製品名ではなく、SailPointが掲げる**戦略ビジョン／フレームワークの名称**。2025年9月のNavigateで打ち出され、2026年3月9日に4本柱として正式整理された。

出発点は「従来のIGAはもう機能しない」という問題意識。同社CTOは、静的で事後的なレビューに頼るのでは不十分であり、AIエージェント・マシン・認証情報を含む全ID種別に継続的な可視性とリアルタイムガバナンスを提供する方向へ移行すると述べている。

### 4本柱

1. **リアルタイムガバナンス** — 定期レビューから、リスク発生の瞬間に検知・防止・修復する継続的な自動ガバナンスへ
2. **AIとマシンの保護** — AIエージェント、サービスアカウント、マシンワークロードへの適用拡張
3. **ユニバーサル／動的特権** — 全環境でのJITアクセスにより、必要な権限を必要最小時間だけ付与し常時特権を削減
4. **統合脅威管理** — IDコンテキストと脅威シグナルを相関させ、ID管理とSOCのギャップを埋める

### 直近の動き

- 2026年3月：特権の検出・分類機能、Microsoft 365 Copilot / Databricks / Amazon Bedrock / Google Vertex AI / Salesforce Agentforce / ServiceNow AI Platform / Snowflake Cortex AI 等のAIエージェント検出コネクタを追加
- 2026年6月29日：非人間ID・シークレット管理のEntro Security（テルアビブ）買収を完了（報道ベースで約2億ドル）。Entroは1,000種類以上の非人間ID／エージェント型、1,200種類以上の認証情報を70以上のソースから検出できるとされる
- 次世代アクセス認証エンジンとSoD（職務分掌）刷新は2026年下半期提供予定

### 評価

**5層モデルで言えば、層3〜4を本拠地としつつ層5に手を伸ばしている**というのが実像。技術的ブレークスルーというより、**IGAという製品カテゴリの再定義**と見るのが正確。

評価できる点：

- 「棚卸し型」から「制御プレーン型」への転換という方向性自体は正しい。420万個を四半期に1回Excelで目視レビューするのは物理的に不可能で、常時自動化以外に道はない
- JIT / ゼロ・スタンディング・プリビレッジをPAM（特権アカウント）の枠を超えて全IDに広げようとする点は、IGAベンダーとしては踏み込んだ動き

割り引いて読むべき点：

- **ビジョン先行**。4本柱すべてが今すぐ揃っているわけではない（認証エンジン刷新は2026年下半期）
- **差別化の主張は業界共通の潮流**。非人間ID・エージェント統制への集中はMicrosoft、Okta、CyberArk（現Palo Alto）も同方向。「アダプティブアイデンティティ」はその潮流にSailPointが付けた旗印、という見方が実態に近い
- **用語の紛らわしさ**：既存の「アダプティブ認証（リスクベース認証）」とは別物。あちらはログイン時の認証強度の話、こちらはアクセス権限そのものの継続的ガバナンスの話

## 7. 実務上の優先順位

効く順番はおそらくこう：

1. **棚卸し** — 何本あるか知らないと何も始まらない
2. **静的な鍵の廃止** — WIF / 短命トークンへ移行できるものは全部移行
3. **残りを金庫に入れてローテーション**
4. **持ち主と有効期限を全部に付ける**（ガバナンス）
5. **その上で監視**

**リアルタイム監視は5番目。**1〜4を飛ばして5だけ買うと、「持ち主不明の鍵が420万個ある」というアラートが毎日鳴るだけの高価なダッシュボードになる。ITDRとISPMが予防と検知のペアで語られるのはそのため。
