# Jev をどう使うか(エンジニア向けの汎用的な学び)
コメント判定のユースケース(`analyze_comments.py` と300件の判定結果)から、題材に依存しない部分だけを抜き出したもの。各項目の「根拠」は今回のデータで実際に起きたこと。題材固有の学びは `jev_learnings_300_v3.md` にある。

confidence の定義はドキュメントを見ていないので、データからの推測。

## 1. Jev の出力は「答え」ではなく「確率つきの特徴量」として扱う

Jev が返す値をそのまま最終判断にしない。複数の値をコードで組み合わせて判断を作る。Jev は特徴量を作る関数で、ロジックは普通のコードに書く。

- 判断のルール(AND、NOT、閾値、優先順位)はコード側にあるので、再判定なしで変えられる。
- 1つの質問が外れても、他の質問との組み合わせで救える。

根拠: 「離脱理由か」の判定は単独だと宣伝コメントも拾うが、「話題は何か」の判定と組み合わせると除外できた。

## 2. 閾値は質問ごとに校正する。0.5 に意味はない

Noul の確率の出方は質問によってまったく違う。小さなサンプルで分布(中央値、上位10%の境目、最大)を見てから閾値を決める。

- 該当がまれな質問は、最大でも 0.8 程度しか出ない。0.5 で切ると取りこぼす。
- 「皮肉か」のように判断が難しい質問は、無関係な入力でも 0.3〜0.4 が出る。0.5 で切ると誤検出だらけになる。こういう質問は絶対値ではなく順位で使う。
- 実用上は3分割にする。高い帯は自動採用、中間の帯は人間が見る、低い帯は捨てる。

根拠: 4つの Noul の中央値は 0.05 から 0.40 まで開いていた。ある質問は 0.7 以上でほぼ全部当たり、0.5〜0.7 は半分近くが誤りだった。

## 3. 1つの質問には1つの軸だけを持たせる。除外や複合条件はコードで作る

instructions に「ただし〜は該当しない」と書いても、効きは弱い。除外したい条件は独立した質問にして、コード側で NOT を取る。

- 「A かつ B でない」を1つの質問に詰めるより、A の質問と B の質問を分けるほうが、どちらも精度が高い。
- Score の段階に別の軸を混ぜない。混ぜると、片方の軸だけ該当する入力で確率が両端に割れる。

根拠: 除外を明記した質問が除外対象に 0.6 前後を付けた一方、同じ対象を専用の選択肢は 0.99 で捕まえていた。「攻撃性」の最上段に「性的な内容」を混ぜた Score は、好意的で性的な入力が 0 と 2 に割れた。

## 4. criteria を書く。特に「紛らわしいが該当しないもの」を false 側に書く

instructions の長文より、criteria の true/false(Choice なら `what` / `not_for` / `examples`)に書いたほうが効いているように見える。

- false 側には「該当しないもの一般」ではなく、「該当しそうに見えて該当しないもの」を書く。
- 判定が甘い箇所は、基準の記述が甘い箇所。Jev は書かれた基準どおりに判定する。

根拠: false 側に「要望の形を借りた揶揄」と書いた質問は、その型の入力を低く抑えられた。criteria のない質問だけ除外が漏れた。ただし criteria の有無だけを変えた比較はしていないので、因果は未検証。

## 5. Score は期待値なので、confidence と確率分布を一緒に保存する

Score の値は各段階の確率の加重平均。確率が両端に割れると、値は真ん中になる。「真ん中で確定」と「両端で割れている」は値だけでは区別できない。

- Score を保存するときは、confidence と、関心のある端の確率(`probabilities[2]` など)も保存する。
- 検知や足切りの用途なら、期待値ではなく端の確率に閾値を置く。
- 確率が割れること自体が情報になる。両義的な入力や皮肉の検出に使える。

根拠: 同じ 1.0 前後の値で、confidence 0.97 のものと 0.00 のものがあった。後者は最上段の確率が 0.47 だった。

## 6. confidence は「迷い」の指標で、「正しさ」の指標ではない

- 低い confidence には誤りが集まる。見直しの優先順位づけに使える。
- 高い confidence でも、系統的な誤りは検出できない。Jev が自信を持って間違える。
- 系統的な誤りの原因は、たいてい入力の情報不足。モデルの能力不足ではない。

根拠: 文中の「お前」が誰を指すかを取り違えた判定が、confidence 0.97 で出ていた。取り違えを解く情報は state に入っていなかった。

## 7. state には、人間が同じ判断をするときに使う情報を全部渡す

「この state だけを見せられた人間が、正しく判断できるか」で確認する。できないなら、Jev にもできない。

- 判定対象と文脈は別のキーで渡し、どれが判定対象かを instructions で固定する。
- 手元にあるメタデータ(投稿者の属性、カテゴリ、時刻など)は、判断に効くなら惜しまず渡す。
- 内輪の用語や略語は、premise に用語集として書く。知らない語は一般的な意味で読まれる。

根拠: 投稿者の立場を示す列が元データにあったのに、state に入れていなかった。入れていれば解けた誤りが複数あった。ドメイン用語を一般語として誤読した判定は、どれも confidence が低かった。

## 8. 手元の既存ラベルは、正解でなくても検算に使える

元データにあるラベルやメタデータと Jev の判定を突き合わせ、食い違うものを見直しキューにする。ラベルが不正確でも構わない。食い違いの中に、Jev の誤りとラベルの誤りの両方が集まる。

根拠: 投稿者の自己申告と Jev の判定が強く食い違う21件を見るだけで、系統的な誤りの型が1つ見つかった。300件を全部読む必要はなかった。

## 9. Choice は逃げ道を用意し、次点も残す。ただし `other` が最多になったら設計を見直す

- 逃げ道の選択肢(`other`、対象外)がないと、無関係な入力がどこかに無理に入り、集計が汚れる。
- `other` が最多になったら、そこに落ちているものを読んで選択肢を足す。`other` は残余であるべき。
- 次点の選択肢とその確率を保存する。複数の話題を持つ入力や、選択肢の見直しに効く。ただし次点の確率が 0.1 未満ならノイズなので捨てる。
- 入力が本質的に複数ラベルなら、Choice ではなく選択肢ごとの Noul を並べる。
- 選択肢が多い Choice や、判断が難しい Choice は全体に confidence が低い。confidence で足切りして使う。

根拠: 10択の Choice で `other` が3割を占め、中身は「好意的な感想」という1つのまとまりだった。4択の Choice の1つは、4分の1の行で confidence が 0.4 未満だった。

## 10. examples は強く効く。だからチューニング用と検証用のデータを分ける

criteria の examples に入れた文言は、ほぼ確実にその選択肢に入る。効果が大きい分、評価データから examples を取ると評価が甘く出る。

- 質問文を直すために見るサンプルと、直した結果を確かめるサンプルを分ける。
- seed 固定のサンプルは、質問の版どうしの比較に使う。別の seed のサンプルは、検証に使う。
- examples は実データの言い回しをそのまま使わず、固有名詞を伏せるなど一般化して書く。

根拠: examples に入れた文言と同じ行が confidence 0.99〜1.0 で判定されていた。同じ300件で直して同じ300件で確かめていたので、改善幅は実際より大きく見えている。

## 11. 運用の型

- **質問はコードとして版管理する。** 質問文を変えたら版を上げ、版を出力ファイル名に入れる。版違いの結果を並べて比較できる。
- **生の確率を全部保存する。** ラベルだけ保存すると、閾値や集計を変えるたびに再判定が要る。確率を残せば、後から何度でも切り直せる。
- **複数の質問を1回の呼び出しにまとめる。** 同じ state に対する質問は `system_one` 1回で済む。
- **並列に回し、失敗は行単位で記録して止めない。** 失敗した行にエラーを書いて先に進む。
- **小さく回してから全件を回す。** 50件で質問文を直し、300件で分布と閾値を決め、それから全件を回す。
- **サンプルは seed 付きシャッフルの先頭から取る。** 件数を増やしても前回の対象を含むので、件数違いの結果を比較できる。

根拠: 8つの質問を1回にまとめ、並列8で300件を回して失敗は0件だった。

## 12. 判定がおかしいときに疑う順番

1. **state に情報が足りているか。** 人間がその state だけで判断できるか。
2. **質問が複数の軸を持っていないか。** 除外条件や「かつ」を含んでいたら、質問を分ける。
3. **criteria に紛らわしいケースが書かれているか。** false 側や `not_for` に足す。
4. **ドメイン用語を誤読していないか。** premise に用語集を足す。
5. **閾値が質問の分布に合っているか。** 分布を見て決め直す。

モデルを疑うのは最後。今回見つかった誤りは、ほぼすべて 1〜5 のどれかで説明がついた。

## まとめ

Jev は自然言語に対する型付きの判定関数。使う側の仕事は次の4つになる。

1. 1軸ずつの質問を書く。
2. 判断に必要な情報を state に入れる。
3. 確率をそのまま保存し、分布を見て閾値を決める。
4. 判断のロジックはコードで組み合わせ、食い違いと低 confidence から見直す。
