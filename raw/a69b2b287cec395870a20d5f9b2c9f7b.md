# LLM-as-a-Verifier をわかりやすく解説する

> 論文: [LLM-as-a-Verifier (arXiv: 2607.05391)](https://huggingface.co/papers/2607.05391)
> 一言でいうと: **LLMの「隠れた確率表」を使って、AIエージェントの解答を精密に採点し、複数の解答から最良のものを選ぶ手法**

## 背景: エージェントは「解ける」より「選べない」ことが問題

コーディングエージェントなどにタスクを解かせると、同じタスクでも実行のたびに結果がブレます。5回実行すれば、そのうち1回は正解しているのに、どれが正解か分からないから拾えない——これが現状のもったいないところです。

実際、Terminal-Bench というベンチマークでは:

- 1発勝負の正解率: **81.8%**
- 5回実行して「正解を知っている神様」が選んだ場合の上限: **89.9%**

この約8ポイントの差が「解けているのに選べていない」損失です。この論文は、この差を埋めるための**高精度な採点係（Verifier）**の作り方を提案しています。同じ設定で **86.4%** まで引き上げており、差の半分以上を回収しています。

## 鍵になる仕組み: logprob（モデルの内心を覗く窓）

### LLMは実は「1つの答え」を決めていない

LLMが文字を出力するとき、内部では全候補トークンに確率を割り振っています。採点を頼んで「7」と返ってきたとき、裏側はこうなっています:

| 候補 | 確率 |
|------|------|
| "7"  | 50%  |
| "6"  | 30%  |
| "8"  | 20%  |

普段見えるのは、ここからサンプリングされた「7」だけ。**logprob とは、この裏側の確率（の対数）を API 経由で受け取れる正式な機能**です。OpenAI なら `logprobs: true`、Gemini (Vertex AI) なら `response_logprobs` をリクエストに足すだけで返ってきます。

ハッキングでも内部への侵入でもありません。モデルの重みや思考過程は相変わらずブラックボックスですが、**最終出力の直前に必ず作られている確率表**を、捨てずに受け取るだけです。

### なぜプロンプトで「細かく採点して」ではダメなのか

1. **モデルが書く「6.9点」は内心の確信度を反映している保証がない。** それっぽい数字を書いただけかもしれない。
2. **引き分けが多発する。** 整数採点だと解答AもBも「7点」になりがちで、優劣がつけられない。

logprob を見れば、A は「7 が確率90%でほぼ確信」、B は「6/7/8 で割れている」と分かり、表面上の同点に差をつけられます。10人の審査員の多数決の結果だけ聞くのではなく、**札の内訳まで集計する**イメージです。

## 採点方式: 3つのつまみでスケールする

Verifier の最終スコアは、次の3段階で作られます。

### ステップ1: 期待値を取る（粒度 G）

出力された「7」をそのまま使わず、確率表全体の重心（期待値）を計算します:

```
6 × 0.30 + 7 × 0.50 + 8 × 0.20 = 6.90点
```

これで整数の「点」が連続値になります。さらに目盛り自体を 1〜10 ではなく 1〜20、1〜50 と細かくでき（= 粒度 G）、粒度を上げるほど正解と不正解の解答がスコア上で分離しやすくなります。

### ステップ2: K回繰り返して平均する（反復 K）

同じ解答を同じ Verifier に複数回（例: 4回）採点させて平均します。LLM の採点は毎回ブレるので、ダーツを4投して平均位置を見るように、ノイズを均します。

### ステップ3: 基準を分解する（基準 C)

「総合何点？」と漠然と聞くのではなく、「正しさ」「完全性」「効率」のように基準を分けて、それぞれ別々にステップ1〜2を実行し、最後に平均します。狭い問いのほうが LLM は正確に答えられるためです。

**最終スコア = C個の基準 × K回の反復ごとに期待値を取り、すべて平均したもの**

G・K・C の3つのつまみを増やすほど採点精度が上がる——これが論文のいう「検証のスケーリング」です。事前学習・事後学習・テスト時計算に続く、第4のスケーリング軸という位置づけです。

## 使い方: Best-of-N 選択

1. エージェントに同じタスクを N 回解かせ、N 個の解答（軌跡）を得る
2. 各解答に上記のスコアを付ける
3. 総当たりで比較し、最も勝った解答を採用する

### 報告されている結果

| ベンチマーク | スコア |
|---|---|
| Terminal-Bench V2 | 86.5% |
| SWE-Bench Verified | 78.2% |
| RoboRewardBench | 87.4% |
| MedAgentBench | 73.3% |

追加学習は一切不要。報酬モデルを別途訓練する必要もなく、logprob が取れる API とプロンプトだけで動きます。副産物として、細かいスコアは RL の密な報酬やエージェントの進捗モニタリングにも使えます。

## 実際に試すには

公式リポジトリ: `github.com/llm-as-a-verifier/llm-as-a-verifier`

```bash
pip install google-genai tqdm
# .env に Vertex AI の API キーを設定（logprob 取得に必要）

python scripts/run_terminal_bench.py \
  --granularity 20 \      # 粒度 G
  --n-verifications 4 \   # 反復 K
  --criteria 3            # 基準 C
```

コアロジックは `scripts/verifier_core.py` にあるので、自分のエージェントに組み込むならここを読むのが早いです。

### 導入時の注意点

- **logprob を返す API が必須。** 返さないプロバイダー/モデルでは使えない
- **コストは N 倍＋検証分かかる。** これは「1回の実行を賢くする」手法ではなく「N回実行して良いものを選ぶ」テスト時スケーリング手法。レイテンシとコストが許容できる場面（重要なタスク、バッチ処理など）向け
- N が大きい場合、総当たり比較のコストを抑えるランキングアルゴリズムが論文で提案されているので参照のこと

## まとめ

- LLM の出力の裏には毎回「確率表」があり、API オプション（logprob）で正式に受け取れる
- その確率表の**期待値**を採点に使うと、整数採点より細かく・較正された連続スコアが得られる
- **粒度 × 反復 × 基準**の3軸で採点精度をスケールできる
- Best-of-N 選択に使うと、追加学習ゼロで主要エージェントベンチマークの数ポイント改善が得られる
