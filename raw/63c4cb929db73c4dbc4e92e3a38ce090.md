# Google と monorepo — 最適性と選択のタイミングの整理

## TL;DR

- Google が monorepo なのは事実。ただし Git ではなく自社製の Piper + CitC で運用している
- monorepo は「最適解」ではなく、Google の条件下(密結合な単一プロダクト群 + 潤沢なインフラ投資 + テスト文化)での合理解
- 「monorepo を選んだ瞬間」は存在しない。創業時の初期状態がたまたま 1 repo で、その後「分割するか」という問いに毎回「しない」と答え続けた結果である
- ただし 2010 年前後の Perforce 限界期に「Git + repo 分割」という現実的な代替案を退けて Piper を自作しており、ここで惰性が意識的な再選択に変わった

---

## 1. 前提: Google の monorepo とは何か

出典: Potvin & Levenberg, "Why Google Stores Billions of Lines of Code in a Single Repository" (CACM, 2016)

- 2016 年時点で約 20 億行 / 8600 万ファイル超 / 約 86TB
- VCS は Git ではなく自社製の **Piper**(分散ストレージ上の中央集権型 VCS)
- 開発者はリポジトリ全体を checkout しない。**CitC (Clients in the Cloud)** が全体を FUSE ファイルシステムとして見せ、実体化するのは変更したファイルのみ
- **trunk-based development**: 長命ブランチがなく、全員が head に小さいコミットを頻繁に入れる
- **OWNERS** によるディレクトリ単位の所有権で、物理的には 1 repo でも論理的には縄張りが分かれている
- **Blaze**(OSS 版: Bazel)が変更の影響範囲だけを差分ビルド・差分テストし、presubmit CI と常時テスト基盤(TAP)が head の健全性を守る
- 大規模一括変更は **Rosie** で自動化
- Android や Chrome など一部 OSS 系プロジェクトは Piper の外で Git を使用

## 2. monorepo とマルチレポの本質的な違い

repo の個数の問題ではなく、**依存の解決方法**の違い。

| | マルチレポ | monorepo |
|---|---|---|
| 依存の解決 | バージョン番号で pin し、たまに上げる | 常に head |
| 境界の契約 | semver・後方互換が必須 | 不要。代わりに変更者が全利用箇所を直す |
| 横断変更 | 各 repo でリリース → 利用側に移行依頼 | 1 コミットで atomic に変更 |
| 障害時 | バージョンの組み合わせの切り分けから | 1 コミットの revert で全社が戻る |
| ダイヤモンド依存 | 発生しうる | 原理的に存在しない |
| 可視性 | 利用箇所の全社的把握が困難 | 全コードが grep 可能 |

monorepo の最大の実益は **atomic change**: 共通ライブラリの API 変更と全呼び出し箇所の修正を 1 コミットで行え、「リリース」「バージョン」「アップグレード依頼の行脚」という工程自体が消える。

## 3. monorepo は最適解か

### 成立条件(Google が揃えているもの)

- 差分ビルド/差分テスト基盤(Blaze)と巨大 CI — 「壊れた head が存在する時間を最小化する機械」
- 仮想ファイルシステム(CitC)— 「全部 clone」を誰もしなくてよい
- 大規模変更の自動化(Rosie)— 「全利用箇所を直す責任」を人力から解放
- 強いテスト文化 — presubmit の防御はテストがあるコードにしか効かない
- これらを維持する専任インフラチーム

### 弱点・批判

- **コストの不可視化**: バージョン境界がないため依存が安易に増え、依存グラフが密になる。ビルド・テストの計算コストは基盤(≒札束)で殴っている
- **組織の結合を強制**: atomic change の裏返しは「他チームの都合で自分のコードが今日書き換わる」こと。チーム自律・リリース独立を重視する組織には毒
- **契約の規律が育ちにくい**: 「壊したら直せばいい」ため、公開 API として切り出す設計力が訓練されない。OSS 切り出し時の境界整理の苦労はこの副作用とも言われる
- **同スケールの反例が存在**: Amazon はサービス完全分離・API 契約の思想(マルチレポ側)で同様に成功している

### 結論

- repo 構成は独立した技術選定ではなく**組織設計の従属変数**(Conway の法則の変奏)。密に協調する一枚岩の組織なら monorepo が低摩擦、自律分散の組織ならマルチレポが低摩擦
- 「巨大で密結合な単一プロダクト群 + 潤沢なインフラ投資」が揃うなら monorepo は非常に強いが、条件が欠けると悪手になりうる
- なお大多数の組織(数十人規模)にはこの議論自体がオーバーキル。1 つの git repo で普通に回るし、それは「Piper 的 monorepo」ではなくただの 1 repo。問題が顕在化するのは数百人・数百万行を超えてから

## 4. Google はいつ monorepo を「選んだ」のか

### 劇的な選択の瞬間は存在しない

- 1998 年、創業時に当時のスタートアップの普通としてコードを 1 repo に置いた(CVS → すぐ Perforce)。2 人の会社が repo を分ける理由はなく、この時点で「monorepo 戦略」という概念すらない
- 以後、成長の各局面で訪れた「分割するか?」という問いに、毎回「分割しない + ツールで延命」を選び続けた:
  - Perforce が苦しい → 世界最大級の Perforce インスタンスを専任チームが気合で運用
  - ビルドが遅い → Blaze を自作
  - Perforce が単一サーバーの限界に(2010 年前後)→ Piper を自作(2012 年頃移行)
  - checkout が重い → CitC を構築
- 各時点では「全社の repo 分割・依存再編」より「ツール 1 個の自作」のほうが常に安く見えた。その 15 年の積み上げが事後的に「戦略」と呼ばれるようになった

### ただし途中から意識的な再選択になった

- 真の分岐点は **2010 年前後の Perforce 限界期**。Git(2005 年生)はすでに主流化しつつあり、「Git 移行 + repo 分割」は現実的な選択肢として社内で検討された
- それでも Piper 自作 + monorepo 維持を選んだのは、この頃には atomic change や head 解決の利益を組織が実感しており、手放したくなかったから
- 2016 年の CACM 論文は、この再選択の事後的な言語化・正当化と読める

### 描写としては

**惰性で始まり、途中から信念になった。** パスディペンデンシー(初期状態の偶然 + 分割コスト回避の連続)が土台だが、少なくとも一度はコストを払ってでも維持すると能動的に選び直している。

### 他社との対比

- **Meta (Facebook)**: ほぼ同じ道。1 repo で開始 → 巨大化 → 2013 年頃 Git 移行を検討し、Git コミュニティに巨大 repo 対応を打診するも折り合わず → Mercurial を魔改造(のちにクライアント Sapling を OSS 化、仮想 FS は EdenFS)
- **Microsoft**: Windows を Git で monorepo 管理するために VFS for Git(現 Scalar)を開発。成果は Git 本体の partial clone / sparse-checkout に還流
- **Amazon / Netflix**: マイクロサービス・チーム自律の組織方針が先にあり、repo もそれに従って分散
- いずれも「repo 構成は組織の歴史の従属変数」という結論を補強する

## 5. 関連ツール(Piper/CitC は非公開)

Piper と CitC は Google 内部インフラ(Spanner 等)に深く依存しており OSS 化されていない。思想を体験するには:

- **Bazel** — Blaze の OSS 版。monorepo スタックの最重要ピース
- **Sapling + EdenFS** (Meta) — 「触ったファイルだけ実体化」という CitC と同じ発想の OSS
- **Git partial clone / sparse-checkout** — Microsoft の Scalar の成果が取り込まれたもの。素の Git で巨大 repo に立ち向かう際の標準装備
