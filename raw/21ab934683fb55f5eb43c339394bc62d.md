### 何を狙っている言語か

公式のvisionドキュメントに明確に書かれています。狙いは「N language問題」の解消です。現在のAI開発はPython + C++ + Rust + CUDAを継ぎ接ぎする必要があり、しかもハードはNVIDIA GPU、AMD、TPU、カスタムASICと断片化している。これを**1つの言語でCPUからGPU・アクセラレータまで全部書ける**ようにするのがMojoの存在意義です。Modular社のミッション「AI computeの民主化」の中核部品で、実際に同社のMAX推論エンジンのカーネルはCUDAを使わずMojoで書かれています。

面白いのは「なぜ既存言語の拡張やPython DSL(Tritonのような)にしなかったか」を明示している点で、既存言語(C++/Rust/Swift/Julia)はCPU時代の設計でTensor Coreやfloat6のような新データ型に対応できず、eDSLは母体言語の文法に縛られてツーリングと予測可能性が壊れる、という理由で「ゼロから作る」を選んだと書いています。

### 既存言語との違い

**Pythonとの違い** — 見た目はPython構文ですが実行モデルは完全に別物です:

- 静的型付けで、AOTコンパイルによりネイティブ機械語を吐く(インタプリタなし)
- **値セマンティクスがデフォルト**。`b = a` は参照共有ではなくコピー(非自明な型は `.copy()` を明示)。共有したいときだけ `ref b = a`
- 関数引数はデフォルト不変で、変更したいなら `mut` を明示
- GCも参照カウントもなく、**Rust風の所有権モデル**(値の所有者は常に1つ、寿命が尽きたら破棄、参照があれば寿命延長)でメモリ管理

ただしPython互換は捨てておらず、CPythonランタイムをそのまま埋め込んで既存Pythonライブラリを100%呼べる+逆にMojoをコンパイルしてPythonの拡張モジュールとして呼べる、という双方向interopが用意されています。「Pythonを置き換える」より「Pythonの高速部分を段階的にMojoへ移す」導線です。

**Rust/C++との違い** — 所有権はあるものの「safe-onlyに閉じ込めない」方針で、必要なら `Pointer` と `alloc/dealloc` で生メモリを触れます。ロードマップには「RustやC++と機能で張り合う気はない、小さく教えやすい言語に保つ」と明記。C++の複雑性スパイラルを名指しで反面教師にしています。C ABI互換のFFIもあります。

**最大の差別化はメタプログラミング**です。ここがこの言語の心臓部でした:

- `[]` がコンパイル時パラメータ、`()` が実行時引数、と構文レベルで分離。`def matmul[dtype: DType, size: Int](...)` のように型も値もコンパイル時に渡せる
- `comptime`(Zig由来の発想)でコンパイル時評価・ループ展開・特殊化
- C++テンプレートの「コンパイル時特殊化」を、エラーメッセージ・コンパイル速度・表現力で大幅に改善したものと自己定義

なぜこれが核かというと、「データ型 × 演算 × ハード」の組み合わせ爆発を手書きカーネルで埋めるのは不可能なので、パラメトリックなコードから各ハード向けに特殊化コードを生成する、という戦略だからです。cuBLASを超えるmatmulをこの仕組みで統一実装した、というのが初期の実証でした。

**アーキテクチャ面** — MojoはMLIR Core(linalg等のAIダイアレクトは使わず、コンパイラ構築基盤の部分だけ)の上に「KGEN」というフレームワークで構築されていて、**MojoコードからMLIRダイアレクト操作を直接書ける**(MLIRの糖衣構文として振る舞う)のが独特です。パラメータ実体化前のIRを保持するので、MAXのグラフコンパイラがカーネルのIRを覗いてfusionなどの変換をかけられる。GPUコードも同一言語内で書けて、stdlibに `std.gpu` があり `thread_idx` / `block_idx` 等でCUDA風のカーネルを普通のMojo関数として書いてenqueueします(実例が `max/examples/custom_ops/kernels/vector_addition.mojo` にあり、CPU版とGPU版を同じファイルで書き分けていて分かりやすいです)。

### 現在地

ロードマップによると、Phase 0(言語基盤)とPhase 1(高性能CPU+アクセラレータ、コンパイラのオープンソース化)は完了。今はPhase 2「システムアプリケーションプログラミング」の途中で、async、代数的データ型とパターンマッチ、動的トレイト、可変エイリアシングを含むメモリ安全性の仕上げなどが進行中。Phase 3で動的オブジェクト指向(Python的な書き味)に踏み込む計画です。逆に言うと、Python構文とはいえ現状は型注釈必須寄りで、Pythonライブラリ相当のstdlib網羅性もまだ意図的に後回しです。proposalsディレクトリを見ると `fn`→`def` 移行、origin(Rustのlifetime相当)設計、境界チェックなど、言語のコア設計がまだ活発に動いているのが分かります。

一言でまとめると、**「Pythonの顔をした、MLIRネイティブでcomptime特化のシステム言語」で、狙いはCUDA独占の打破とAIスタックの単一言語化**。技術的に一番ユニークなのはメタプログラミングとMLIR直結の部分で、所有権や値セマンティクスはRust/Swiftからの借用、という構図です。

さらに深掘りしたい部分(例えばorigin/lifetimeの設計、trait系、stdlibの実装の読み方など)があれば言ってください。

## Claude

そうです。もっと正確に言うと「**AIのハードウェアを動かす低レベル側**のデファクト」を狙ってます。

今のAI開発って、実は言語が分業になってるんですよ:

- 研究者が書くのは Python
- でも実際にGPUを速く動かす部分は C++ と CUDA(NVIDIA専用)

この「速い部分」が CUDA でしか書けないせいで、みんな NVIDIA に縛られてる。Mojo は「Python みたいに書けて、CUDA の代わりになる言語」を作って、この縛りを壊そうとしてます。NVIDIA でも AMD でも他のチップでも、同じコードで動く、というのが売り。

なので Python を置き換えるというより、**Python の下で動いてる C++/CUDA の層を置き換える**のが当面の狙いです。「Python と文法を似せてる」のは、AI をやってる人がほぼ全員 Python 使いだから乗り換えやすくするため。

ただし現状はまだ発展途上で、作ってる Modular 社の製品(推論エンジン)の中では実戦投入されてるけど、世間のデファクトになるかは全然これからです。
